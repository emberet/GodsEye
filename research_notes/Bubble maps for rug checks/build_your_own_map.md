# Building our own Solana bubble map (holder cluster graph) for pre-copy rug screening

Scope and honesty notes. Research run 2026-10-27, about 55 tool calls. "Cited Findings" are things I read on the linked page (or in the GodsEye files, cited as file:line). "Inferences" are my own engineering reasoning, including Solana mechanics I know but did not source on a page; they are labelled as such. Several vendor pages publish no thresholds or algorithms; those are listed under Gaps instead of guessed. Two sources were read via GitHub's public REST API (search and tree listings) and `raw.githubusercontent.com`, GET only, no keys, no sign-ups.

## 0. What GodsEye already does, and precisely what it misses against a Bubblemaps-style map

### Takeaway
GodsEye's check is a four-part screen (top-10 concentration, creation-slot buy share, one-hop first-funder grouping of the top-10 wallets, plus RugCheck's insider networks). It cannot see the pattern Bubblemaps is best known for catching (many mid-sized wallets, each below the top-10 cutoff, linked by transfers or a shared funder), it never uses token or SOL transfers between holders as edges, and its funder grouping has no exchange or service filter so it can both false-alarm (two unrelated CEX withdrawals) and go blind (any wallet with 1,000+ signatures returns "no funder").

### Cited Findings
**What the bot does (from the code)**
- Holder universe is `getTokenLargestAccounts` only. Solana's RPC returns at most 20 token accounts for that call — `agent/src/market/holders.ts:122` (call), [Solana docs: getTokenLargestAccounts](https://solana.com/docs/rpc/http/gettokenlargestaccounts) (max 20). Owners come from `getMultipleAccounts` (`holders.ts:127`), program-owned accounts are dropped with an on-curve test (`holders.ts:83-89, 131`), and the top 10 owners form `top10Pct` (`holders.ts:133-134`).
- Launch bundle = tokens bought from a pool/curve in the mint's first two slots (`firstSlot + 1`), computed from the mint's earliest signatures: two pages of `getSignaturesForAddress` (limit 1000) and, if the second page is also full, it returns `null` ("too busy to measure") (`holders.ts:137-157`, window at line 146, null at 156; the UI string is at line 61). Only the 40 oldest early signatures are fetched with `getTransaction` (line 146-147).
- Funder cluster: for each of the top-10 holders, `getSignaturesForAddress(limit 1000)`, skipped (returns null) if the wallet has 1,000 or more signatures, then `getTransaction` on the oldest signature and `findFunder` (`holders.ts:160-167`). `findFunder` picks the account whose lamports fell the most in the wallet's first transaction while the wallet's rose (`agent/src/chain/parse.ts:301-318`). Holders are grouped by that one funder; a group counts as a cluster at 2+ holders, or at 1 if the funder is the creator (`holders.ts:170-183`). There is no exchange, bot-hub or "service wallet" exclusion in that grouping.
- Funders are cached only for tracked wallets (column `wallets.funder`, `shared/src/schema.ts:56-57`); holders of a candidate token are looked up fresh each time.
- RugCheck insider networks are used only when RugCheck has mapped the coin (`holders.ts:188-195`, `rugcheck.ts:46`). The whole holder check runs under a timeout (default 8,000 ms, `agent/src/config.ts:163`) and fails closed (`rugcheck.ts:177-204, 248-249`). Defaults: bundle 25%, cluster 15%, top-10 50%, insider 20% (`config.ts:155-161`).
- The Yellowstone stream already subscribes to every non-vote, non-failed transaction touching the DEX programs (pump.fun, PumpSwap, Raydium, Orca, Meteora, Jupiter) — `agent/src/stream/stream.ts:127-134`, `agent/src/chain/programs.ts:7-17`. Per-wallet history for untracked wallets lives only in memory: `LiveBook` keeps up to 60 recent swaps per wallet and no per-mint index (`agent/src/stream/live-book.ts:1-40`); `wallet_swaps` stores only tracked wallets (`shared/src/schema.ts:80-109`, stream header at `stream.ts:1-12`). The Jito tip account list in `programs.ts:34-43` matches Jito's published eight.

**What Bubblemaps does (for comparison)**
- A link means "there has been an on-chain transfer between those holders"; in V2 transfers can involve any token and sometimes cross-chain; links can be filtered by token and USD value — [Bubblemaps wiki: How does it work](https://wiki.bubblemaps.io/bubblemaps-v2/how-does-it-work). An older Bubblemaps post says two bubbles connect if there was at least one historical transaction in the chain's gas token, drawn only between the top 250 holders, dotted for one-way, solid for two-way (per a fetched summary of [Find Deeper Connections](https://blog.bubblemaps.io/find-deeper-connections-between-wallets/); the product has changed since, so treat the V1/V2 difference as unresolved).
- Map covers the top 250 holders in the app and 80/250/500 via the API; CEX, DEX and contract bubbles are hidden by default; "supernodes" (very high transaction volume) have reduced features and two connected supernodes show no link — [wiki](https://wiki.bubblemaps.io/bubblemaps-v2/how-does-it-work), [API: Get Token Bubble Map](https://docs.bubblemaps.io/data/api/tokens/map.md).
- Magic Nodes add non-holder addresses (even zero-balance ones, for example a shared gas-funding or deposit address) that connect holders; Time Nodes are suggested nodes for wallets with coordinated timing such as funding or activation at about the same time — [Magic Nodes wiki](https://wiki.bubblemaps.io/bubblemaps-v2/magic-nodes), [search summary of the wiki](https://wiki.bubblemaps.io/bubblemaps-v2/how-does-it-work). The exact computation of either is not published.
- Cluster = "a set of wallets linked by on-chain behavior over time" (shared funding sources, transfers between wallets, patterns across multiple tokens); bundle = "a set of wallets that transacted together during the token launch", detected by same block or within seconds; the two are separate objects, and a token can have no bundle yet a large cluster — [Bubblemaps: bundle vs cluster](https://blog.bubblemaps.io/whats-the-difference-between-bundle-cluster-2/).
- A flagged example: the RugProof creator sent SOL to 162 wallets which bought about half the supply at launch — [search summary of Bubblemaps' rug-pull guide](https://blog.bubblemaps.io/how-to-spot-a-rug-pull-using-bubblemaps-before-it-happens/).

### Inferences
- **Miss 1 — the long tail.** With at most 20 token accounts (fewer owners once the bonding-curve/pool account and any multi-account owners are removed), a sybil ring of 40 wallets each holding 0.5-1% is invisible: none of them is in the top 10, so `clusterPct` is 0. The RugProof-style pattern (162 wallets) is exactly this. This is the single largest gap and it is structural, not a tuning issue.
- **Miss 2 — no edges between holders.** The bot never looks at token transfers or SOL transfers *between* holders (Bubblemaps' core link), only at the first funder. Supply split by transfer from one bundle wallet to fresh wallets after the buy is therefore invisible, as is a funder who is not the *first* funder (a wallet later topped up by the deployer).
- **Miss 3 — "launch bundle" is flow, "cluster" is stock, and they are never joined.** `launchBundlePct` is tokens bought in two slots; it ignores whether those buyers still hold, and the buyers are not linked to the current top-10. A bundle that already sold shows as 25%+ bought (conservative, possibly a false block); a bundle that moved tokens to fresh wallets shows full but unlinked.
- **Miss 4 — window.** Two slots is narrower than Bubblemaps' "within seconds" and than the community norms (the sybil skill below uses 3-slot clusters and a 5-slot bundle window), so snipers landing in slots 3-10 are not bundled.
- **Miss 5 — null on busy coins.** Any mint with roughly 2,000+ signatures yields no launch metric (`holders.ts:154-156`); coins that are already a few minutes into a pump are exactly the ones a copy signal usually arrives on. Likewise any holder with 1,000+ signatures yields no funder (`holders.ts:163`), so bots and old wallets silently drop out of the cluster.
- **False-positive risk.** `findFunder` can return an exchange hot wallet, a bot-platform fee wallet or an aggregator account as "the funder"; two unrelated top holders withdrawing from the same exchange then form a "cluster" and, if they hold more than 15% together, hard-block the buy. Bubblemaps and the other tools below exclude exchanges/services from cluster edges; the bot does not.
- **No program-account filter beyond off-curve.** The on-curve test removes PDAs (bonding curve, PumpSwap pool, vault escrows) but not on-curve non-holders: CEX wallets, burn-style wallets, LP lockers with keypair authority, or a Mayhem-mode agent wallet if that is a normal keypair (unverified, see section 4).
- **Cost is dominated by repeated per-token history reads** with no cross-token reuse: funders and wallet ages are never cached for arbitrary holders even though a wallet's first funder is immutable once it exists.

### Gaps
- I did not run the bot against sample tokens, so the 60-call / 3-9 s figures in the brief are taken as given, not re-measured.
- RugCheck's insider-network algorithm is undocumented in anything I could retrieve (search returned no primary source).

## 1. Graph construction: which edges, how many hops, how to avoid false links

### Takeaway
Use a typed, weighted edge set and cluster only on high-precision edge types: exact edges (direct SOL or token transfer between holders, same-transaction buys, same fee payer, a shared non-service funder with small fan-out) and treat timing/same-slot/amount similarity as supporting evidence. One funder hop plus "intermediary" (magic) nodes is the practical limit at 2-10 s; deeper hops are research-grade. The false-link controls are a deny-list of program/fee/tip accounts and a service-wallet filter (labels plus fan-out/throughput heuristics).

### Cited Findings
**Edge types in use elsewhere**
- Bubblemaps: direct transfers between holders (any token), plus Magic Node intermediaries and Time Nodes (coordinated timing); the API returns `GROUPED_TRANSFER` relationships grouped by (from, to, token) with `total_value`, `total_transfers`, `first_date`, `last_date` — [Bubblemaps API: map](https://docs.bubblemaps.io/data/api/tokens/map.md).
- Seizd (open source, section 5) defines these edge types: `funded_by` (most recent inbound SOL transfer of at least 0.01 SOL before the wallet's first acquisition; drawn only if the funder funded 2+ analysed wallets, is the deployer, or is a holder), `shared_funding_tx` (one transaction paying several analysed wallets; high), `same_tx_buy` (several distinct wallets buying in one transaction; high), `same_slot_buy` (timing only; low; "never used for clustering"), `bundle_fingerprint` (buys at consecutive positions in one block with identical construction such as priority fee, programs, fee/tip recipients), and `token_transfer`/`sol_transfer` between analysed wallets (token transfers out of early buyers always drawn). Clusters are connected components over medium/high-confidence edges; edges touching pools, curves, burn addresses, exchanges or high-throughput funders are never cluster-eligible — [seizd graph.ts](https://raw.githubusercontent.com/benguadomar/seizd/main/server/src/analysis/graph.ts).
- Pine Analytics' pump.fun study used a one-hop filter (same-block buyers with a direct SOL transfer to or from the deployer before launch) and says multi-hop (5-7 hop) funding was excluded for cost — as summarised in the GodsEye note [wallet_clustering.md](/Users/srinjoydas/GodsEye/research_notes/Memecoin%20wallet%20tracking%20methods/wallet_clustering.md), original [Pine Analytics](https://pineanalytics.substack.com/p/exit-liquidity-machines) (not re-opened in this run).
- Community "sybil detection" skill (MIT): funding trace follows each holder back "1-2 hops" in prose but the code does one hop (`max_hops` unused), keeps native SOL transfers above 0.001 SOL, clusters 3+ holders sharing a funder; same-slot grouping uses a window of 3 slots anchored on the first buy, groups of 3+; bundle window 5 slots; it states it does not exclude exchanges — [claudeskills mirror of agiprolabs/claude-trading-skills](https://claudeskills.info/skills/agiprolabs/claude-trading-skills/sybil-detection/).
- Behavioural linking without any money flow: MadeOnSol's linked-wallets endpoint compares first buys within a 2-second window across 3+ shared tokens, scoring on time and size deltas; it calls the result "a strong hint, not a proof" — [MadeOnSol article](https://madeonsol.com/blog/solana-linked-wallets-detection-co-buy-clustering).

**Jito bundles, tips and what is visible**
- A bundle is up to 5 transactions executed sequentially and atomically within a single slot; a tip is a SOL transfer (top-level or CPI) to one of 8 tip accounts, minimum 1,000 lamports; bundle id is a SHA-256 over the transaction signatures; `getBundleStatuses` takes bundle ids (not signatures) and returns null if not landed — [Jito low-latency docs](https://docs.jito.wtf/lowlatencytxnsend/), [Helius getBundleStatuses via search summary](https://www.helius.dev/docs/api-reference/sender/getbundlestatuses.md). The 8 addresses are listed on the Jito page and are identical to `JITO_TIP_ACCOUNTS` in `agent/src/chain/programs.ts:34-43`.
- I found no official endpoint that maps a transaction signature to its bundle; only a third-party Go client method that appears to do so — [search summary of jito-go](https://beta.pkg.go.dev/github.com/weeaa/jito-go/api).

**Exchanges, services, and false links**
- Bubblemaps hides CEXs, DEXs, contracts and "hypernodes" (over 200,000 transfers) by default and states hidden nodes "are not considered in the relationships, score, and clusters computation" — [API: map](https://docs.bubblemaps.io/data/api/tokens/map.md).
- Bubblemaps itself says clusters can form innocently, for example friends withdrawing from the same exchange — [bundle vs cluster](https://blog.bubblemaps.io/whats-the-difference-between-bundle-cluster-2/).
- Elliptic notes shared custody infrastructure (omnibus wallets, exchanges) produces apparent co-control that is not common ownership, and recommends confidence scoring — [Elliptic: wallet clustering limits](https://www.elliptic.co/corpus/gen-3524/blockchain-privacy/wallet-clustering-limits.html) (via search summary).
- Seizd treats a funder as a "service" if it is labelled an exchange, or if its latest 1,000 signatures span under 6 hours (that is, 1,000+ transactions in under 6 h) — [seizd funding.ts](https://raw.githubusercontent.com/benguadomar/seizd/main/server/src/analysis/funding.ts). Seizd also excludes Jito tip senders and the System program as funders and requires at least 0.01 SOL for a funding edge (same file).
- Counter-example showing why CEX-funded rings still matter: the Dec 2025 $AVA case (23 wallets funded from Bitget and Binance in narrow windows with similar amounts and zero prior history) — as summarised in the GodsEye [wallet_clustering.md](/Users/srinjoydas/GodsEye/research_notes/Memecoin%20wallet%20tracking%20methods/wallet_clustering.md) citing [Blockchain.News](https://blockchain.news/flashnews/23-wallets-from-bitget-binance-sniped-ava-on-solana-bubblemaps-on-chain-alert-for-traders) (not re-opened here).
- Evasion is an active market: a GitHub search for "bubblemaps" returned many repos advertising tools to defeat Bubblemaps/InsightX analysis (multi-wallet SOL distribution, mixers, bundlers), several with double-digit stars and updates in 2026 — [GitHub search API: bubblemaps](https://api.github.com/search/repositories?q=bubblemaps&sort=stars&per_page=15). I did not read their code.

**Pump.fun-specific non-links (accounts that touch many wallets)**
- Fee recipients: 8 "normal", 8 "reserved" (used for mayhem-mode coins) and 8 "buyback" fee recipient addresses, listed in [pump-public-docs FEE_RECIPIENTS.md](https://raw.githubusercontent.com/pump-fun/pump-public-docs/main/docs/FEE_RECIPIENTS.md). Every `buy_v2`/`sell_v2` passes a fee recipient and buyback recipient, and a creator vault PDA derived from `["creator-vault", bonding_curve.creator]` — [pump IDL](https://raw.githubusercontent.com/pump-fun/pump-public-docs/main/idl/pump.json) (read directly; `buy_v2` account list).
- On "holder rewards" coins the creator fee is "set aside for the people who hold the coin" and pump.fun pays it out to holders, with no claim instruction; the recorded creator is a pump.fun-controlled address — [HOLDER_REWARDS_README.md](https://raw.githubusercontent.com/pump-fun/pump-public-docs/main/docs/HOLDER_REWARDS_README.md).

### Inferences
- **Recommended edge tiers** (my proposal, informed by Nansen-style tiers in the earlier GodsEye note, which gave no derivation of its percentages):
  - Tier A (cluster-eligible alone): direct SOL transfer or token transfer between two holders; two holders bought in the same transaction; shared fee payer or co-signer; both funded by the same non-service funder within a small fan-out (say 2-20 distinct holders-or-buyers across all tokens seen, a parameter to calibrate); funded by the creator or by a wallet the creator funded.
  - Tier B (needs two independent B signals, or one B plus a funder match): same-slot or same-bundle-fingerprint buys, near-identical buy sizes, funded from the same CEX hot wallet within a narrow window (seconds-minutes) with similar amounts, both wallets "fresh" (no prior history), identical-amount funding.
  - Tier C (display only): same slot only, wallet age, shared tip account (tip account choice is random by design per Jito's advice, so it carries almost no information).
- **Hops.** One funder hop plus holder-to-holder transfers covers the main laundering-free cases. A second hop (funder of the funder) is cheap only when the first funder is a *fresh* wallet (short history), which is the common sybil pattern ("deployer -> hub wallet -> 30 buyers"); stop at a service wallet or at a wallet with large fan-out. Beyond two hops, cost and false-link risk both grow (Pine excluded 5-7 hops for cost). This is a trade-off judgment, not a sourced threshold.
- **Cheap CEX/service detection, in order of cost:** (1) static deny-list built from your own data plus labels (see section 3: Helius batch identity, curated lists); (2) fan-out from your own funder cache: a funder that has funded N or more distinct wallets across all tokens you have ever screened is a service (the earlier GodsEye note proposed N=25 as "reasonable" but derived it by reasoning, not from a source; calibrate); (3) throughput test as in seizd (1,000 signatures in under 6 h, one RPC call per candidate funder, cached); (4) a Bubblemaps-like supernode cut (very high lifetime transfer count). Apply (2)-(3) only to funders shared by at least two wallets in the current map, which keeps the cost to a few calls.
- **Do not discard CEX-funded wallets entirely** (the $AVA lesson): downgrade the *funder* edge to Tier B and require timing/amount agreement.
- **Pump.fun deny-list for transfer edges:** the 24 fee recipients, 8 Jito tips, the pump and PumpSwap programs, all creator vault/bonding-curve/pool PDAs (off-curve anyway), and, for holder-rewards coins, the pump.fun distributor address (so that a reward payout to every holder does not create a star graph). The last item follows from the holder-rewards doc and is my extrapolation: I did not see payout transactions.
- **Bundle attribution inside a slot.** Bundles are not recorded on-chain as such; membership has to be inferred from block order (consecutive transactions in one slot, a tip transfer to a Jito tip account in one of them, shared fee payer/signer or identical construction), as seizd's `bundle_fingerprint` does. The gRPC transaction update carries the transaction's index in the block (my recollection of the Yellowstone protobuf, not re-verified), but `convertGrpcTx` currently keeps only `slot` (`agent/src/stream/convert.ts:49-63`); the index would need to be passed through.

### Gaps
- No source gives a validated numeric threshold for "this funder is an exchange" on Solana, nor false-positive rates for any single edge type.
- Bubblemaps' real link-creation thresholds (minimum transfer value or count, Magic/Time Node selection rules) are unpublished; the API docs state none.
- I did not find a public, complete, machine-readable Solana CEX/bot-hub address list (see section 3).

## 2. Clustering method and "share of supply held by a cluster"

### Takeaway
Connected components over a pruned, high-precision edge set (union-find) is what the open-source tools and, on the evidence available, Bubblemaps' visible clusters amount to; community detection (Leiden, not Louvain) is only worth adding for dense components that chain through a hub. Report cluster share as *current* balance over total supply, together with *peak/bought* and *sold* shares so wallets that already exited are not hidden.

### Cited Findings
- Seizd and the Bubblemaps docs both describe clusters as groups of linked holders; seizd explicitly uses union-find over cluster-eligible edges, labelling the result "potentially linked wallets" or "suspected coordinated cluster" and noting clusters are not proof of common ownership — [seizd graph.ts](https://raw.githubusercontent.com/benguadomar/seizd/main/server/src/analysis/graph.ts). Bubblemaps says clusters "form when linked bubbles have sent funds to each other" but publishes no algorithm or minimum size — [wiki](https://wiki.bubblemaps.io/bubblemaps-v2/how-does-it-work).
- Bubblemaps' API returns for each cluster `share`, `amount`, `holder_count`, `holders`, plus counts of magic and time nodes; metrics include `supply_stats` (cexs, dexs, contracts, fresh_wallets, top_10_adjusted, bundles) as fractions of supply, and the Gini, HHI and Nakamoto scores — [API: map](https://docs.bubblemaps.io/data/api/tokens/map.md). Holder bubbles represent current holdings, not historical ones — [wiki](https://wiki.bubblemaps.io/bubblemaps-v2/how-does-it-work).
- Louvain can yield badly connected communities: in the Leiden paper's experiments "up to 25% of the communities are badly connected and up to 16% are disconnected"; Leiden guarantees connected communities and is faster — [Traag et al., From Louvain to Leiden (arXiv 1810.08473)](https://arxiv.org/abs/1810.08473).
- Heuristic precision: Elliptic recommends treating clustering as evidence-backed inference, using multiple independent signals before asserting common control, and confidence scoring — [Elliptic](https://www.elliptic.co/corpus/gen-3524/blockchain-privacy/wallet-clustering-limits.html) (via search summary). The Bitcoin multi-input heuristic is described in [Harrigan and Fretter, The Unreasonable Effectiveness of Address Clustering](https://arxiv.org/pdf/1605.06369); Ethereum deposit-address-reuse is one of three heuristics in a Tornado Cash cross-chain study — [arXiv 2510.09433](https://arxiv.org/pdf/2510.09433) (both seen only as search snippets). A MadeOnSol post notes funder-based clustering is weak where wallets share a CEX withdrawal and can be defeated by chain-hopping — [MadeOnSol](https://madeonsol.com/blog/solana-linked-wallets-detection-co-buy-clustering).
- I found no published precision/recall for any Solana wallet-clustering heuristic (a search for Solana funder-clustering precision returned vendor blogs and one unrelated DBSCAN study of automated-trading detection).
- Bubblemaps' guidance on bands (cluster share: under 15% reasonably healthy, 15-30% elevated, over 30% high, over 50% extreme; bundled supply under 5% low, over 15% serious, over 30% avoid), which it says are "not hard rules", is quoted in the GodsEye note [wallet_clustering.md](/Users/srinjoydas/GodsEye/research_notes/Memecoin%20wallet%20tracking%20methods/wallet_clustering.md) (original Bubblemaps meme-coin holder guide not re-opened here; 10% bundle red flag is confirmed in [bundle vs cluster](https://blog.bubblemaps.io/whats-the-difference-between-bundle-cluster-2/)).

### Inferences
- **Method.** Build the graph on at most about 250 nodes (holders above a dust cutoff plus any intermediaries), union-find on Tier A edges to get *core* clusters, then attach Tier B members only when they have two independent B signals to the core. Avoid "one weak edge merges everything" (giant-component chaining) by (a) never clustering through a service node and (b) capping hub degree. If a component is large and dense, run Leiden inside it (connectivity guarantee) and report sub-communities; with 250 nodes this costs milliseconds, so the choice is about interpretability, not speed.
- **Supply denominator.** The bot's current top-10 uses the full mint supply as denominator, which for pump.fun means the curve still holding unsold supply dilutes every share. Two views are useful: share of *total supply* (comparable with Bubblemaps' `supply_stats`) and share of *circulating* supply (supply minus curve/pool/vault balances), since a 20% cluster of total supply on a coin where 60% sits on the curve is a 50% cluster of what is actually in wallets. State which one a threshold refers to; the bot's `CLUSTER_MAX_PCT=15` was calibrated on total supply in `holders.ts:175`.
- **Current vs peak.** For each cluster keep three numbers per wallet from a per-mint ledger: `bought` (cumulative tokens received from pools/curves), `sold` (cumulative sent to pools/curves), `held_now` (exact balance from an account snapshot or running ledger). Cluster-level: `current_share = sum(held_now)/supply`, `peak_share = max over time of cluster holding / supply` (running sum from the ledger, fine to compute from swaps alone), `exited_share = peak_share - current_share`. A cluster with `current_share` small but `exited_share` large is "already dumped" (useful for avoiding late entries: sellers are the exit liquidity), while the reverse is the live risk. Transfers between wallets are internal to a cluster and net to zero, so they do not alter cluster totals; transfers out to non-cluster wallets are leakage and should be tracked as "distributed".
- **Thresholding at the cluster level, not the wallet level.** Pair each cluster with the *evidence tier* of its edges, so the bot can block hard on a Tier A cluster of 15%+ but only warn on a Tier B-only cluster; this directly addresses the false-positive risk in section 0.

### Gaps
- Bubblemaps' internal clustering rule (and whether it uses union-find, thresholds or something richer) is unpublished; I can only say what the API exposes.
- No published precision/recall for common-funder, same-slot or token-transfer heuristics on Solana; no ground-truth dataset of operator-labelled wallet sets was found.

## 3. Data, cost, latency, incremental design with the existing stream

### Takeaway
A per-mint ledger fed by the stream the bot already has (buyers, slots, sizes, tips) removes most of the per-token RPC. What still needs RPC is (a) an exact holder snapshot and (b) each wallet's first funder plus holder-to-holder transfers; with a permanent funder cache and Helius's `getTransactionsForAddress` (oldest-first, one call) that is roughly 20-60 cache-missing lookups, in parallel, and plausibly 2-5 seconds. Credits are small on Helius; the binding constraint is requests per second on whichever provider serves the RPC.

### Cited Findings
**Primitives and their costs (Helius, as published)**
- Credit cost: `getTransaction` 1, `getSignaturesForAddress` 1, `getProgramAccounts` 10, standard calls 1; Wallet API (identity, batch identity of up to 100 addresses, funded-by) 100 per request; Parsed Events 10 per request; Enhanced Transactions legacy 100 and in maintenance mode — [Helius credits](https://www.helius.dev/docs/billing/credits). (The page does not list `getTokenLargestAccounts` or `getMultipleAccounts` individually; the fetch tool reported them as standard 1-credit calls, which is an inference from the page.)
- Plans: Free $0 / 1M credits / 10 RPC req/s / 2 DAS req/s / no gRPC; Developer $49 / 10M / 50 / 10 / gRPC devnet only; Business $499 / 100M / 200 / 50 / LaserStream yes; Professional $999 / 200M / 500 / 100 — [Helius pricing](https://www.helius.dev/pricing). LaserStream gRPC bills 2 credits per 0.1 MB, mainnet on Business or above — [credits page](https://www.helius.dev/docs/billing/credits).
- `getTransactionsForAddress` (Helius-only): `sortOrder: "asc"` returns oldest first; `limit` up to 1,000 signatures or 1,000 full transactions; filters on slot, blockTime, status, tokenTransfer, and `tokenAccounts: balanceChanged`; cost 10 credits flat for signatures, or 10 credits per 100 full transactions (10 minimum); its own example fetches a wallet's oldest transaction with `limit: 1`, full details, for the 10-credit minimum; mainnet retention unlimited — [Helius docs](https://www.helius.dev/docs/rpc/gettransactionsforaddress.md). A search summary says it needs a Developer plan or higher and 100 credits per request, which conflicts with the 10-credit figure on the method's own page; I rely on the method page — [search result summary](https://helius.dev/docs/rpc/gettransactionsforaddress).
- Helius Wallet API `funded-by` returns the funder from the wallet's first incoming SOL transfer, labelling known entities such as exchanges; paid plan only; beta ("endpoints and response formats may change"); 100 credits per call; the identity database has 32,500+ labelled accounts and programs — [Helius funded-by (search summary)](https://docs.helius.dev/docs/wallet-api/funded-by), [Wallet API overview](https://www.helius.dev/docs/wallet-api/overview.md).

### Inferences
**Cost model of today's check (Helius, assuming all calls are 1 credit):** about 60 credits per token, 60 req of the 75 req/s budget, 3-9 s (given in the brief).

**Proposed hybrid (stream ledger + short on-demand RPC):**
1. *Per-mint launch ledger from the existing stream (zero RPC).* The stream already parses every pump.fun/PumpSwap swap. Keep, in memory (and flush to a small SQLite table) for each mint younger than, say, 30-60 minutes: a list of buy/sell events (wallet, slot, tx signature, tx index within the block if added, token amount, SOL amount, Jito tip, fee payer) plus running per-wallet bought/sold. From this alone the bot can compute launch-window buyers in 0-N slots (not just 2), bundle fingerprints, same-transaction buys, and `peak_share`/`exited_share` per wallet, without the 2,000-signature limit. Memory is small relative to `LiveBook` since it is capped per young mint. Limit: it only knows swaps seen since the bot started and only on streamed programs, and token *transfers* between wallets are invisible to a DEX-only subscription.
2. *Exact current holders.* Options in increasing cost: (a) running ledger (approximate; breaks on transfers); (b) one-shot snapshot at signal time via a holder listing call (Helius DAS `getTokenAccounts` paginated or `getProgramAccounts` with a `memcmp` on mint; 10 credits on Helius for the latter) — fine for a few hundred holders, heavy for 10k+; (c) a dynamic Yellowstone `accounts` subscription with `memcmp` on the mint (offset 0 of the standard SPL token account layout, an unsourced detail) for mints being watched, giving real-time balances and transfers for free once subscribed. Note that new pump.fun coins use the Token-2022 program (`create_v2` passes `TokenzQd...` as token program in the IDL), so the owner-program filter must cover both token programs.
3. *Funders by cache + single-call oldest-first lookup.* Never recompute a wallet's first funder: it is immutable once it exists, so persist `(wallet -> funder, funding_sig, slot, lamports, amount_bucket)` forever (the bot already has `wallets.funder` for tracked wallets, `schema.ts:56`; generalise to an `address_funding` table). For misses use Helius `getTransactionsForAddress` with `sortOrder: asc, limit: 1` (10 credits, no 1,000-signature ceiling) or, on providers without it, the current two-call route. Then 1 batch-identity call (100 credits, up to 100 addresses) labels exchange funders; cache labels for days.
4. *Holder-to-holder edges.* For wallets in the map with short histories (fresh wallets, the interesting ones), fetch their history with `getTransactionsForAddress` (full, `tokenAccounts: balanceChanged`, up to 100 transactions for 10 credits) and extract SOL/token transfers whose counterparty is another map node, or an intermediary shared by two nodes (magic-node analogue). Skip wallets above a history cap (supernode analogue).
5. *Graph compute* (union-find, Tier rules, supply shares): milliseconds for 250 nodes.

**Latency budget for a fresh pump.fun token (estimates, not measured):** ledger read 0 s; holder snapshot 0.3-1 s; funder lookups for up to about 40 uncached holders in parallel, bounded by the RPS cap (40 requests at 75 req/s is roughly 0.5 s plus network round trips of 0.1-0.4 s, so about 1-2 s); label batch 0.2-0.5 s overlapping; history reads for fresh nodes 1-2 s; compute under 0.1 s. Total plausible 2-5 s, inside the existing 8 s timeout, assuming the provider's RPC latency is typical. Because a copy signal can be queued, the same work can also start at *mint creation* (the stream sees `create`/`create_v2`), so by the time a leader buys, most wallets are already cached; the signal-time step then only updates balances. That is the largest latency win and costs only credits, not wall-clock.

**Credit cost per token (Helius pricing, estimates):** ledger 0; holder snapshot 10-50; up to 40 funder lookups at 10 each = at most 400 (about 40-200 after cache hits); one identity batch 100; up to 40 history reads at 10 each = 400. So roughly 500-1,000 credits worst case, 100-400 typical; at 10M credits per month (Developer) that is on the order of 10,000-100,000 tokens a month, so the bot should map only tokens that reach a copy decision, not every token it sees. Compared with a Bubblemaps call at 25-125 credits per token (25 base, +50 for 250 holders, +25 nodes, +25 refresh) but an unknown per-credit price and unknown freshness on minutes-old coins.

**Providers.** The bot's RPC defaults to Helius when only an API key is set (`config.ts:179-183`) but the stream is documented for Shyft; if RPC is not Helius, `getTransactionsForAddress` and Wallet API are unavailable and the fallback is more calls per wallet (or Solscan's `funded_by` batch of 50 per call, documented in the earlier note).

### Gaps
- Triton and QuickNode official per-method and gRPC prices were not retrievable (404 or only third-party figures).
- The Helius `getTransactionsForAddress` plan requirement and credit cost differ between the method page (10 credits) and a search summary (100 credits, Developer+); confirm on the live page or by one test call.
- Helius `getTokenAccounts` page leaves page size and credits unstated; no measured latency for any of these calls on a minute-old pump.fun token.
- I could not confirm that the Yellowstone transaction update exposes a block-position index, nor how a dynamic account-subscription reconfiguration behaves under Shyft's limits.
- Bubblemaps' per-credit price and plans.

## 4. Pump.fun / PumpSwap specifics: separating real holders from program accounts, launch bundle, bundle attribution

### Takeaway
On pump.fun the bonding-curve token account, PumpSwap pool vaults and creator vaults are PDAs and are removed by the bot's off-curve test, but three things need explicit handling: Mayhem-mode coins (doubled supply and an agent), holder-rewards coins (the creator fee flows to holders, which can look like funding), and the fact that pump's mint uses Token-2022. Launch-bundle attribution should be a ledger of the creation transaction plus every buy in the first N slots, with Jito membership inferred from block order.

### Cited Findings
- Program ID `6EF8rrecthR5Dkzon8Nwu78hRvfCKubJ14M5uBEwF6P`; Mayhem program `MAyhSmzXzV1pTf7LsNkrNwkWKTo4ougAJ1PPg47MD4e`; PumpSwap `pAMMBay6oceH9fJKBRHGP5D4bD4sWpmSwMn52FMfXEA` (the last also appears in `agent/src/chain/programs.ts:10`) — [pump IDL](https://raw.githubusercontent.com/pump-fun/pump-public-docs/main/idl/pump.json) and the IDL's `migrate_v2` account list.
- The `BondingCurve` account has fields `virtual_token_reserves`, `real_token_reserves`, `token_total_supply`, `complete`, `creator`, `is_mayhem_mode`, `is_cashback_coin`, `quote_mint`, `creator_fee_bps`, `is_holder_reward` and more — read directly from the [IDL](https://raw.githubusercontent.com/pump-fun/pump-public-docs/main/idl/pump.json). ### Inferences
- **Real holders vs program accounts:** keep the off-curve rule (bonding-curve, pool, pool_authority, creator-vault, Mayhem vault accounts are PDA-owned, so they are all excluded — this follows from the IDL's PDA derivations; the `mayhem_token_vault` owner is not shown in the IDL I read, so assuming it is PDA-owned is an inference). Add explicit exclusions for on-curve addresses that are not holders: the Jito tips, the 24 pump fee recipients, known burn addresses, CEX/labeled wallets, and any Mayhem agent wallet if it turns out to be a keypair. Read the `BondingCurve` account (1 `getAccountInfo`) to get `creator`, `is_mayhem_mode`, `is_holder_reward`, `complete` and the exact curve balance, rather than guessing from the largest accounts.
- **Supply denominators for Mayhem coins:** `token_total_supply` may be 2B while a separate allocation belongs to the agent and is burned within 24 hours; shares computed on total mint supply will be understated relative to tokens that actually circulate. Flag Mayhem coins in the output, compute shares on both denominators, and treat the agent's holding as program-like (excluded from holders) until its location is verified by looking at one such coin on-chain.
- **Holder-rewards coins:** because pump.fun distributes fees to holders, SOL arriving in many holders' wallets from one pump-controlled address is not funding evidence. Exclude that distributor from funder and transfer edges.
- **Token-2022:** the bot's current mint read handles both programs (`holders.ts:119-121` comment), but any account-owner filter or `getProgramAccounts` holder listing must target the right token program (pump `create_v2` uses Token-2022 per the IDL).
- **Launch ledger rather than first-two-slots:** record the create transaction's slot `S0`, then all buys in `[S0, S0+N]` with `N` around 5-10 slots (about 2-4 s; slot time of about 400 ms is general Solana knowledge, not sourced here), and classify each buy as (a) same transaction as creation, (b) same slot, (c) within the window. Join the buyer set to the current-holder set so the output is `bought_in_window`, `still_held`, `sold`, `moved_out`. This also fixes Miss 3 and Miss 5 from section 0, since the stream never has the 2,000-signature problem.
- **Bundle attribution:** within a slot, treat consecutive transactions that share a fee payer or co-signer, or that contain a tip transfer to one of the 8 tip accounts in one member, as one Jito bundle (up to 5 transactions); mark the buyers as "bundled with creator" if the group contains the creation transaction. This follows the Jito rules (sequential, atomic, single slot) and seizd's fingerprint idea, but is probabilistic: a tip-bearing transaction proves a bundle exists, not that its neighbours were members, unless they share signer/fee payer or sit adjacent with matching fees.
- **Mixed-denominator bug to avoid when migrating from the current code:** `launchBundlePct` (flow, first two slots) and `clusterPct` (stock, top-10) are compared against separate thresholds; in the new design report bundle and cluster as different objects, as Bubblemaps does.

- Where Mayhem agent tokens are held (program vault vs keypair wallet) was not documented in any source I could open; Pump's own Mayhem docs were not found (the public-docs repo pages I read do not mention it).
- I did not verify the PumpSwap pool account derivation beyond the IDL's `migrate_v2` listing, nor how Pump's backend sets creators for community-takeover coins.

## 6. Accuracy checks: validating a home-built map against Bubblemaps, and build-vs-buy

### Takeaway
Validate on two axes: agreement with Bubblemaps (a reference, not ground truth) using partition metrics and a decision-level agreement at the bot's own thresholds, and, more importantly, usefulness against real outcomes (rug or large drawdown) using the audit tooling the repo already has. For the build-vs-buy choice: calling Bubblemaps is cheap and rich but its freshness on minute-old coins is undocumented, so run both in shadow mode and decide from data; extending the in-house screen is justified by the long-tail and stream-ledger advantages and the cost profile.

### Cited Findings
- The Bubblemaps map endpoint can return the holders with shares (`return_nodes`), relationships (`return_relationships`), clusters (`return_clusters`, default on), `limit` of 80/250/500, `refresh=true` to bypass the cache, `timestamp` for history, and switches `use_magic_nodes` and `use_time_nodes` (default true) — [API: map](https://docs.bubblemaps.io/data/api/tokens/map.md). Cost per call as in section 3.
- Adjusted Rand Index compares two partitions by pairs grouped together or apart in both, corrected for chance, range [-0.5, 1], symmetric and invariant to label names; NMI ranges 0-1 but is not chance-adjusted; adjusted indices are preferred for small samples or many clusters; all need a reference labelling — [scikit-learn clustering evaluation](https://scikit-learn.org/stable/modules/clustering.html#adjusted-rand-index).
- Bubblemaps' own caveats: clusters are indicators, not proof; benign clusters occur; the web app's data can be up to six hours old — [bundle vs cluster](https://blog.bubblemaps.io/whats-the-difference-between-bundle-cluster-2/), [wiki](https://wiki.bubblemaps.io/bubblemaps-v2/how-does-it-work).
- The repo already contains rug-outcome audit material (`research_notes/Rug detection for copy trading/rug_outcome_audit.ts.txt`, `internal_audit.md`) and a shadow log of every token a leader bought (`shared/src/schema.ts:367-418`, `agent/src/shadow/`), which could provide outcomes.

### Inferences
**Protocol (proposed):**
1. *Sample.* 150-300 Solana tokens stratified by age and venue: (a) fresh pump.fun curve (under 30 min), (b) just-graduated PumpSwap, (c) older established memecoins, (d) tokens from the shadow log that later rugged or crashed (positives) and ones that held (negatives). Include a few well-known Bubblemaps-flagged cases (RugProof, LIBRA/MELANIA, $AVA) as known positives.
2. *Align configurations.* Call the Bubblemaps map with `limit=250`, `return_nodes=true`, `return_clusters=true`, `use_magic_nodes` and `use_time_nodes` at default and again off (to separate the effect of intermediaries), `refresh=true` for fresh tokens. Snapshot ours at the same slot or within seconds; record Bubblemaps' `ts_update`. Remove from both the categories Bubblemaps hides (CEX, DEX, contract). Restrict comparison to the intersection of holder addresses so ranking differences (80 vs 250 vs ours) do not pollute the score. Estimated reference cost at the API's published prices: about 25 + 50 + 25 + 25 = 125 credits per token, so 200 tokens is about 25,000 credits (price per credit unknown).
3. *Partition agreement.* On the common holders, treat unclustered holders as singletons and compute ARI and AMI between the two partitions; also pairwise precision and recall of "same cluster" pairs, and a supply-weighted version (weight each pair by the product of holdings) because a large wallet matters more than dust. Report per stratum, with bootstrap intervals over tokens.
4. *Magnitude agreement.* Compare the largest-cluster share (ours vs Bubblemaps `clusters[0].share`) and `top_10_adjusted`, `bundles` supply stat: Spearman correlation, median absolute error in percentage points, and a Bland-Altman plot for bias; separate current vs peak share because Bubblemaps shows current holdings only.
5. *Decision agreement at the bot's thresholds.* Treat "Bubblemaps cluster share over X%" (X in 10, 15, 25) versus ours as binary classifiers and report confusion matrix, Cohen's kappa, and the disagreement list for manual review. This is the metric that matters for a hard block.
6. *Disagreement triage.* Label each disagreement with a cause: missing edge type (token transfer, Magic Node, Time Node), different service filter, snapshot time, different holder cutoff, or a genuine error; the distribution tells which of the Tier A/B rules to tune.
7. *Outcome check (ground truth proxy).* For tokens with known outcomes, compare ours, Bubblemaps and the existing check on "rug or fall of at least 80% within N hours" with ROC/PR curves; pick the thresholds on one half and report on the other. Agreement with Bubblemaps does not prove either is right.

**Build vs buy (judgment from the evidence above):**
- Bubblemaps API gives the richest links (Magic/Time Nodes, cross-token and cross-chain transfers) for 25-125 credits, with an official label set, but price per credit, the cache TTL on minutes-old tokens, and behaviour on pump.fun tokens are undocumented, and its response can take "up to a minute" for outliers. Practical test: a few dozen fresh pump.fun mints with `refresh=true` and measure latency and holder coverage before relying on it in the 2-10 s window.
- The in-house route wins on: seeing every streamed buy in real time (no 6-hour or cache staleness), a launch window not limited by signature counts, current/peak/exited shares, ability to cache funders across tokens for near-zero marginal cost, and no vendor dependency in the buy path. It loses on: cross-token/cross-chain links, label coverage, and tuning effort with no ground truth.
- A staged path with low regret: (1) fix the obvious false-positive and null issues in the existing check (service-funder filter, funder lookup without the 1,000-signature ceiling, bundle window from the stream); (2) add the ledger and the Tier A holder-to-holder edges for the top 50-100 holders; (3) run Bubblemaps in shadow mode on the same tokens for a few weeks; (4) decide, per component, whether to keep calling it as a second opinion (for example only when our map is borderline).

### Gaps
- I did not call the Bubblemaps API (no key, and the task forbids sign-ups), so no latency or coverage measurement exists for fresh pump.fun tokens.
- No public benchmark of Bubblemaps' own accuracy or false-positive rate was found; it is a vendor product whose cluster definition is only loosely documented.
- The thresholds in the protocol (sample size, bands) are proposals; there is no published standard for validating wallet-cluster maps against each other.
