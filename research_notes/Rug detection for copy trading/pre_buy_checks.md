## 1. Sell simulation / honeypot test: which method is practical, and what Token-2022 fee/hook extensions and real Solana anti-sell tricks do to it

### Takeaway
A Jupiter sell quote only prices the AMM; it does not exercise the token program, so it cannot see a freeze, a reverting transfer hook or a hidden transfer tax. The practical test is to read the mint's extensions statically (free, same `getAccountInfo` the bot already makes for authorities) and then run one RPC `simulateTransaction` of buy-then-sell from the bot's own wallet; a live test buy-and-sell is dominated by fees and adds nothing a simulation cannot show. Documented token-program-level sell blocking (freeze abuse) is only about 0.6% of labelled Solana rugs, so for pump.fun/PumpSwap-native coins the sell test is cheap insurance, not the main defence.

### Cited Findings
- A transfer hook is a program the token program CPIs into on every transfer; "If this fails, the initial token transfer fails", i.e. the hook can return an error and block a transfer. The sender's signer privileges are not passed to the hook (accounts become read-only). — [Solana docs: Transfer Hook](https://solana.com/docs/tokens/extensions/transfer-hook) [D]
- The mint `authority` can "Update the transfer hook program" after launch (authority table in Neodyme's Token-2022 review), so a hook that is benign at check time can be swapped. Upgradeability of the hook program itself was not covered. — [Neodyme, "SPL Token-2022: Don't shoot yourself in the foot with extensions"](https://neodyme.io/en/blog/token-2022/) [D/security research]
- Transfer fee: the transferred amount "is reduced by the configured fee"; fee updates go into a "next configuration" that "takes effect starting two epochs later"; the `transferFeeConfigAuthority` can change it; withheld fees sit on the destination token account and harvesting is permissionless. — [Solana docs: Transfer Fees](https://solana.com/docs/tokens/extensions/transfer-fees) [D]
- Neodyme on other extensions: permanent delegate can move or burn tokens in any account (a pool vault can be drained, "your amazing swap pool could suddenly be out of funds"); default-account-state lets new accounts be created frozen and the `freeze_authority` can change that default later; accounts with withheld fees cannot be closed until fees are harvested; non-transferable tokens cannot be moved at all. — [Neodyme](https://neodyme.io/en/blog/token-2022/) [D]
- Mint-level screening reads the mint account via `getAccountInfo` and parses extensions; vendor rule: permanentDelegate or transferHook returns "DANGER"; pausable, nonTransferable and default-frozen are also listed as traps. No accuracy or false-positive data is given. — [DEV Community (RugCheck AI author)](https://dev.to/mrwizardlyloaf/token-2022-traps-that-drain-ai-trading-agents-and-how-to-screen-them-33bo) [V]
- Open-source detector `onchainvanguard/solana-honeypot-detector` checks LP lock across Raydium/Orca/Meteora/PumpSwap, mint/freeze authority and Token-2022 transfer-fee/hook/permanent-delegate/pausable/non-transferable, with a stablecoin whitelist to avoid false positives; its README does not describe a sell simulation and it reports testing on only three tokens (USDC, PYUSD, BONK). — [GitHub README](https://github.com/onchainvanguard/solana-honeypot-detector) [V]
- GoPlus's Solana token-security API exposes `freezable`, `mintable`, `transfer_fee` (+`_upgradable`), `transfer_hook` (+`_upgradable`), `default_account_state` (+`_upgradable`), `none_transferable`, `balance_mutable_authority`, `closable`, `metadata_mutable`, `creators`, `holders`, `lp_holders`, `trusted_token`; it has no dedicated honeypot or sell-ability field. The `*_upgradable` flags are a ready-made "can this change after my check" signal. — [GoPlus docs](https://docs.gopluslabs.io/reference/solanatokensecurityusingget) [V]
- Vendor description of honeypot variants (EVM-flavoured, Solana mechanics listed as frozen accounts, transfer hooks, very high transfer fees): sells blocked above a dollar threshold, sells allowed only to dev-controlled wallets, logic added later via upgrade; the same vendor says it simulates a Jupiter swap in both directions and calls that the most reliable pre-trade check, and says honeypots are rarer on Solana than EVM with no independent data. — [Sharpe.ai honeypot guide](https://www.sharpe.ai/rug-check/risk/honeypot) (snippet only; page returned HTTP 429 on fetch) [V]
- Empirical mix of Solana rug mechanisms (76,469 labelled rugs, H1 2025, Orca/Raydium/Meteora): pump-and-dump 79.0% (60,402), liquidity withdrawal 20.4% (15,606), freeze-authority abuse 0.6% (461). Freeze-abuse detection rule: creator still holds freeze authority and at least one FreezeAccount hit a user account. Freeze-abuse tokens live longer: median ~11.6 h, P25 ~47 min, P75 ~4.7 days (vs ~32-35 min median for pump-and-dump / all rugs). — [Chen et al., SolRugDetector, arXiv 2603.24625](https://arxiv.org/abs/2603.24625) (numbers from the full-text fetch) [P]
- `simulateTransaction`: `sigVerify` defaults to false and the transaction "is not required to be signed unless `sigVerify` is `true`"; it conflicts with `replaceRecentBlockhash`; the `accounts` option returns post-simulation account state (e.g. token balances); response includes `err`, `logs`, `unitsConsumed`, `fee`, `innerInstructions`. The page does not state whether the fee payer must be funded. — [Solana RPC docs](https://solana.com/docs/rpc/http/simulatetransaction) [D]
- Jupiter Swap V2: `GET /order` without `taker` returns a quote with `transaction: null`; with `taker` it assembles a transaction; `GET /build` returns raw Metis swap instructions you assemble yourself; slippage on `/order` comes from a Real-Time Slippage Estimator using "live failure rates"; routing engines are "self-learning and sideline underperforming sources". The pages read describe no simulation, sell-ability check or warnings field. Keyless 0.5 req/s, free key 1 req/s, Developer 10, Launch 50, Pro 150. — [Jupiter Swap V2 overview](https://developers.jup.ag/docs/swap.md), [Routing](https://developers.jup.ag/docs/swap/routing) [D]
- Jupiter Shield (`/ultra/v1/shield`, marked "no longer actively maintained", superseded by Swap V2) returns per-mint warnings; documented types: `HAS_FREEZE_AUTHORITY` (warning), `HAS_MINT_AUTHORITY`, `NOT_VERIFIED`, `LOW_ORGANIC_ACTIVITY`, `NEW_LISTING` (info). No honeypot or Token-2022-extension warning is documented. — [Jupiter: Get Shield](https://developers.jup.ag/docs/ultra/get-shield.md) [D]
- Jupiter's Token-2022 support post says transfer fees were supported "across the entire stack"; it does not address hooks. A third-party table claims Jupiter has only "limited" transfer-hook support and no permanent-delegate/confidential-transfer support, unsourced. — [Jupiter blog](https://docs.jup.ag/blog/jup-token2022-support) (snippet only); [skills.cat table](https://skills.cat/skills/sanctifiedops/solana-skills/token-2022-extensions) (snippet only, unverified) [V]
- pump.fun `create_v2` creates a Token-2022 mint (decimals 6, a metadata-pointer extension) with `mint_authority` initialised to a Pump PDA; the page does not say whether that authority is later revoked and does not mention freeze authority. Helius docs say launchpads such as pump.fun and LetsBonk set mint authority to null (snippet). — [pump-public-docs COIN_CREATION](https://raw.githubusercontent.com/pump-fun/pump-public-docs/main/docs/instructions/COIN_CREATION.md) [D]; [Helius Orb: explore authorities](https://docs.helius.dev/docs/orb/explore-authorities) (snippet only) [V]
- Fees that a test round trip would pay: bonding curve protocol fee 100 bps per trade (buy and sell); PumpSwap LP fee 20 bps + protocol fee 5 bps per trade (creator fee on top, schedule not stated in the docs read). — [PUMP_PROGRAM_README](https://raw.githubusercontent.com/pump-fun/pump-public-docs/main/docs/PUMP_PROGRAM_README.md), [PUMP_SWAP_README](https://raw.githubusercontent.com/pump-fun/pump-public-docs/main/docs/PUMP_SWAP_README.md) [D]

### Inferences
- Ranking of methods for this bot (my reasoning):
  1. **Static extension read** (free): parse the same mint account the screen already fetches. Block on: any `transferHook` with a non-null program (unless on an allow-list), `permanentDelegate`, `pausable` (paused or not), `nonTransferable`, `defaultAccountState=frozen`, `confidentialTransfer`, and transfer fee where either `olderTransferFee` or `newerTransferFee` (read both; the two-epoch lag means a pending hike is visible before it applies) exceeds a small cap, plus `*_authority` still set (GoPlus `*_upgradable` logic). The bot already covers permanent delegate / pausable / default-frozen; the gaps are hook program, transfer fee (current and pending), non-transferable, confidential transfer and update authorities.
  2. **Jupiter sell quote**: useful only as a liquidity/route-exists check and for price impact; it cannot detect token-program-level blocks, because a quote is computed from pool state (inference: Jupiter's pages read document no simulation step). Keep it as a cheap secondary gate, mindful of the 1 req/s free-key limit.
  3. **One `simulateTransaction` of [buy, sell-of-the-received-amount] from the bot's own wallet** (`sigVerify:false`, `accounts` = own token account). It exercises the token program and hook for a non-allow-listed wallet, shows the real round-trip loss (captures transfer tax and fee), and costs one RPC call. Build instructions with Jupiter `/build` or the pump SDK. Sell-leg input has to be the quote's minimum-out (the simulated buy output is not known in advance), so run the sell with a conservative amount.
  4. **Do not use a live test buy/sell**: it costs at least 2% round trip on a curve token (1% each way, per docs) plus tips and base fees, on 0.05-0.15 SOL tickets, adds one-to-two blocks of delay, and tells nothing about later changes. Its only unique information (that a real transaction lands) is also what the bot's own first buy proves.
  5. **Post-buy re-check by account subscription**: the freeze/hook/fee risks are mutable after the check (authority can update the hook; freeze abuse median ~11.6 h). Subscribe to the mint account of every open position over Yellowstone and re-run the static read on each update; that is near-zero RPC cost.
- Known bypasses/false negatives of the simulate-and-read approach: allow-list logic (sell passes for whitelisted wallets; our wallet is not whitelisted, so simulate from our wallet, not from a leader's, otherwise an insider-whitelisted leader gives a false pass), threshold- or time-conditioned blocks, upgrades after the check, same-slot buy-then-sell behaving differently from a later sell (cooldown logic gives false positives), and tx size/compute limits when two routed swaps are packed in one transaction (may force a direct-pump instruction path rather than Jupiter). All are reasoning from the mechanisms above, not measured.
- False positives to expect: **Token-2022 itself is not a red flag for new pump.fun coins** (`create_v2` mints are Token-2022 with a benign metadata pointer), so rules must key on specific dangerous extensions, not on the token program. Also check whether `mint_authority` of fresh `create_v2` mints is revoked; if it stays a Pump PDA, an existing "mint authority present = block" rule would reject every such coin. This is a one-call test the bot owner can do on a handful of live `create_v2` mints.
- For pump-native coins the dominant failure is price collapse (79% pump-and-dump in Chen's pools; pump LP is burned at migration, see Section 2), not blocked sells. The simulation therefore protects the minority tail (non-pump launchpads, Raydium/Meteora/Orca pools) and any copied leader trade routed outside pump.

### Gaps
- No quantified catch rate or false-positive rate for any Solana sell-simulation tool; the Sharpe.ai method is vendor description only.
- No documented, dated case study of a Token-2022 transfer-hook honeypot on a pump-origin coin in 2025-2026; only mechanism descriptions and scanner marketing were found.
- Whether Jupiter currently routes tokens with a transfer hook (and with which accounts) is not documented in the pages read.
- Latency and RPC-credit cost of `simulateTransaction` for a two-swap transaction are not published; must be measured on the bot's own RPC.
- Whether the fee payer must hold lamports for a `sigVerify:false` simulation is not stated in the RPC docs read.
- Final on-chain authority state of `create_v2` mints (mint/freeze) not verified (needs a live account read, which is outside the public-GET constraint).

## 2. Liquidity and size gates: relating pool depth to ticket size and exit impact; pump.fun curve vs PumpSwap reading

### Takeaway
With 0.05-0.15 SOL tickets, the bot's own exit impact is negligible on any pool above roughly 5-10 SOL of quote reserve (my arithmetic), so a minimum-liquidity gate sized on "our impact" is cheap to satisfy. The liquidity that matters is exit capacity after holders dump: price falls by `1 - 1/(1+T/B)^2` when `T` tokens hit a constant-product pool holding `B` base tokens, so concentrated supply vs pool base reserve, not ticket size, sets the real exit risk. All needed reserves are in the pump events or two account reads.

### Cited Findings
- BondingCurve account (field order): `virtual_token_reserves`, `virtual_quote_reserves` (was `virtual_sol_reserves`), `real_token_reserves`, `real_quote_reserves`, `token_total_supply`, `complete`, then trailing `creator`, `is_mayhem_mode`, `is_cashback_coin`, `quote_mint`, `creator_fee_bps`, `can_edit_creator_fee`, `is_holder_reward`, `creator_fee`, `protocol_fees`, `depth`, `initial_virtual_quote_reserves`, `post_complete_base_out`, `post_complete_quote_in`. Older accounts are shorter; missing trailing fields read as zero/false/default. — [pump.json IDL, parsed by me](https://github.com/pump-fun/pump-public-docs/blob/main/idl/pump.json); field notes in [PUMP_PROGRAM_README](https://raw.githubusercontent.com/pump-fun/pump-public-docs/main/docs/PUMP_PROGRAM_README.md) [D]
- Curve is "based on Uniswap V2" with virtual reserves; initial values 1,073,000,000,000,000 virtual tokens, 30,000,000,000 lamports virtual SOL, 793,100,000,000,000 real tokens, 1,000,000,000,000,000 total supply (6 decimals). `complete` is set at the end of a buy when `real_token_reserves == 0`; `migrate` is permissionless and the resulting LP tokens are burned; fee 100 bps per trade; migration fee 15,000,001 lamports. — [PUMP_PROGRAM_README](https://raw.githubusercontent.com/pump-fun/pump-public-docs/main/docs/PUMP_PROGRAM_README.md) [D]
- Graduation point: about 115 virtual SOL, i.e. about 85 real SOL (market cap cited ~$69K in Sept 2025); only 4,338 of 655,770 tokens (0.63%) graduated in Sept 2025; median time to graduation ~4.4 min and ~457 swaps. — [Predicting the success of new crypto-tokens, arXiv 2602.14860](https://arxiv.org/html/2602.14860v1) [P]
- Every `TradeEvent` carries post-trade `virtual_sol_reserves`, `virtual_token_reserves`, `real_sol_reserves`, `real_token_reserves`, plus `creator`, `mayhem_mode`, `ix_name`, `fee`, `creator_fee`, `quote_mint`, `virtual_quote_reserves`, `real_quote_reserves` (parsed from the IDL). `CreateEvent` carries `creator`, `user`, `token_program`, `is_mayhem_mode`, `is_holder_reward`, `quote_mint`, initial reserves. — [pump.json IDL](https://github.com/pump-fun/pump-public-docs/blob/main/idl/pump.json) [D]
- PumpSwap `Pool` account: `pool_base_token_account`, `pool_quote_token_account` (vault ATAs), `lp_supply`, `coin_creator`, `is_mayhem_mode`, `virtual_quote_reserves` (i128, can be negative since 30 Sept; treat as signed), `creator_fee_bps`, `is_holder_reward`. Quote against effective reserves: `effective_quote = quote_vault.amount + Pool.virtual_quote_reserves`; base reserve is the raw base vault balance. Canonical migrated pools use index 0; pool PDA seeds `["pool", index, creator, baseMint, quoteMint]`. Constant-product AMM; LP fee 20 bps, protocol fee 5 bps. — [PUMP_SWAP_README](https://raw.githubusercontent.com/pump-fun/pump-public-docs/main/docs/PUMP_SWAP_README.md), [changelog](https://github.com/pump-fun/pump-public-docs) [D]
- PumpSwap `BuyEvent`/`SellEvent` include `pool_base_token_reserves`, `pool_quote_token_reserves`, `virtual_quote_reserves`, `base_supply`, `coin_creator`, `pool`, `user` (parsed from the IDL), so effective pool reserves can be rebuilt from the event stream. The changelog states this explicitly ("indexers can rebuild effective reserves from the event stream"). — [pump_amm.json IDL](https://github.com/pump-fun/pump-public-docs/blob/main/idl/pump_amm.json); [changelog](https://github.com/pump-fun/pump-public-docs) [D]
- Synthetic migration: the buy that empties the curve can fill the remainder at the pool's price; after it, "no buys or sells are possible until migration". — [pump-public-docs changelog](https://github.com/pump-fun/pump-public-docs) [D]
- `create_v2` can pair a new coin with an existing pump coin as quote (depth up to 2) and USDC is supported as a quote asset; `quote_mint` is `Pubkey::default()` for SOL-paired coins. — [changelog](https://github.com/pump-fun/pump-public-docs), [PUMP_PROGRAM_README](https://raw.githubusercontent.com/pump-fun/pump-public-docs/main/docs/PUMP_PROGRAM_README.md) [D]
- Published rule of thumb: a Liquidity-to-Market-Cap ratio of at least 10-15% is cited as a memecoin heuristic; vendor guide, no validation. — [DEXTools liquidity guide](https://www.dextools.io/news/what-is-liquidity-in-crypto-a-memecoin-trading-guide) (snippet only) [V]
- Thin-liquidity manipulation: a "liquidity-pool price inflation" attack with median buy volume $54 produced >500% gains in half of events (cross-chain, Solana-heavy). — [Mongardini et al., arXiv 2507.01963](https://arxiv.org/html/2507.01963v1) [P]
- Pre-migration filter used by MemeTrans: dropped launches whose sale lasted <1 min or had <100 holders, which were about 95% high-risk. — [MemeTrans, arXiv 2602.13480](https://arxiv.org/html/2602.13480v1) [P]
- I found no published, validated formula or rule for "minimum pool liquidity as a multiple of trade size" for Solana memecoins; only the vendor ratio above.

### Inferences
- My arithmetic (constant product, ignoring fees): selling a position of value `S` into quote reserve `Q` gives impact `f/(1+f)`, `f=S/Q`. Own-exit impact for S = 0.05 / 0.15 / 1 SOL: Q=10 SOL: 0.50% / 1.48% / 9.1%; Q=20: 0.25% / 0.74% / 4.8%; Q=40: 0.12% / 0.37% / 2.4%; Q=85 (post-migration): 0.06% / 0.18% / 1.2%. To keep own impact under 2% for a 0.15 SOL position you need Q >= ~7.4 SOL; under 1%, Q >= ~14.9 SOL; under 5%, Q >= ~2.9 SOL. On the curve itself, a 0.1 SOL buy has 0.33% impact at the start (30 virtual SOL) falling to ~0.09% at 80 real SOL; a flat-price round trip on the curve returns about 98.0% of principal after 1%+1% fees (assumes the fee is taken before the curve, sources differ on ordering).
- Therefore: set the liquidity gate as `quote_reserve >= max(7-15 SOL, 50-100 x ticket)` as a floor against manipulability and fee/impact drag, but treat it as a weak gate; it does not protect against holder dumps. (Thresholds are my proposal, not sourced.)
- The binding constraint is stressed exit: if a block of tokens `T` (bundled supply, insider cluster, top-N non-pool holders) sells into a constant-product pool with base reserve `B`, spot price falls by `1 - 1/(1+T/B)^2` and quote reserve shrinks by `1/(1+T/B)`. Table: T/B = 0.1 / 0.25 / 0.5 / 1 / 2 -> price drop 17% / 36% / 56% / 75% / 89%. At migration the pool's base reserve is about 206.9M tokens (1B supply minus 793.1M real curve tokens; my derivation from the Global constants) and ~85 SOL, so a holder block equal to 5% / 10% / 20% of supply dumping is a ~35% / ~55% / ~74% price drop. This reframes the existing bundle-share and top-10 checks as pool-relative: compute `T/B` using bundle + insider-cluster + top-holder tokens and reject above a threshold (for example T/B > 0.5). The numbers show why the 35% stop-loss is often not enough to rely on once insiders sell first.
- Exit capacity check to run per candidate (cheap): (a) read reserves from the latest `TradeEvent` / PumpSwap `BuyEvent`/`SellEvent` seen in the stream for that mint, no RPC; (b) if the stream has no recent event (older token, thin tape, 93.5% of entries per `internal_audit.md` had a silent tape within 60 min), do one `getMultipleAccounts` for bonding curve (or pool + two vaults); (c) compute own impact and stressed exit; (d) also reject `complete == true` with unmigrated curve (buy/sell impossible until migration, see Section 4).
- 300 bps slippage vs impact: our own impact is 0.1-0.4% on pools above ~20 SOL, so most of the 300 bps is headroom for price drift and for sandwichers; Jupiter's `/order` RTSE can set slippage from live failure data instead of a fixed 300 bps (inference: RTSE description only). Not tested.
- When `quote_mint` is not SOL/WSOL (USDC- or pump-coin-quoted), SOL-denominated gates, price and size maths are wrong; skip those coins or normalise.

### Gaps
- No empirical study relating pool-liquidity multiple to realised exit loss for small Solana memecoin positions.
- Creator-fee value on PumpSwap/curve ("standard schedule") is not stated in the docs read (`Global.creator_fee_basis_points` is 0 on the curve per PUMP_CREATOR_FEE_README), so total PumpSwap round-trip cost beyond 25 bps per leg is unverified.
- Exact tokens-out formula and fee ordering for the curve are not in the docs (they point to the SDK); my curve numbers use plain `x*y=k` on virtual reserves.
- Whether the bot's current stream already retains pump `TradeEvent` / PumpSwap event fields (vs only derived `price_sol`, `venue`, `quote`, `slot`, `jito_tip`, `token_age_sec` columns seen in `wallet_swaps`) was not checked beyond the schema.

## 3. Token-age and creator-history gates: serial deployers, creator holdings/sells, dev-wallet funding

### Takeaway
Creator history is the most-cited pre-buy heuristic but the evidence is thin: the only quantitative numbers are vendor data (MadeOnSol) and a Substack, and the one academic test (one month of pump.fun) reports mixed, non-metric results on creator conditioning. The strongest published fact is structural: rug operations are repeat deployers and syndicates (78 large groups in Chen et al.), and a prior-launch table can be built cheaply from the `CreateEvent` stream. Treat creator history as a veto for "known farm" cases, not as a quality score.

### Cited Findings
- MadeOnSol deployer dataset (vendor, snapshot article updated 15 Sept 2026): 561,645 deployer wallets, 1,353,664 deployments, 25,560 bonded (1.89% sitewide), 19,477 wallets (3.5%) bonded at least once; "repeat rugger" defined by the vendor as >=10 lifetime deploys and zero bonds: 11,643 wallets averaging 50.2 launches (top wallet 4,674 launches, 0 bonds); "Cold" tier 21,718 wallets, avg 44 launches, 0.5% bond rate; "Elite" tier 38 wallets, 73.4% bond rate; no post-bond survival or 2x rates published. Zero bonds is not proof of malice, and time-to-bond buckets do not sum to the bonded-wallet total. — [MadeOnSol deployer analysis](https://madeonsol.com/blog/pump-fun-deployer-analysis-2026-561k-wallets) [V]
- Same vendor's scoring heuristic: 0-5 prior launches with >=30% graduation = pass; 5-20 mixed = caution; 20+ launches with <10% graduation = red flag; first-time deployers are not automatically bad and wallet funding source matters. — [MadeOnSol, score a token in 60 seconds](https://madeonsol.com/blog/how-to-score-pumpfun-token-60-seconds) (snippet only) [V]
- Academic test, Sept 2025, 655,770 tokens / 243,123 creators: "top creators" defined as >=50 tokens with graduation ratio >0.001; for the top 10 creators conditional success exceeds breakeven at advanced vSol levels (small sample), yet the conclusion states creator conditioning does not improve prediction over the baseline (internal inconsistency in the paper); no AUC or accuracy reported; trade speed ("liquidity velocity") judged most informative; 92.22% of 184,282 tokens with >=30 swaps had at least one dump (4-sigma rule), only 2.55% of those graduated; the study does not analyse creator holdings or metadata. — [arXiv 2602.14860](https://arxiv.org/html/2602.14860v1) [P]
- Rug operations are organised: 78 large groups (16 single repeat deployers, 62 multi-party syndicates), median 36 members / 48.5 tokens / 25 creators / 12 profit addresses; "Star" and "Cluster" topologies; the authors recommend warning on matches to known high-risk creator-deployer-profit graphs and on newly created tokens with retained authorities or abnormal holder dynamics. — [SolRugDetector, arXiv 2603.24625](https://arxiv.org/abs/2603.24625) [P]
- Substack (Apr 2025, secondary data): top 1% of deployers account for nearly 30% of launches; about 15% of deployers control clusters of 50+ wallets; launch cost ~0.02 SOL; the article states it found no public wallet addresses or funding-source data for serial deployers and its 98%/98.5% rug figures are inconsistent. — [Killy, "Serial Token Deployers on Solana"](https://killy7.substack.com/p/serial-token-deployers-on-solana) [V]
- A Notion write-up describes one deployer cluster of 174 tokens with median 17 minutes from launch to rug; anecdotal and unverified. — [The Rug Factory Next Door](https://unruly-mandolin-c0f.notion.site/The-Rug-Factory-Next-Door-1e0fb2db7d0c80f29dd4c512f9fae08b) (snippet only) [V]
- MemeTrans: 98.7% of mint events co-occur with a developer buy at the lowest curve tier; one of its 122 features is `dev_hold_pct`; the paper reports no per-feature importance for it (only group level: market activity and bundle statistics highest). — [MemeTrans, arXiv 2602.13480](https://arxiv.org/html/2602.13480v1) [P]
- Creator identity on-chain: `CreateEvent` has both `user` (signer) and `creator` (receives creator fees; may be supplied separately or set from Metaplex metadata); every `TradeEvent` repeats `creator`, so "creator sold" is `TradeEvent.user == creator && !is_buy`; `BondingCurve.creator` and PumpSwap `Pool.coin_creator` carry it too (zero address on older pools). — [pump.json IDL](https://github.com/pump-fun/pump-public-docs/blob/main/idl/pump.json), [PUMP_CREATOR_FEE_README](https://raw.githubusercontent.com/pump-fun/pump-public-docs/main/docs/PUMP_CREATOR_FEE_README.md), [PUMP_SWAP_README](https://raw.githubusercontent.com/pump-fun/pump-public-docs/main/docs/PUMP_SWAP_README.md) [D]
- Rug time scale for age gates: pump-and-dump median ~32 min (P25 ~12 min, P75 ~1.2 h); liquidity withdrawal median ~55 min; all rugs median ~35 min. Cross-token wallet-funding evidence on multi-hop deployer funding (5-7 hops) is already in the earlier notes (Pine Analytics). — [SolRugDetector](https://arxiv.org/abs/2603.24625) [P]
- Creator-fee mechanics (relevant if "creator claims fees" were used as a behavioural signal): fees accumulate in a creator vault PDA, collected by `collectCreatorFee` signed by the creator; `Global.creator_fee_basis_points` is 0 on the curve per the docs read; fee-sharing config can be created by creator or admin and the shareholder list can be replaced only once (`admin_revoked = true` after update). — [PUMP_CREATOR_FEE_README](https://raw.githubusercontent.com/pump-fun/pump-public-docs/main/docs/PUMP_CREATOR_FEE_README.md), [CREATOR_FEE_SHARING](https://raw.githubusercontent.com/pump-fun/pump-public-docs/main/docs/instructions/CREATOR_FEE_SHARING.md) [D]
- Two graduation-rate baselines conflict: 0.63% of tokens in Sept 2025 (academic, one month) vs 1.89% of launches (vendor, undated multi-month snapshot) vs 1.4% (Substack, Apr 2025). Definitions (per token vs per deployer wallet, window) differ. — [arXiv 2602.14860](https://arxiv.org/html/2602.14860v1); [MadeOnSol](https://madeonsol.com/blog/pump-fun-deployer-analysis-2026-561k-wallets); [Killy](https://killy7.substack.com/p/serial-token-deployers-on-solana)

### Inferences
- Implementation, cheapest to dearest (my design):
  1. **Creator = leader / creator sold / creator holdings**: zero extra RPC if the bot decodes pump `TradeEvent`/`CreateEvent` (fields above). Keep a per-mint row: `creator`, creator's running token balance (from creator's own buys/sells in events), `creator_sold` flag. Block or size down if creator has sold a large fraction already (threshold untested), or creator holding is large relative to pool base reserve (use the `T/B` stress test from Section 2).
  2. **Prior-launch table by creator and by signer**: requires either subscribing to pump program transactions (heavy bandwidth: ~17-18K launches/day per [The Block](https://www.theblock.co/post/379285/pump-funs-new-mayhem-mode-fails-boost-token-launches-revenue), Nov 2025 data, plus all trades) or a per-candidate lookup: Helius `getTransactionsForAddress` on the creator (previous creates) plus one `getMultipleAccounts` on the bonding curves of those mints (`complete`, real reserves). Both `user` and `creator` must be keyed because they can differ.
  3. **Creator funding source and cluster**: one call for the creator's first inbound SOL transfer (oldest-first, limit 1), then compare with the existing funder-cluster logic; one-hop checks undercount (Pine: 5-7 hops), so use cluster membership rather than direct equality.
- What the evidence supports as a gate: veto when the creator wallet or its funder cluster has many prior launches with no graduation and short lifetimes (MadeOnSol's "cold"/repeat pattern, Chen's syndicate topology). It does not support using a high prior-bond rate as a positive quality signal: a bond can be funded by the deployer's own wallets (Pine Analytics, already in earlier notes) and the academic test found no predictive gain from creator conditioning. I would use creator history only as a one-way veto or size reducer.
- Token-age gate: given rug medians of ~30-55 min and 4.4 min median to graduation, "older than a few minutes" mostly filters out creation-block sniping, which is already partly handled by the 60 s lateness limit and the bundle-share check. MemeTrans's <1 min / <100 holders cut (about 95% high-risk) is the only published age/holder threshold; its use as a copy gate would remove most copies given that the bot's leaders buy mostly <5 min-old tokens (340 of 478 priced entries, `internal_audit.md`), so test it in shadow mode before enforcing.

### Gaps
- No independent, peer-reviewed measurement of outcomes for tokens launched by wallets that rugged before; all creator-history rates are vendor numbers or one inconsistent academic section.
- No source on how often "serial rug" creators change wallet after one rug (wallet-rotation rate), which bounds the value of a creator-address blacklist.
- No data on creator-holding thresholds (what percent of supply held or sold by the creator predicts a collapse).
- Dev-wallet funding-source statistics for pump.fun creators: none found beyond Pine's deployer-funded sniper study.
- MadeOnSol live deployer API endpoints and pricing not verified from primary docs.

## 4. Pump.fun-specific checks: curve completion/migration, creator-fee sharing, mayhem and other modes, metadata/social, copycats

### Takeaway
Several pump-specific states change whether a buy or sell can execute at all or what the holder table means: a completed-but-unmigrated curve cannot trade, mayhem-mode coins have an extra agent-held supply and 24-hour synthetic activity, quote-paired coins are not SOL-denominated, and holder-reward coins redirect creator fees. All are flags readable from `CreateEvent` / `TradeEvent` / account data with no extra RPC. Metadata/social and copycat checks have only heuristic, unvalidated support.

### Cited Findings
- Completion and migration: `complete` flips when `real_token_reserves == 0`; `migrate` is permissionless, idempotent and burns the resulting LP tokens; after the synthetic-migration buy no buys or sells are possible until migration. Events: `CompleteEvent` (user, mint, bonding_curve, timestamp, quote_mint) and `CompletePumpAmmMigrationEvent` (includes `pool`, `mint_amount`, `sol_amount`). — [PUMP_PROGRAM_README](https://raw.githubusercontent.com/pump-fun/pump-public-docs/main/docs/PUMP_PROGRAM_README.md), [changelog](https://github.com/pump-fun/pump-public-docs), [pump.json IDL](https://github.com/pump-fun/pump-public-docs/blob/main/idl/pump.json) [D]
- Post-migration risk: 84.13% of migrated pump tokens in MemeTrans were labelled high-risk (minimum price within 20 min <0.3x the migration price, or manipulation score >=0.7). — [arXiv 2602.13480](https://arxiv.org/html/2602.13480v1) [P]
- Mayhem mode (opt-in at creation, launched Nov 2025): an autonomous agent can trade the coin in its first 24 hours, caps on trade size and frequency, pays no protocol fees; 1 billion extra tokens are minted for it (Chainstack says coins launch with 2 billion tokens), unused agent tokens burned after 24 h; first-week launch counts barely changed (about 17,300 to 17,800 per day); commentary that the agent's activity can resemble wash-like volume. On-chain flags: `BondingCurve.is_mayhem_mode`, `Pool.is_mayhem_mode`, `CreateEvent.is_mayhem_mode`, `TradeEvent.mayhem_mode`; the IDL also has `UpdateMayhemVirtualParamsEvent`. Mayhem coins use a Token-2022 bonding-curve token account. — [The Block](https://www.theblock.co/post/379285/pump-funs-new-mayhem-mode-fails-boost-token-launches-revenue); [Chainstack (vendor)](https://chainstack.com/trading-bot-update-full-mayhem-mode-support-for-pump-fun/); [pump.json IDL](https://github.com/pump-fun/pump-public-docs/blob/main/idl/pump.json) [N/V/D]
- Other modes in the program: holder-reward coins (`is_holder_reward`: creator fee goes to holders instead of a creator wallet), cashback coins (deprecated; `create_v2` rejects `is_cashback_enabled=true`, existing cashback coins still trade), custom quote mints (pump-coin quote up to depth 2, USDC), mayhem. — [changelog](https://github.com/pump-fun/pump-public-docs) [D]
- Creator-fee sharing: `sharing_config` is mandatory on buys and sells; shareholder list replaceable once. No trader-facing risk is described in the docs. — [CREATOR_FEE_SHARING](https://raw.githubusercontent.com/pump-fun/pump-public-docs/main/docs/instructions/CREATOR_FEE_SHARING.md) [D]
- Legacy-instruction trap for decoders: bots that only watch legacy `create` miss `create_v2` launches (Token-2022); v3/v2 trade instructions use fixed 17-account layouts while legacy trade instructions still work; a community report says `sell` swaps the order of `creator_vault` and `token_program` relative to `buy`. — [Chainstack](https://chainstack.com/trading-bot-update-full-mayhem-mode-support-for-pump-fun/) [V]; [changelog](https://github.com/pump-fun/pump-public-docs) [D]; [pumpfun-mechanics skill page](https://skillselion.com/skills/agiprolabs/claude-trading-skills/pumpfun-mechanics) (snippet only) [V]
- Metadata/social: in the SolRugDetector sample only 19.0% of flagged rug tokens list an X account and 14.3% a website (no baseline given for non-rug tokens, so no lift can be computed). Name max 32 chars, symbol 13, URI 200 chars on-chain. The authors recommend flagging look-alike names and name-symbol mismatches against verified assets. — [arXiv 2603.24625](https://arxiv.org/abs/2603.24625) [P]; [COIN_CREATION](https://raw.githubusercontent.com/pump-fun/pump-public-docs/main/docs/instructions/COIN_CREATION.md) [D]
- Copycats: pump.fun allows duplicate tickers (name and symbol are not unique); on 20 Jan 2025 Cointelegraph/Birdeye data found 61 new Solana memecoins presenting as official TRUMP/MELANIA among thousands launched, and six had liquidity drained within 24 h. Vendor signals: metadata matching a known project, deployed after the original, mint not on the canonical list, socials that predate launch but do not reference the mint. No validated copycat detector or accuracy figure was found. — [Cointelegraph](https://cointelegraph.com/news/fake-trump-melania-tokens-record-inflows) (snippet only); [Sharpe.ai copycat guide](https://www.sharpe.ai/rug-check/risk/copycat-token) (snippet only) [N/V]

### Inferences
- Concrete rules (my proposals):
  - Skip if `complete == true` and no `CompletePumpAmmMigrationEvent`/pool seen yet (cannot trade); for copied leader buys in the first minutes after migration, treat as the highest-risk window (84% high-risk label) and apply the stressed-exit check.
  - For `mayhem_mode == true`: exclude the agent's token vault from top-10 / holder-concentration calculations (otherwise an extra 1B-token supply held by the agent inflates concentration and trips the screen, a likely false positive that I have not tested), expect 24 h of non-organic two-sided volume, treat early volume/holder counts as less informative, and note the zero protocol fee on agent trades when estimating organic volume.
  - Parse `quote_mint`; skip or normalise any non-SOL quote.
  - Always decode `create_v2` / v3 / v2 instruction variants; a screen run on a decoder that misses them silently never fires.
  - Copycat check is local and RPC-free: keep a rolling map of normalised symbol and name to the highest-volume mint seen; flag a new mint that reuses a symbol/name of an older mint with materially more volume. Expect many false positives (duplicate tickers are common among legitimate memes) so use it as size-down, not veto. Metadata/social checks require fetching the URI (IPFS/HTTP, latency not measured), so make it asynchronous or skip it for sub-minute copies.
  - Holder-reward and fee-sharing flags: no evidence they predict loss; log, do not gate.

### Gaps
- Exact mayhem-mode supply split and the agent vault address/behaviour are not in the program docs read (only the secondary sources above); no outcome study of mayhem coins (rug rate, copyability).
- No peer-reviewed or on-chain-audit evidence on holder-reward, cashback or fee-sharing as risk predictors.
- No baseline for social-link presence among non-rug pump tokens, so the 19%/14% figures cannot be turned into a gate.
- No validated copycat/impersonation detector for Solana; accuracy unknown.
- pump.fun's own docs do not state the market-cap-based migration threshold; the ~85 real SOL figure comes from an academic paper.

## 5. Leader-side context as a per-token risk signal (not a reason to drop the wallet)

### Takeaway
Three leader-vs-token relations are cheap to compute and are risk signals for that specific token: the leader bought in the creation block / same bundle as the create, the leader is the creator, and the leader's SOL traces to the creator's cluster. Published support is for the mechanism (deployer-funded sniping, bundle bots, creator-linked clusters), not for a copy-specific effect size, so apply them as per-token size-down or skip rules measured in shadow mode, consistent with the decision to keep copying insider-pattern wallets.

### Cited Findings
- (Already established in earlier notes, not repeated: deployer-funded same-block snipes, >55% exit within 1 minute; bundle bots in about a quarter of projects; K=5-block sniper window.) See [Pine Analytics](https://pineanalytics.substack.com/p/exit-liquidity-machines) and [arXiv 2601.08641](https://arxiv.org/html/2601.08641).
- Creator-linked address definition in rug detection: "a creator-related address (mint authority or initial pool deployer)" removes liquidity, used as the liquidity-withdrawal rule; syndicates form Star/Cluster funding topologies. — [SolRugDetector](https://arxiv.org/abs/2603.24625) [P]
- Wash/volume-bot evidence of single-funder structure: 30 of 30 flagged wallets traced to one funder seeding 200+ bots with 0.5 SOL in under a minute (April 2026 case). — [Bitquery](https://bitquery.io/blog/solana-volume-numbers-are-a-lie) [V]
- Fields available per leader trade for these tests: `TradeEvent.creator` and `.user` (leader == creator test); `CreateEvent.timestamp` and the create transaction's slot (creation-block test); pump `ix_name`; Jito tip account transfer in the leader's transaction (the bot's `wallet_swaps` already stores `slot`, `jito_tip`, `token_age_sec`, `venue`). — [pump.json IDL](https://github.com/pump-fun/pump-public-docs/blob/main/idl/pump.json); [GodsEye schema](agent/src/analysis/analyze.ts) [D/internal]
- Evidence that these signals change copier outcomes: none found. The only copier-vs-leader quantification (14% vs 3%, and -41% at a 2-minute delay) is in the earlier notes and does not condition on creator-linkage.

### Inferences
- Rules (cheapest first), each applied per token to the copy decision only:
  1. `leader == TradeEvent.creator`: the leader is the deployer. Skip, or size-down hard (the leader's buy is not independent information). Zero RPC.
  2. `leader_buy_slot - create_slot <= K` (K around 5, per the earlier K=5 window) or same Jito bundle as the create: flag as "launch-block participant". Our 60 s lateness limit means we are already behind this cohort; the flag matters most for predicting how soon the leader exits.
  3. Creator -> leader funding: precompute, per tracked leader (about 10 with `copy_weight>0`), the set of funders over 2-3 hops once and cache it; per token, test whether the creator (or the creator's first funder) is in that set, or whether the creator sent SOL to the leader in the last N hours. This is a handful of RPC calls amortised across all tokens, because leaders are few. Pine's 5-7 hop finding means one-hop checks will miss many.
  4. Leader buy as a share of pool: if the leader's own buy moved price by more than a few percent on the curve, chasing it costs more; use the post-trade reserves in `TradeEvent`.
- How to express as a signal, not a wallet verdict: add `leader_context` fields to the copy record (creation-block, creator-is-leader, creator-funded, leader tip) and apply a size multiplier or skip per token; keep the wallet's `copy_weight` unchanged. The measurement needs shadow-mode logging of every candidate plus later prices from a full-tape source (per the conclusion of `internal_audit.md`, because the tracked-wallet tape goes silent after a pull), then compare outcomes of flagged vs unflagged copies.

### Gaps
- No published outcome comparison of copies of creator-linked vs independent buyers.
- No evidence on how well the 2-3 hop funder search separates "creator-funded" from legitimately shared CEX/withdrawal funders (high false-positive risk if exchange hot wallets are not excluded; MemeTrans's co-funder heuristic does exclude CEXs per earlier notes).
- Same-bundle detection requires the bundle composition (Jito bundle id); only the tip transfer is visible on-chain from the leader's own transaction, so membership in a bundle with the create transaction cannot be proven from the leader's data alone.

## 6. What can be done from data the bot already streams vs what needs extra RPC

### Takeaway
Most of the high-value, pump-specific checks (creator = leader, creator sold, mayhem/holder-reward/quote mode, reserves and exit capacity, curve completion, copycat, creation-block) come free from pump program events if the decoder keeps the event fields; the static Token-2022 read piggybacks on the mint fetch the screen already makes; creator history, creator funding and the buy+sell simulation need extra calls.

### Cited Findings
- The pump events carry the needed fields (see Sections 2-5): `TradeEvent` (reserves, creator, mayhem_mode, quote_mint, fee, is_buy, user), `CreateEvent` (creator, token_program, mayhem, holder-reward, quote), `CompleteEvent`, `CompletePumpAmmMigrationEvent`, PumpSwap `BuyEvent`/`SellEvent` (pool reserves, coin_creator, base_supply), `CreatePoolEvent` (pool, coin_creator, mayhem). — [pump.json](https://github.com/pump-fun/pump-public-docs/blob/main/idl/pump.json), [pump_amm.json](https://github.com/pump-fun/pump-public-docs/blob/main/idl/pump_amm.json) [D]
- Existing stream/store: the bot stores `wallet_swaps` rows with `slot`, `price_sol`, `venue`, `jito_tip`, `fee_lamports`, `token_age_sec`, `quote`, `quote_amount` for tracked wallets only (6,192 wallets) — [agent/src/analysis/analyze.ts line 60](agent/src/analysis/analyze.ts) [internal]. The tape therefore lacks swaps by untracked wallets, which limits creator-history and reserve freshness from stored data alone (`internal_audit.md`).
- Jupiter limits that bound extra calls: keyless 0.5 req/s, free key 1 req/s, Developer 10 req/s. — [Jupiter Swap V2](https://developers.jup.ag/docs/swap.md) [D]
- Yellowstone gRPC is the standard low-latency account/transaction stream (1,015 stars, AGPL-3.0, active) — [rpcpool/yellowstone-grpc](https://github.com/rpcpool/yellowstone-grpc) (as recorded in `signals_ml_opensource.md`) [D/secondary]

### Inferences
Table (my assessment; latencies are not measured and are not claimed):

| Check | Data source | Marginal cost | Notes |
|---|---|---|---|
| Creator == leader; creator sold; creator share | pump `TradeEvent` stream | none if event fields decoded | needs a per-mint running state |
| Creation-block / launch-block participation | `CreateEvent` slot vs leader `slot` | none | `token_age_sec` is second-resolution; slot diff is better |
| Reserves, own impact, stressed exit (`T/B`) | latest `TradeEvent` / PumpSwap `BuyEvent`/`SellEvent` | none if recent event; else 1 `getMultipleAccounts` | thin tape fallback |
| Curve complete / migrated; mayhem; quote mint; holder-reward | `CompleteEvent`, `CreateEvent`, `BondingCurve` | none (events) or same fetch as above | decoder must support `create_v2`, v3 |
| Copycat / duplicate ticker | local map from `CreateEvent` name/symbol | none | high FP |
| Token-2022 extensions: hook, transfer fee (older+newer), non-transferable, update authorities | mint `getAccountInfo` | zero marginal (mint is already fetched for authority check) | parse extension TLV |
| Post-buy mint watch | Yellowstone account subscription to held mints | near zero | catches hook swap, fee change, freeze authority use |
| Buy+sell simulation | 1 `simulateTransaction` (+ Jupiter `/build` or pump SDK) | 1 RPC + 1-2 Jupiter calls | within free-key 1 req/s only if serialised |
| Creator prior-launch history | Helius `getTransactionsForAddress` + `getMultipleAccounts` on curves | about 2-3 calls | or run a program-wide `CreateEvent` indexer |
| Creator first funder / cluster | `getTransactionsForAddress` oldest-first, limit 1, then hops | 1-4 calls | reuse existing funder-cluster code |
| Metadata/social | HTTP fetch of URI | 1 external fetch, slow/variable | async only |

- Suggested order of implementation by value/cost (inference): (1) decode and persist pump create/trade/complete events; (2) static extension read incl. pending fee; (3) pool-relative stressed-exit and complete/migration/quote/mayhem gates; (4) creator-is-leader / creation-block flags; (5) buy+sell simulation; (6) creator history and funding; (7) copycat and metadata.

### Gaps
- Per-check latency and credit cost on the bot's actual RPC provider are unmeasured; Yellowstone bandwidth for a program-wide pump subscription is not quantified.
- Whether the bot's decoder retains the event-level fields above was not inspected beyond the `wallet_swaps` schema.

## 7. Published evidence on loss reduction from pre-trade filters: effect sizes and caveats

### Takeaway
Only one study reports a simulated loss reduction from a risk model (MemeTrans: 60.71% -> 26.64% average loss, top-100 pick, MLP). It applies to a narrow, favourable setup (selecting the 100 lowest-risk of a few thousand test tokens, buying at migration, 1-hour horizon) and does not transfer directly to a veto-style filter on copy trades. Rule-based detectors report high precision/recall but against labels they define themselves; ML early-warning work reports modest, venue-specific skill. No study quantifies the loss avoided by simple structural gates (authorities, LP lock, extensions, simulation).

### Cited Findings
- MemeTrans (41,470 pump tokens that migrated to Raydium, Dec 2024-Mar 2025): top-100 tokens ranked by predicted risk: random (no model) precision 0.254 and loss 60.71%; MLP 0.800 and 26.64%; RF 30.34%; XGBoost 31.45%; LightGBM 31.99%; LR 34.06%. Top-200: random 64.84%, MLP 31.47%. Protocol: purchase at migration price, loss averaged over 100 random sell times within the next hour; precision means share of selected tokens that are not high-risk; recall at top-k not reported; the paper calls it a 56.1% relative reduction. Labels: high-risk if the minimum price within 20 min after migration <0.3x migration price or a manipulation-detector score >=0.7; features use only pre-migration data; only migrated tokens covered; tokens with sale <1 min or <100 holders excluded; 74% of the filtered task data is high-risk; labels are derived from post-migration behaviour. — [MemeTrans, arXiv 2602.13480](https://arxiv.org/html/2602.13480v1) [P]
- "Catching the Rug" (arXiv 2608.20271): features from the first 5 minutes predict 1-hour fraud; in-domain MCC about 0.25-0.36; cross-DEX transfer collapses (MCC ~0); authors say results are "not yet sufficient for real-world deployment". — [Li et al.](https://arxiv.org/abs/2608.20271) [P] (figures as recorded in `signals_ml_opensource.md`)
- SolRugDetector (rule-based, H1 2025, 100,063 tokens): reported accuracy 0.9936, recall 0.9540, precision 0.9838 for separating non-malicious tokens from scams prior to the malicious manoeuvre; labelling false-positive rate 0.26% (1 of 382 audited); the tool's labels and the benchmark (117 verified rugs) come from the same authors' rules. — [arXiv 2603.24625](https://arxiv.org/abs/2603.24625) (accuracy figures from search snippet; FP rate from the fetched full text) [P]
- Pump.fun success study (Sept 2025): conditional graduation-probability curves only; no AUC/accuracy; every strategy tested mostly below buy-and-hold breakeven; the authors state the breakeven comparison ignores fees and gas. — [arXiv 2602.14860](https://arxiv.org/html/2602.14860v1) [P]
- Copy-trading ablation (earlier notes): removing the wallet agent cut copier gross return 9.4% and the coin agent 8.5%; the copier-vs-leader gap and delay results are in `copy_edge_and_adversaries.md`. — [arXiv 2601.08641](https://arxiv.org/html/2601.08641) [P]
- Warning against circular scores: SolRPDS's AUC 0.987 uses a label derived from the same liquidity-activity features (recorded in `signals_ml_opensource.md`). — [arXiv 2504.07132](https://www.arxiv.org/pdf/2504.07132) [P]
- Scanner vendors (RugCheck, GoPlus, Sharpe, InsightX, Jupiter Shield) publish no precision/recall or loss-avoided figures that I could find; Jupiter states Shield accuracy "is expected to change". — [Jupiter Shield](https://developers.jup.ag/docs/ultra/get-shield.md) [D]

### Inferences
- Reading the MemeTrans number correctly: random baseline 60.71% is a very high loss because the population is 74% high-risk and the horizon is one hour from the migration price. My arithmetic: after the <1 min / <100-holder filter 41,470 - 19,835 = 21,635 tokens remain; a 30% test split is roughly 6,500 tokens (assumes a 7:3 chronological split on the filtered set; paper split details not fully verified), so top-100 is about the best 1.5%. The loss reduction therefore comes from picking the safest few, not from vetoing the riskiest; a veto filter that keeps, say, half of candidates will show a smaller improvement, and that curve (loss vs share kept) is not published. Expect less than the headline.
- For GodsEye the nearest use is as a veto/size-down using the feature groups shown to matter (market-activity: sale duration, tx/buyer/holder counts; bundle-aware holder concentration; dev holding), and the earlier notes already propose this. The Li et al. result (MCC ~0.3 in-domain, ~0 across venues) warns that a model trained on one venue/regime (pump pre-migration) will not carry to PumpSwap-era or other venues, and CoinGecko-style regime shifts (profitable-wallet share swinging 30-73%) make a fixed threshold stale.
- The only decision-useful way to quantify filter value for this bot is its own: run each candidate check in shadow mode on every leader buy (the screen has never run live, `internal_audit.md`), record verdict and inputs, and measure counterfactual outcome of blocked vs passed copies from a full-tape price source. Report loss avoided, wins forgone and share of copies blocked, because published figures give no such trade-off.

### Gaps
- No study reports loss reduction for simple rules (authority checks, LP lock, extension checks, buy+sell simulation, creator history) on Solana memecoins.
- No study measures filters on actual copy-trade entries (all use random or pre-selected token baskets).
- No published recall-at-k or loss-versus-coverage curve for MemeTrans; the test-set size is not stated in the text I read.
- No 2026 H2 update to rug base rates or filter performance; Chen (H1 2025) and MemeTrans (Dec 2024-Mar 2025) pre-date mayhem mode, holder-reward coins, quote-paired coins and the current PumpSwap fee schedule.
