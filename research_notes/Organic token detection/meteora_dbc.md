# Meteora Dynamic Bonding Curve (DBC) on Solana: mechanics, data availability, detection, and executability

Research date: 2026-10-27. Method notes: "Live measurement" items below were collected by me on 2026-10-27 from public GET endpoints (GeckoTerminal v2, DexScreener, Jupiter lite-api, GitHub raw) and are point-in-time. The live sample is the top 100 Meteora DBC pools by 24h volume on GeckoTerminal (pools created roughly 2026-10-26 03:00 to 23:00 UTC), so it is biased toward high-volume, very new pools and is NOT a representative sample of all DBC tokens. Programs.ts check: /Users/srinjoydas/GodsEye/agent/src/chain/programs.ts maps only `LBUZKhRx...` (DLMM) and `Eo7WjKq6...` (DAMM v1, per the IDL below) to "meteora". It has neither the DBC program nor the DAMM v2 program, so DBC swaps and the post-migration DAMM v2 swaps are both unlabelled as DBC/Meteora (Jupiter-routed ones will be labelled "jupiter" by VENUE_RANK unless inner instructions are inspected).

## 1. DBC mechanics: programs, accounts, curve parameters, instructions, events, migration, token program

### Takeaway
DBC is a single Anchor program (`dbcij3LWUppWqq96dh6gJWwBifmcGfLSB5D4DuSMaqN`, same id on mainnet and devnet) where a launchpad "partner" creates a `PoolConfig` and users create a `VirtualPool` per token that trades on a virtual piecewise curve until `quote_reserve >= migration_quote_threshold`, after which a keeper (or anyone, via the manual migrator) calls `migration_damm_v2` to move liquidity into a Meteora DAMM v2 pool (DAMM v1 is deprecated for new pools). Base tokens are SPL Token or Token-2022; in my live sample 68 of 100 were Token-2022.

### Cited Findings
- Program id: `dbcij3LWUppWqq96dh6gJWwBifmcGfLSB5D4DuSMaqN` on mainnet-beta and devnet; repo has `programs/dynamic-bonding-curve`, `idls`, TypeScript SDK; DAMM v2 is the recommended migration target and DAMM v1 (`migration_option` 0) is deprecated and rejected for new configs/pools but existing pools can still migrate — [MeteoraAg/dynamic-bonding-curve README](https://github.com/MeteoraAg/dynamic-bonding-curve)
- Partners configure launch pools (quote mint, fees, curve, token type, decimals, migration params); users create tokens on partner UIs; curve is piecewise (each price range has its own liquidity); token graduates once quote reserve reaches `migration_quote_threshold` and migrates to a DAMM pool; trading fees go to protocol, optional swap host referral, partner, and optionally creator; after migration LP is locked for partner/creator who claim fees on locked LP — [README](https://github.com/MeteoraAg/dynamic-bonding-curve)
- `token_type` 0 = SPL Token, 1 = Token-2022; token decimals 6 to 9 — [README](https://github.com/MeteoraAg/dynamic-bonding-curve)
- Docs: DBC is a "token launch primitive" that creates a virtual reserve pool, trades through a configured curve, migrates finished pools to DAMM v2; curves can have 1 to 16 segments (config array capacity 20) — [Meteora DBC developer guide](https://docs.meteora.ag/developer-guides/dbc.md), [What is DBC](https://docs.meteora.ag/core-products/dbc/what-is-dbc.md), [constants.rs](https://raw.githubusercontent.com/MeteoraAg/dynamic-bonding-curve/main/programs/dynamic-bonding-curve/src/constants.rs)

VirtualPool PDA seeds: quote mint, base mint, config. Base/quote vault seeds: pool + mint. ### Inferences
- Because the 10 SOL keeper threshold is cheap and graduation can occur minutes after creation, "graduated DBC token" tells you almost nothing about organic demand; the threshold is set by the partner config, so copy decisions should read `migration_quote_threshold` from the config (offset 264) rather than assume graduation means success.
- Because migration emits no DBC event and `is_migrated` is only set in the migration handler, the cheap stream-side signal for graduation is the `migration_damm_v2` instruction itself (top-level or inner) or `EvtCurveComplete` for "curve full, awaiting migration".
- The tradable gap between curve completion and keeper migration (swaps return PoolIsCompleted) is not documented numerically; I did not measure it.

### Gaps
- Exact supply split (how much of 1B goes to curve vs post-migration LP vs vesting) is config-specific and not given in the docs I could read; the `What is DBC` page explicitly does not disclose it.
- The docs page for the trading-terminal integration guide (`integrate-with-dbc`) returned 404 on direct fetch; only search snippets were seen.
- Anti-sniper docs page returned 404 on fetch; numbers come from a third-party GitHub issue.
- Could not confirm which of the two keeper addresses is current.
- Audit report contents not read.

## 2. Launchpads on DBC, share of launches, and known abuse

### Takeaway
Many launchpads sit on DBC (Jupiter Studio, Bags, Believe, Moonshot, daos.fun, trends.fun, StonkFun, Swarms and others, each identified by a partner `config` pubkey), and the one hard share figure I found is Aug 31 2025: Meteora DBC 35.3% of Solana token issuance vs pump.fun 49.3% (a year old). In today's live data most high-volume DBC tokens are throwaway farm launches: they graduate within minutes, trade with tiny organic participation, and the migrated DAMM v2 pool is drained to under $1 liquidity.

### Inferences
- The pattern in the live sample (graduation within minutes at the keeper's cheap 10 SOL threshold, hundreds of round-trip trades from a few hundred wallets, post-graduation pool drained to about $1, dev wallets with 100+ prior mints, Jupiter organic score 0) is consistent with automated launch farming plus volume churn, probably to harvest creator/partner fees or to bait copy-trading and screener feeds. This is my interpretation of the data, not a sourced conclusion. The sample is the highest-volume pools, so it over-represents churn.
- The post-graduation liquidity collapse likely reflects the creator/partner claiming or removing their LP allocation (configs allow unlocked partner/creator LP percentages) but I did not verify the mechanism on-chain.
- Smart-money wallets appearing in such tokens may be farm-operated wallets rather than informed traders; the wash_trading_signals note in this folder may be a better place for wallet-level heuristics.

### Gaps

- Could not read Jupiter or Dune dashboards; no official abuse statements located.
- `hooked` and `ember` launchpad labels in Jupiter's API: could not determine what apps/configs they are (the label `ember` is unrelated to the user's persona as far as I can tell).

## 3. Data availability: DexScreener, GeckoTerminal, Birdeye, Jupiter, Solscan, Helius, and why a token can look empty

### Takeaway
DexScreener, GeckoTerminal and Jupiter all index DBC virtual pools before migration (DexScreener `dexId: meteoradbc`, GeckoTerminal `meteora-dbc`, Jupiter `Dynamic Bonding Curve` route label and `met-dbc` launchpad), with volume, txns and FDV, but DexScreener omits the liquidity field for DBC pairs, and after migration the new DAMM v2 pair (dexId `meteora`, label `DYN2`) commonly shows about $1 liquidity and FDV 1 because the pool was drained. So "no volume/no data" in DexScreener is mostly a presentation of a drained or liquidity-less state, not a missing index, in my sample; I could not reproduce an outright missing token.

### Cited Findings

## 4. Detecting DBC activity in a stream and reading curve state

### Takeaway
Match program id `dbcij3LWUppWqq96dh6gJWwBifmcGfLSB5D4DuSMaqN` in both top-level and inner instructions (Jupiter-routed DBC swaps appear as inner instructions), identify swaps by the `swap`/`swap2`/`swap2_with_transfer_hook` discriminators and swap events via the Anchor event-CPI self-invocation, read the pool with one `getAccountInfo` using the fixed byte offsets, and treat `migration_damm_v2` (or `is_migrated`=1 / `migration_progress`=3) as the graduation signal; the new DAMM v2 pool address is account index 4 of that instruction or `graduatedPool` from Jupiter.

### Cited Findings
- Add `dbcij3LWUppWqq96dh6gJWwBifmcGfLSB5D4DuSMaqN` (DBC) and `cpamdpZCGKUy5JxQXB4dcpGPiikHawvSWAd6mEn1sGG` (DAMM v2) to venue detection; GodsEye's current table lacks both — [programs.ts](/Users/srinjoydas/GodsEye/agent/src/chain/programs.ts) read locally, ids from [DBC README](https://github.com/MeteoraAg/dynamic-bonding-curve) and [DAMM v2 IDL](https://raw.githubusercontent.com/MeteoraAg/dynamic-bonding-curve-sdk/main/packages/dynamic-bonding-curve/src/idl/damm-v2/idl.json)
- Swap recognition by first 8 data bytes: `swap` `f8c69e91e17587c8`, `swap2` `414b3f4ceb5b5b88`, from the IDL decimals `[248,198,158,145,225,117,135,200]` and `[65,75,63,76,235,91,91,136]` (hex conversion by me). `swap2_with_transfer_hook` exists for transfer-hook pools — [IDL json](https://raw.githubusercontent.com/MeteoraAg/dynamic-bonding-curve-sdk/main/packages/dynamic-bonding-curve/src/idl/dynamic-bonding-curve/idl.json)

- New launch signal: instruction `initialize_virtual_pool_with_spl_token` or `initialize_virtual_pool_with_token2022` (and the transfer-hook variant) or `EvtInitializePool`; pool = index 5, base_mint = 3, config = 0, creator = 2 — IDL, [Bitquery](https://docs.bitquery.io/docs/blockchain/Solana/meteora-dynamic-bonding-curve-api/)
- Events are Anchor `emit_cpi!`: look for an inner instruction to the DBC program whose data begins with tag `e445a52e51cb9a1d` then the 8-byte event discriminator (EvtSwap2 `bd4233a826507599`, EvtCurveComplete `e5e756549c864b18`, converted by me from the IDL decimals) — [ix_swap.rs](https://raw.githubusercontent.com/MeteoraAg/dynamic-bonding-curve/main/programs/dynamic-bonding-curve/src/instructions/swap/ix_swap.rs), IDL. Progress = quote_reserve / config.migration_quote_threshold (config read at offset 264). ## 5. Executability through Jupiter and price impact

### Takeaway
Yes. Jupiter quotes and routes pre-migration DBC pools (route label "Dynamic Bonding Curve", ammKey = the virtual pool address) and post-migration pools (label "Meteora DAMM v2"). Price impact on a live pre-migration token was small for 1 SOL (0.034%) and 20 SOL (0.19%), but post-migration pools on churn tokens are effectively empty, so executability does not imply meaningful exit liquidity.

### Cited Findings
- Jupiter announced (April 2025) that tokens launched through DBC are available instantly within Jupiter routing — [Jupiter on X](https://x.com/JupiterExchange/status/1915474312728871016) (snippet only). Meteora docs say swap hosts like Jupiter, Photon and trading bots can pass a referral account to earn part of the protocol fee — [Meteora integration guide (snippet)](https://docs.meteora.ag/developer-guide/trading-terminals/integrate-with-dbc.md)
- Live quote, pre-migration TMINUS (`6ZEKAPJ5o5sQR5XMG4xg1QoU2W8tMeAq1Q46zGqtTxph`, liquidity about $5.75k on Jupiter): SOL to token, 1 SOL in gave outAmount 4,569,760,449,614 raw with `priceImpactPct` 0.0339, single route hop labelled "Dynamic Bonding Curve" with `ammKey` `8XM1u1i4BfCW9f92NLww1vGyqCQjXyz5ctucQogJjaKo` (the DBC pool); 20 SOL in had `priceImpactPct` 0.194 and still a single "Dynamic Bonding Curve" hop — [Jupiter lite-api quote, 1 SOL](https://lite-api.jup.ag/swap/v1/quote?inputMint=So11111111111111111111111111111111111111112&outputMint=6ZEKAPJ5o5sQR5XMG4xg1QoU2W8tMeAq1Q46zGqtTxph&amount=1000000000&slippageBps=100)
- Live quote, post-migration EDGE (`HiTtfNd...`, DAMM v2 pool liquidity $0.62): 0.1 SOL in returned outAmount 732,917,229,103,943 raw with `priceImpactPct` 0.93 via one hop "Meteora DAMM v2" `ammKey` `BPFHijMN3MB6zvyNhH6Wxuj5n15xksxvgoFKaFy45aDV`. Implied price versus the DBC pool price (about 1.9e-7 SOL per token per GeckoTerminal) is about 1,400x lower — [Jupiter lite-api quote, EDGE](https://lite-api.jup.ag/swap/v1/quote?inputMint=So11111111111111111111111111111111111111112&outputMint=HiTtfNdK1rmZtXFv9wquxBCqBbVWzkqgHtqtSDj4iKoY&amount=100000000&slippageBps=100)
- Swap errors a copier can hit pre-migration: `ExceededSlippage` 6002, `PoolIsCompleted` 6013 (curve full awaiting migration), `AmountLeftIsNotZero` 6047 (exact-in near completion needs partial fill), `NotEnoughLiquidity` 6012 — [Program errors docs](https://docs.meteora.ag/developer-guides/dbc/program/errors.md)
- Anti-sniper fees mean the first buys in a pool can pay up to a 99% fee with a decaying schedule, so a copy buy seconds after creation can execute at a very different effective price than the leader's — [Fees docs](https://docs.meteora.ag/core-products/dbc/fees.md) (max 99%, scheduler), [top-pad issue 4](https://github.com/imDev2023/top-pad/issues/4) (third-party numbers)
- Token-2022 base mints (68% of the sample) may carry a transfer fee up to 10% (0.2.2) or transfer hook; GodsEye's ALLOWED_SWAP_PROGRAMS already includes Token-2022 but Jupiter must handle hook accounts — [CHANGELOG](https://raw.githubusercontent.com/MeteoraAg/dynamic-bonding-curve/main/CHANGELOG.md), [constants.rs](https://raw.githubusercontent.com/MeteoraAg/dynamic-bonding-curve/main/programs/dynamic-bonding-curve/src/constants.rs)

### Inferences
- The Jupiter `priceImpactPct` on DAMM v2 for EDGE looks inconsistent with a $0.62-liquidity pool (0.93% for 0.1 SOL), so the quoted impact field is not a reliable guard for drained pools; a guard should compare the quote's implied price to the leader's fill price and require minimum pool liquidity (e.g. Jupiter `liquidity` or reserve reads) instead.
- Copy-trade allowlist in programs.ts (`ALLOWED_SWAP_PROGRAMS`) checks only top-level programs, which stays valid for Jupiter-wrapped DBC swaps; a direct (non-Jupiter) DBC route would need the DBC program added.
- A practical filter set for the smart-money feed from these findings: drop or flag tokens with `launchpad = met-dbc` that are pre-migration and younger than N minutes, where distinct traders is small relative to txns, where dev wallet mint count (`devMints`) is high, or where post-migration DAMM v2 liquidity is under a few dollars. These are suggestions, not tested thresholds.

### Gaps
- Did not execute or simulate a swap; quotes only. Price impact for large sizes after migration not characterised beyond the single EDGE sample.
- Jupiter's official docs on DBC routing (beyond the April 2025 announcement) not found; JUP docs URLs I tried returned 404.
- Behavior of Jupiter quotes for Token-2022 transfer-fee or transfer-hook DBC tokens not tested.
