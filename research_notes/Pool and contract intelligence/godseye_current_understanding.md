## 2. How a swap is identified and attributed

### Takeaway
The parser is deliberately DEX-agnostic: it reads one wallet's balance changes and accepts a swap when exactly one non-quote token moved and the wallet paid/received SOL, wSOL, USDC or USDT (or two tokens settled through a SOL hop). That makes Jupiter multi-hop routes, wSOL wrapping and unknown programs "just work", but it also means the venue label, pool identity and any non-SOL/USDC/USDT quote are lost, a hard-coded rent constant is now wrong, and non-Jito tips are counted as swap price.

### Cited Findings
- Wallet attribution: the signer's own token accounts (`owner === wallet`) and native lamports; the fee payer gets the network fee added back. [parse.ts:181-182](file:///Users/srinjoydas/GodsEye/agent/src/chain/parse.ts), [parse.ts:192-193](file:///Users/srinjoydas/GodsEye/agent/src/chain/parse.ts)
- Jupiter-routed multi-hop (A -> pool -> B -> pool -> memecoin): intermediate hops sit in program-owned accounts, so only the wallet's SOL/stable and the final token move; it is recorded as one buy/sell with venue `jupiter`. The pools actually used are not recorded. [parse.ts:233-294](file:///Users/srinjoydas/GodsEye/agent/src/chain/parse.ts), [parse.ts:97-110](file:///Users/srinjoydas/GodsEye/agent/src/chain/parse.ts)
- Token <-> token swaps: accepted only when exactly 2 tokens moved with opposite signs, no stablecoin moved, wallet SOL change under 0.0005 SOL, and `routedSolLamports` finds a biggest SOL drop and biggest SOL rise among non-wallet accounts that agree within 90% and are each >= 0.001 SOL; recorded as a sell + a buy, both at the routed SOL value, quote label `SOL (routed)`. [parse.ts:117-144](file:///Users/srinjoydas/GodsEye/agent/src/chain/parse.ts), [parse.ts:243-266](file:///Users/srinjoydas/GodsEye/agent/src/chain/parse.ts). DB query: 3,399 swaps (0.12%) carry `SOL (routed)`.
- Any token pair without a SOL hop is dropped (returns `[]`), as is any swap in which a mint from `NON_MEMECOIN_MINTS` moves, or three or more tokens move. [parse.ts:233-234](file:///Users/srinjoydas/GodsEye/agent/src/chain/parse.ts), [parse.ts:268](file:///Users/srinjoydas/GodsEye/agent/src/chain/parse.ts). `NON_MEMECOIN_MINTS` includes USD1, PYUSD, USDS, EURC, JitoSOL, mSOL, JUP, RAY, cbBTC and others, so a memecoin quoted in USD1/PYUSD/USDS is silently discarded before it reaches the DB. [constants.ts:18-42](file:///Users/srinjoydas/GodsEye/shared/src/constants.ts)
- wSOL: its token-balance delta is folded into lamports and removed from the token list; a wSOL account opened and closed inside the transaction never shows up in pre/post token balances, so native lamports already net it. [parse.ts:212-217](file:///Users/srinjoydas/GodsEye/agent/src/chain/parse.ts)
- USDC/USDT: a stable change >= $0.01 counts as quote; converted to SOL using `solUsdAt`; if the SOL price is unknown the swap is dropped. Quote label distribution (DB query): SOL 96.17%, USDC 2.86%, SOL+USDC 0.80%, SOL (routed) 0.12%, USDT 0.04%, SOL+USDT 0.004%.
- LP add / remove: both legs move the same way (token out + SOL out, or token in + SOL in), so the sign test rejects them (`tokenDelta > 0 && value < 0` is a buy; `tokenDelta < 0 && value > 0` is a sell; anything else returns `[]`). Adds/removes that mint or burn an LP token or position NFT make `moved.length >= 2` and are dropped. [parse.ts:281-284](file:///Users/srinjoydas/GodsEye/agent/src/chain/parse.ts). No code anywhere records an LP event; there is no "LP add/remove" or "pool creation" event type.
- Pool creation and migration (pump.fun -> PumpSwap): nothing records them; the creator's seed deposit moves token and SOL out together and is dropped; the migration is performed by a program/bot and leaves the wallets' balances unchanged. Launch time is instead derived from the mint's first transaction or from GeckoTerminal's earliest pool. [history.ts:99-120](file:///Users/srinjoydas/GodsEye/agent/src/chain/history.ts), [tokens.ts:57-97](file:///Users/srinjoydas/GodsEye/agent/src/market/tokens.ts), [geckoterminal.ts:206-223](file:///Users/srinjoydas/GodsEye/agent/src/market/geckoterminal.ts)
- Token-2022: decimals are read from each transaction's own token-balance entries (`Number(amount) / 10 ** decimals`), so decimals are right for either token program. [parse.ts:94](file:///Users/srinjoydas/GodsEye/agent/src/chain/parse.ts). Token-2022 transfer fees are not modelled at all (see misclassification list item 6).
- The rent constant used to separate token-account rent from the trade is `2_039_280` lamports, applied as `(opened - closed) * 2_039_280`. [parse.ts:23](file:///Users/srinjoydas/GodsEye/agent/src/chain/parse.ts), [parse.ts:205-210](file:///Users/srinjoydas/GodsEye/agent/src/chain/parse.ts). Live chain values today: rent-exempt minimum for a 165-byte account = 1,488,440 lamports, 170 bytes = 1,513,840, 182 bytes = 1,574,800 (RPC `getMinimumBalanceForRentExemption`). — [Solana RPC](https://api.mainnet-beta.solana.com)
- Concrete example of the rent error: PumpSwap buy that opened a Token-2022 token account of 170 bytes (`createAccount` lamports 1,513,840): code stored `sol_amount = 0.056434` where the rent-corrected figure is `0.056959` (buy understated by 0.000525 SOL, 0.93% of a 0.056 SOL buy). The same constant over-credits the refund on sells that close an account. — [Solana RPC tx sample, 8 PumpSwap/pump.fun swaps; 1 of 8 opened an account](https://api.mainnet-beta.solana.com)
- Tips: only the 8 Jito tip accounts are recognised (`JITO_TIP_ACCOUNTS`); they are added back in `parseSwaps`/`tradeCostSol` and set `jito_tip`. [programs.ts:34-43](file:///Users/srinjoydas/GodsEye/agent/src/chain/programs.ts), [parse.ts:184-189](file:///Users/srinjoydas/GodsEye/agent/src/chain/parse.ts). In a 12-swap sample of `SOL+USDC`-labelled direct Raydium/Orca/Meteora swaps (selected because they carry the mixed label, so this explains the label rather than measuring its prevalence), all 12 had a native SOL residual of 0.0005 to 0.0039 SOL with no token account opened or closed (6 of 12 at exactly ~1,000,000-1,000,100 lamports) that is not a Jito account and not rent, i.e. a relay/bot tip or fee. It exceeds `SOL_NOISE` (0.0005) so the swap is labelled `SOL+USDC` and the tip is priced into the swap. [parse.ts:28](file:///Users/srinjoydas/GodsEye/agent/src/chain/parse.ts), [parse.ts:272-274](file:///Users/srinjoydas/GodsEye/agent/src/chain/parse.ts). — [Solana RPC sample](https://api.mainnet-beta.solana.com)
- Stream timestamps: `convertGrpcTx` sets `blockTime = receivedAtMs/1000`, so streamed swaps carry receive time, history swaps carry block time. [convert.ts:62-64](file:///Users/srinjoydas/GodsEye/agent/src/stream/convert.ts)
- Venue detection: top-level instruction programs first (ranked), then inner instructions; if the venue came only from an inner instruction AND some top-level program is neither plumbing nor a venue, it is labelled `<venue> (via bot)`. [parse.ts:97-110](file:///Users/srinjoydas/GodsEye/agent/src/chain/parse.ts). Venue is never used to accept/reject a swap and no pool address or pool type is stored on the swap row (`wallet_swaps` columns: wallet, signature, slot, ts, mint, side, token_amount, token_balance_before, sol_amount, price_sol, venue, jito_tip, fee_lamports, token_age_sec, quote, quote_amount, sol_usd, usd_amount; DB schema).

### Inferences — constructible misclassification risks
1. **Unlisted pool programs get `venue = NULL` while still counting as swaps.** Evidence: 255,623 swaps, 39 of 41 sampled being DAMM v2. These are not "unknown venue" in the benign sense: the wash-trading pattern below is concentrated there. Example mint `FVzXko3DbK5bKPVf8xFwogoGFJXqLktBVsBYCs9RkyEp` (`michi`): all 3,114 swaps null-venue, 21 wallets, each wallet ~90 buys and ~90 sells (net SOL about zero), 7,512 SOL gross volume in 16 minutes (DB queries by mint/wallet). RugCheck lists a single `meteora_damm_v2` market with 0% LP locked and ~$54 liquidity for it today. — [RugCheck report](https://api.rugcheck.xyz/v1/tokens/FVzXko3DbK5bKPVf8xFwogoGFJXqLktBVsBYCs9RkyEp/report). 68 wallets have >50% null-venue swaps; 63 of them are in the `insider` tier (DB query joining `wallets.tier`), versus 1,340 insiders out of 6,959 wallets overall.
2. **Stale rent constant** biases every first buy (which opens an account) and every full exit (which closes one) by roughly 0.0005 SOL, and can flip the `usesSol` test for USDC-quoted swaps (residual `+0.000525` SOL exceeds `SOL_NOISE`), producing a spurious `SOL+USDC` label. Token-2022 accounts with extensions have yet another size.
3. **Non-Jito tips/relay fees are priced into the swap** (above), mis-labelling the quote and hiding `jito_tip` for relays that are not Jito (the classifier's tip rule, [classifier.ts:98-99](file:///Users/srinjoydas/GodsEye/agent/src/analysis/classifier.ts), only sees the 8 Jito accounts).
4. **Create-and-buy**: on pump.fun a creator's launch tx moves SOL for mint/metadata/curve account rent as well as the buy; only token-account rent is subtracted, so the parsed buy cost includes that rent (inferred from code, not measured).
5. **Single-sided LP and position moves can masquerade as swaps** if an unrelated SOL leg of the right sign is present (position-account rent refund >= 0.0001 SOL on a single-sided deposit looks like a sell; rent paid on a single-sided withdraw looks like a buy). Constructible from the sign rule at [parse.ts:281-284](file:///Users/srinjoydas/GodsEye/agent/src/chain/parse.ts); I did not find a confirmed instance.
6. **Transfer-fee Token-2022 tokens**: the wallet's balance delta is net of the fee on a buy and gross on a sell, so the wallet-level "price" is worse than the pool's by the fee in both directions. In a 300-mint swap-weighted sample, 11 mints had `transferFeeConfig` (100-300 bps); in a 300-mint random `token_info` sample, 6 did (all 100 bps). The parser, the replay tape (which then divides by `1 +/- feeBps` again, [model.ts:131-134](file:///Users/srinjoydas/GodsEye/agent/src/replay/model.ts)) and the depth estimator ([model.ts:179-193](file:///Users/srinjoydas/GodsEye/agent/src/replay/model.ts)) all treat the stored price as pool-level.
7. **Merged pools**: the replay tape groups by `mint` only, so a token that traded across pump.fun, PumpSwap, DLMM, DAMM v2 etc. is one price series with one fee and one depth. DB query for 2026-10-22: of 9,297 mints, 1,554 traded across at least 2 venue families (`jupiter` counted as a family, so this overstates distinct pools).
8. **Tokenized stocks counted as memecoins**: 23 permanent-delegate mints found in a 300-mint swap-weighted sample (xStocks and "Backpack Securities" tokens) account for 18,844 swaps, 701 wallets and 46,391 SOL of volume in wallet_swaps (DB query on that mint list). `isNonMemecoinSymbol` only catches xStocks (`/^[A-Z]{1,5}x$/`) and a fixed symbol list, so symbols like `AMD`, `LLY`, `MU`, `BABA` pass. [constants.ts:48-52](file:///Users/srinjoydas/GodsEye/shared/src/constants.ts); mints verified on chain via `getMultipleAccounts` as Token-2022 with `permanentDelegate`, `pausableConfig`, `defaultAccountState`, `scaledUiAmountConfig`. — [Solana RPC](https://api.mainnet-beta.solana.com)
9. **USD1/PYUSD/USDS-quoted memecoin pools** are invisible (dropped before insertion); the share is unmeasurable from the DB.
10. **Token <-> token detection can be fooled** because it picks the single biggest SOL drop and biggest SOL rise over every non-wallet account (including fee receivers or unrelated wallets in the same tx). Low probability, not observed.
11. **`(via bot)` is "any unknown top-level program"**, including wallet-guard or fee programs; and `jupiter` hides the real pool. Neither is wrong as a label, but both are weak proxies for "bot".

### Gaps
- No record of which pool a swap executed in, the pool's fee tier, or pool type; not reconstructible from `wallet_swaps` columns.
- How often `moved.length === 1` fails because of an extra token (e.g. token-2022 fee mint, LP NFT) cannot be measured, because those transactions are dropped at parse time.

## 3. Where pool state or liquidity is used, and what is not known

### Takeaway
GodsEye never reads a pool account. Every liquidity or depth number comes from a third party (Jupiter, GeckoTerminal, RugCheck) or is back-solved from the tape of stored swaps, and there is no per-swap "the pool" at all; `token_info.pool_address` is GeckoTerminal's highest-reserve pool for the token, populated for only 16.7% of tokens and used only for price candles.

### Cited Findings
- RPC calls that touch accounts: `getAccountInfo` on the mint (rugcheck.ts:116, holders.ts:121, verify.ts:84-88), `getTokenLargestAccounts` + `getMultipleAccounts` on the mint's top token accounts (holders.ts:122-127), `getTokenSupply` (decimals.ts:10), `getParsedTokenAccountsByOwner` for the bot's own wallet (executor.ts:66, wallet.ts:43), `simulateTransaction` with account return for GodsEye's own wallet and ATA (verify.ts:92). No pool, vault, LP mint, position or program account is ever fetched, and the gRPC subscription has `accounts: {}`. (Whole-repo grep for `getAccountInfo|getMultipleAccounts|getTokenAccountBalance|getTokenSupply|getTokenLargestAccounts|getProgramAccounts|accountSubscribe`.) [stream.ts:128](file:///Users/srinjoydas/GodsEye/agent/src/stream/stream.ts)
- Replay depth: constant-product assumption; "effective SOL reserve" estimated per token from pairs of consecutive tape swaps within 60 s (`reserve ~ (flow_i + flow_j) / delta ln(price)`, median, clamped to 1 to 5,000 SOL), window 600 s, falling back to the last 400 swaps then to a default of 30 SOL ("a fresh pump.fun curve"); DEX fee fixed at 100 bps one-way; impact capped at 3x; per-trade cost 0.0005 SOL. [model.ts:76-91](file:///Users/srinjoydas/GodsEye/agent/src/replay/model.ts), [model.ts:100-109](file:///Users/srinjoydas/GodsEye/agent/src/replay/model.ts), [model.ts:161-193](file:///Users/srinjoydas/GodsEye/agent/src/replay/model.ts), [model.ts:219-228](file:///Users/srinjoydas/GodsEye/agent/src/replay/model.ts). ## 4. Token contract knowledge

### Takeaway
The only on-chain token facts GodsEye reads are mint authority, freeze authority and the Token-2022 extension list of the mint (via one `getAccountInfo`), plus supply and the top-20 token accounts. Four extensions are acted on; transfer fee, non-transferable and metadata mutability are not. Token-2022 is the norm in this data (83% to 97% of sampled mints), so these omissions matter.

### Cited Findings
- `readMint` returns `mintAuthority`, `freezeAuthority`, `extensions` from `getAccountInfo(jsonParsed)`; it throws if the account is not a parsed mint, and the whole screen fails closed. [rugcheck.ts:71-90](file:///Users/srinjoydas/GodsEye/agent/src/market/rugcheck.ts), [config.ts:158](file:///Users/srinjoydas/GodsEye/agent/src/config.ts)
- Everything else comes from RugCheck's risks list: names matching `rugged|honeypot|scam` block; anything else except mint/freeze/permanent-control is passed through as a warning. The header's "mutable metadata" warning ([rugcheck.ts:21](file:///Users/srinjoydas/GodsEye/agent/src/market/rugcheck.ts)) is not implemented against chain data (`tokenMetadata.updateAuthority` is never read); it only appears if RugCheck says so. ## 5. Execution-side knowledge

### Takeaway
Execution is Jupiter-only and fails closed at the top-level program list, but it has no knowledge of which pools or AMMs a route uses; safety rests on the transaction simulation of GodsEye's own balances.

### Cited Findings
- Allowed top-level programs: Jupiter v6, System, ComputeBudget, SPL Token, Token-2022, ATA. Anything else, including a program resolved only through a lookup table, returns "calls an unexpected program ..." and nothing is signed. [programs.ts:46-53](file:///Users/srinjoydas/GodsEye/agent/src/chain/programs.ts), [verify.ts:34-65](file:///Users/srinjoydas/GodsEye/agent/src/copy/verify.ts) (check at verify.ts:44-45)
- Other static rules: GodsEye must be fee payer and sole signer; system instructions limited to transfer into its own wSOL ATA; token instructions limited to SyncNative and CloseAccount into its own wallet; priority fee within 2x `PRIORITY_FEE_MAX_LAMPORTS` (default 1,000,000). [verify.ts:37-63](file:///Users/srinjoydas/GodsEye/agent/src/copy/verify.ts), [config.ts:151](file:///Users/srinjoydas/GodsEye/agent/src/config.ts)
- Inner (CPI) programs are not inspected; Jupiter's `routePlan` is read only for logging labels in the gate. [gate.ts:138](file:///Users/srinjoydas/GodsEye/agent/src/audit/gate.ts). There is no allow/deny list of AMMs and no use of Jupiter's `dexes`/`excludeDexes`. [jupiter.ts:45](file:///Users/srinjoydas/GodsEye/agent/src/market/jupiter.ts)
- A swap through an unknown or newly added AMM is therefore accepted as long as Jupiter routes it, the top level is Jupiter, and the simulation passes; if Jupiter ever builds a transaction with an extra top-level program (for example a different aggregator program or a fee/tip instruction) it is refused rather than reviewed.
- Simulation: buy must spend at most `inLamports + 0.01 SOL` and deliver at least the quote's `otherAmountThreshold` tokens into the derived ATA; sell must return at least `otherAmountThreshold - 0.01 SOL`. `OVERHEAD_LAMPORTS = 10_000_000` is a flat slack independent of trade size. [verify.ts:27](file:///Users/srinjoydas/GodsEye/agent/src/copy/verify.ts), [verify.ts:98-105](file:///Users/srinjoydas/GodsEye/agent/src/copy/verify.ts)
- The fill is re-read from the landed transaction with the same parser (`parseSwap`) and `tradeCostSol`, so the stale rent constant and non-Jito tip handling also affect GodsEye's own recorded fills. [executor.ts:91-96](file:///Users/srinjoydas/GodsEye/agent/src/copy/executor.ts)
- Quote-based fills (paper mode and the fallback) assume the quote side is SOL (`/ LAMPORTS_PER_SOL`) and use decimals from `getTokenSupply`. [executor.ts:39-44](file:///Users/srinjoydas/GodsEye/agent/src/copy/executor.ts)
- Slippage default is 300 bps (`COPY_SLIPPAGE_BPS`). [config.ts:150](file:///Users/srinjoydas/GodsEye/agent/src/config.ts)

### Inferences
- A route through a honeypot or fee-on-transfer token is only stopped by (a) the rug check's extension rules and (b) the simulation; the sell-ability check (the gate's sell quote) is log-only, so today nothing in the live path requires a sell route to exist before buying.
- The flat 0.01 SOL slack makes the sell simulation check weak for positions worth less than about 0.05 SOL.

### Gaps
- Did not test how Jupiter builds routes for Token-2022 transfer-fee tokens (whether the quote already nets the fee).
- Never observed a real filled copy in this DB (`copy_trades`: 741 rows, all `real|skipped`), so the post-landing parse path has no stored evidence here.

## 6. Ranked gaps that would change decisions or produce wrong numbers

### Takeaway
The highest-value problems are (1) unlisted pool programs, especially DAMM v2, which both hide wash-trading farms inside the "insider" tier and are invisible to the live stream, and (2) the Token-2022 blind spots, because most current mints are Token-2022 and the rug check ignores transfer fees. The rest are smaller numeric biases or log-only machinery.

### Cited Findings (ranked)
1. **Meteora DAMM v2 / DBC / LaunchLab etc. unrecognised.** What is wrong: `VENUES` lacks them, so swaps get `venue = NULL`; the live stream never subscribes to transactions that only touch them; wash-trading farms there pollute wallet stats. Evidence: DB 255,623 null-venue swaps (8.95%); 39 of 41 sampled null swaps called `cpamdp...`; mint `FVzXko3D...` had 21 wallets x ~180 swaps, 7,512 SOL, net ~0; 63 of the 68 wallets with >50% null-venue swaps are `insider` tier. Fix difficulty: easy to add ids (stream widens automatically); medium to detect wash loops (same-wallet buy/sell churn, net-zero P&L) so they stop counting as skill.

11. **Execution allowlist knows programs, not routes or tokens.** Evidence: [verify.ts:44-45](file:///Users/srinjoydas/GodsEye/agent/src/copy/verify.ts) only top-level; no `routePlan` check; sell-ability only in the log-only gate; 0.01 SOL flat slack on simulation. Effect: a buy of a token that cannot be sold back, or through an unexpected AMM, passes if Jupiter quotes it and simulation succeeds. Fix difficulty: easy for requiring a sell quote and a max-impact before signing (the gate already computes them); medium for AMM allow/deny.
12. **Launch-time / "pool created" is borrowed from GeckoTerminal page 1 or the mint's first transaction, and the "crash" candles come from one current top pool.** Evidence: [geckoterminal.ts:206-223](file:///Users/srinjoydas/GodsEye/agent/src/market/geckoterminal.ts), [history.ts:99-120](file:///Users/srinjoydas/GodsEye/agent/src/chain/history.ts), [crash.ts:77-85](file:///Users/srinjoydas/GodsEye/agent/src/analysis/crash.ts); 22% of swaps (630,399) have `token_age_sec` NULL (DB query). Effect: early-buy and insider-tier signals use incomplete token age; crash checks use whichever pool is deepest now, not necessarily where the wallet sold (e.g. pre-migration curve). Fix difficulty: medium.

### Inferences
- Items 1, 2 and 3 can be fixed with changes confined to `programs.ts`, `rugcheck.ts` and `parse.ts` and each has direct, cheap evidence of impact. Items 4 to 6 share one root cause (no pool state) and would be solved together by a small pool-registry plus vault-balance reader.
- The wash-trading finding (item 1) is the only one that likely changes who gets copied: 63 `insider`-tier wallets are mostly null-venue churners. Copy weights today are positive for only 10 wallets (all `ai` / `insider`; average 24.9% of their swaps are null-venue; one has >50%). This is a statement about the local DB snapshot, not a statement that those 10 were selected because of the farms.

- I did not measure how many of the 68 high-null-venue wallets are farming versus genuinely trading a DAMM v2 token; only the `michi` mint was examined in detail.
