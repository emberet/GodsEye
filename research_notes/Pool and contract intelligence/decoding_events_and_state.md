## 1. How Anchor programs identify instructions and emit events, and the discriminators / IDL names for the target programs

### Takeaway
Anchor instruction data starts with an 8-byte discriminator (first 8 bytes of sha256("global:<snake_case_name>")); account data starts with sha256("account:<Name>")[0..8]; events use sha256("event:<Name>")[0..8]. Events reach you by one of two routes: `emit!` writes a base64 "Program data:" log line; `emit_cpi!` makes a self-CPI whose instruction data is `e445a52e51cb9a1d` (the event-instruction tag) + the 8-byte event discriminator + Borsh payload, visible only in inner instructions. Among the target programs, pump.fun, PumpSwap, Meteora DLMM, DAMM v2 and DBC use CPI events; Raydium CPMM, Raydium CLMM and Orca Whirlpool use log events; Raydium AMM v4 is not Anchor at all (u8 instruction tags, base64 "ray_log" logs). The same instruction name gives the same discriminator in every program (swap = f8c69e91e17587c8 in six programs), so always key decoding by (programId, discriminator).

### Cited Findings
**Rules**
- Instruction discriminator = "the first 8 bytes of the Sha256 hash of the prefix `global` plus the instruction name"; example sha256("global:initialize") -> [175,175,109,31,13,152,155,237] — [Anchor docs: IDL](https://www.anchor-lang.com/docs/basics/idl)
- Event discriminator default is generated by `gen_discriminator("event", event_name)`; the `#[event(discriminator = ...)]` attribute can override it with a custom constant — [Anchor source: event attribute](https://raw.githubusercontent.com/coral-xyz/anchor/master/lang/attribute/event/src/lib.rs)
- `EVENT_IX_TAG: u64 = 0x1d9acb512ea545e4` with comment "Sha256(anchor:event)[..8]"; `EVENT_IX_TAG_LE` is its little-endian bytes (e4 45 a5 2e 51 cb 9a 1d). I recomputed sha256("anchor:event")[0..8] = 1d9acb512ea545e4 (matches) — [Anchor source: event.rs](https://raw.githubusercontent.com/coral-xyz/anchor/master/lang/src/event.rs)
- `emit!()` writes the event with the `sol_log_data()` syscall; base64-encoded, prefixed `Program Data:`; page warns "data providers may truncate logs"; `emit_cpi!()` emits through a CPI to the program itself, needs the `event-cpi` feature, and the page says CPI instruction data is less likely to be truncated but costs compute. Client example for CPI events: take `innerInstructions[0].instructions[0].data`, base58-decode, drop the first 8 bytes, then decode with the events coder; the page also says CPI event data "cannot be directly subscribed to" so a client must fetch the full transaction — [Anchor docs: events](https://www.anchor-lang.com/docs/features/events)
- Accounts get a CPI-event signature: IDLs show `event_authority` (a PDA with seed `__event_authority`) and `program` accounts on every instruction that emits CPI events. Counting `event_authority` in each IDL's instruction account lists (my script, IDLs above): pump 53/56 instructions, pump_amm 37/38, DLMM 55/76, DAMM v2 33/39, DBC 20/26 (all swap-like instructions included); Raydium CPMM 0/14, CLMM 0/34, DAMM v1 2/30 (neither of the two is a swap or liquidity instruction) — [pump IDL](https://raw.githubusercontent.com/pump-fun/pump-public-docs/main/idl/pump.json), [pump_amm IDL](https://raw.githubusercontent.com/pump-fun/pump-public-docs/main/idl/pump_amm.json), [DLMM IDL](https://raw.githubusercontent.com/MeteoraAg/dlmm-sdk/main/idls/dlmm.json), [DAMM v2 IDL](https://raw.githubusercontent.com/MeteoraAg/dynamic-bonding-curve/main/idls/damm_v2.json), [DBC IDL](https://raw.githubusercontent.com/MeteoraAg/dynamic-bonding-curve/main/scripts/idl/release_0.1.6.json), [CPMM IDL](https://raw.githubusercontent.com/raydium-io/raydium-idl/master/raydium_cpmm/raydium_cp_swap.json), [CLMM IDL](https://raw.githubusercontent.com/raydium-io/raydium-idl/master/raydium_clmm/raydium_clmm.json), [DAMM v1 IDL](https://raw.githubusercontent.com/MeteoraAg/damm-v1-sdk/main/ts-client/src/amm/idl.json)

### Inferences
- A decoder keyed on a global `Map<discriminatorHex, name>` would be wrong: swap/deposit/withdraw/buy/sell/create_pool/remove_liquidity collide across programs. Key on `${programId}:${hex}`; for inner instructions use the inner instruction's own `programIdIndex`.
- To decode a CPI event from inner instructions: match inner instruction with `programId == the emitting program` AND `data[0..8] == e445a52e51cb9a1d`-tag bytes (`e4 45 a5 2e 51 cb 9a 1d`), then `data[8..16]` = event discriminator, `data[16..]` = Borsh payload. This follows from the Anchor docs' "drop first 8 bytes then decode" example plus the EVENT_IX_TAG constant; the earlier GodsEye note's report that PumpSwap inner-instruction event discriminators are 16 bytes (sol-shred-sdk) is consistent. Also check the accounts list contains the program's `event_authority` PDA to avoid false matches.
- To decode a log event: scan `meta.logMessages` for lines starting `Program data: ` (Anchor docs spell it `Program Data:`; real runtime lines are `Program data: <base64>`, a detail from general knowledge, so match case-insensitively), base64-decode, compare first 8 bytes against the event discriminator. Attribute the line to a program using the surrounding `Program <id> invoke [n]` / `success` lines, as the log does not name the emitter.
- Log-event programs (Raydium CPMM/CLMM, Whirlpool, DAMM v1) are the ones that break if your provider truncates logs; CPI-event programs do not. For a copy bot, PumpSwap/pump.fun/DLMM/DAMM v2/DBC events are therefore the more reliable ones, but they only appear in `innerInstructions`, so make sure the transaction subscription returns inner instructions (the Yellowstone transaction meta is the standard `TransactionStatusMeta`, which includes them; see Q3 gaps).
- Highest-value fields per program for the stated goal: pump `TradeEvent` (is_buy, user, sol_amount, token_amount, reserves, fee, creator_fee, quote_mint) plus `CompleteEvent`/`CompletePumpAmmMigrationEvent` for graduation; PumpSwap `BuyEvent/SellEvent` (post-trade pool reserves, fees, `virtual_quote_reserves`), `CreatePoolEvent`, `DepositEvent/WithdrawEvent`; CPMM `SwapEvent` (includes vault balances before and transfer fees) and `LpChangeEvent`; CLMM `SwapEvent` (post sqrt price, liquidity, tick); Whirlpool `Traded`/`LiquidityIncreased/Decreased`; DLMM `Swap/Swap2Evt`, `AddLiquidity/RemoveLiquidity`; DAMM v2 `EvtSwap2` and `EvtLiquidityChange` (the only AMM event with post-trade `reserve_a/b_amount` AND owner); DBC `EvtSwap2` (includes `quote_reserve_amount` and `migration_threshold` = curve progress).
- Treat pump `buy`/`sell` (v1) as live: the README says existing instructions keep working, so a decoder needs v1, v2 and v3 layouts of the same logical operation.

## 2. Jupiter v6 routes: route plan, SwapEvent, per-hop pools and amounts; top-level vs inner instructions

### Takeaway
A Jupiter v6 route's instruction data holds the route plan (a Vec of steps: `Swap` enum variant naming the AMM type + percent + input_index + output_index), `in_amount`, `quoted_out_amount`, slippage and platform fee, but NOT pool addresses; pool addresses live in the remaining accounts, and the actual AMM calls are inner instructions (CPIs) of the Jupiter instruction. Each hop also emits a Jupiter `SwapEvent {amm, input_mint, input_amount, output_mint, output_amount}` as a CPI event, which is the cleanest per-hop (pool, amounts) record. The only IDL I could read is old (39 `Swap` variants; no `route_v2`), so newer Jupiter instruction families are unverified.

### Cited Findings
- The jupiter-cpi repo IDL (version 0.1.0, camelCase names) lists `route` (e517cb977ae3ad2a), `routeWithTokenLedger` (96564774a75d0e68), `sharedAccountsRoute` (c1209b3341d69c81), `sharedAccountsRouteWithTokenLedger` (e6798f50779f6aaa), `sharedAccountsExactOutRoute` (b0d169a89a7d453e); I computed these as sha256("global:<snake_name>"). ### Inferences
- **Why detectVenue must look at inner instructions.** The transaction's top-level instruction list only contains programs the signer called directly: Jupiter, a trading-bot router, a Jito tip transfer, ComputeBudget. Every AMM call a router makes is a CPI recorded only in `meta.innerInstructions[index]`. A top-level-only detector labels a routed trade "jupiter" (loses the venue/pool) and labels a bot-routed trade as "unknown". For hop-level accounting you also need `stackHeight` (the AMM call is one level below the router; the AMM's own self-CPI event and token transfers are one level deeper), and the inner-instruction `index` to tell which top-level route produced it when a transaction has several routes.
- **Per-hop (pool, amounts) from a Jupiter transaction, in order of reliability:** (1) the Jupiter `SwapEvent`s among that route's inner instructions (`amm`, input/output mint and amount per hop; `amm` should be the pool/market account for most AMMs, unverified for all of them); (2) the child AMM instruction under the route with its program ID and pool account (use that program's decoder; pool is a named account); (3) the inner SPL token `transfer`/`transferChecked` instructions beneath each AMM call (source/destination token accounts, amounts; identifies vaults). Multi-hop shape: consecutive SwapEvents chain (hop n's output mint = hop n+1's input mint); split routes share the same input mint with `percent` summing to 100 in the plan.
- **Instruction-data-only route plan** tells you which AMM types are used (variant names) and the split percentages but is not enough for pool addresses, and variant order changes as Jupiter adds AMMs (39 variants in the stale IDL vs many more live), so decoding it needs the on-chain IDL of that date. Prefer events/inner instructions; use the route plan only for `in_amount`, `quoted_out_amount`, `slippage_bps`, `platform_fee_bps`.
- The new-instruction-family hazard: Jupiter has to keep adding instruction variants; I computed discriminators for plausible `route_v2` (bb64facc31c4af14), `shared_accounts_route_v2` (d19853937cfed8e9), `exact_out_route_v2` (9d8ab85215f4f324) but have no evidence these exist. A defensive decoder should treat any instruction whose program is Jupiter and whose discriminator is unknown as "route-like", fall back to inner-instruction/event decoding, and log the discriminator for review.
- Treat "balance-delta says wallet swapped X for Y" as truth for the wallet, and use events/inner instructions only to attribute venues and pools; do not require the route plan to parse correctly.

### Gaps
- No readable current Jupiter v6 IDL or official docs page for the on-chain program (`docs.jup.ag/notes/on-chain-program` returned 404; Helius lists only `route`, `shared_accounts_route`, `exact_out_route`). ## 3. Balance deltas versus instruction decoding for amounts; a robust hybrid

### Takeaway
Balance deltas (pre/post token balances + lamport balances, per owner and mint) are the only venue-agnostic ground truth for "who got what", but they mis-state price when fees, tips, rent, wSOL wrapping, Token-2022 transfer fees or multi-hop intermediate accounts are involved, and they cannot tell you which pool or what kind of action it was. Instruction/event decoding gives exact pool, direction, fees and post-trade reserves but is brittle to program upgrades (pump had v1, v2, v3 layouts in 2026) and silent when the program or variant is unknown. Use both: deltas for amounts, decoding for attribution and cross-checks, and flag disagreement.

### Cited Findings
- `getTransaction` meta provides `preBalances/postBalances` indexed to `accountKeys`, `pre/postTokenBalances` with `accountIndex`, `mint`, `owner`, `programId` (the last two "may be omitted"), `fee`, `err`, `loadedAddresses {writable, readonly}` (docs do not say how they combine with static keys) and `innerInstructions` — [Solana docs: getTransaction](https://solana.com/docs/rpc/http/gettransaction)
- Token-2022 TransferFee: the fee is withheld on the destination token account, so the recipient receives the amount minus the fee; fee = basis points with a maximum; fee changes take effect two epochs later — [Solana docs: transfer fees](https://solana.com/docs/tokens/extensions/transfer-fees)
- Programs expose transfer-fee-aware amounts in their events, evidence that "amount sent" and "amount received" differ: CPMM `SwapEvent` has input_transfer_fee/output_transfer_fee; CLMM `SwapEvent` has transfer_fee_0/1; Whirlpool `Traded` has input/output_transfer_fee; DAMM v2 `EvtLiquidityChange` has transfer_fee_included amounts and `EvtSwap2` has included/excluded_transfer_fee amounts — IDLs/sources cited in Q1.
- pump.fun SOL-paired bonding curves trade in native SOL ("Trading and transfer will continue to happen with native SOL"), and in `multi_hop_swap` a SOL-curve hop takes lamports from the user wallet while a wrapped-SOL ATA is passed "read for its mint only"; PumpSwap pool hops move wrapped SOL — so wSOL token-balance changes alone miss the curve leg — [pump-public-docs README](https://raw.githubusercontent.com/pump-fun/pump-public-docs/main/README.md), [Multi-hop swap doc](https://raw.githubusercontent.com/pump-fun/pump-public-docs/main/docs/instructions/MULTI_HOP_SWAP.md)
- New pump fee model: new trade instructions keep protocol and creator fees on the curve/pool (paid later by permissionless `sweep_*`); `virtual_quote_reserves` can be negative because fees kept in a pool are subtracted from it — [pump-public-docs README](https://raw.githubusercontent.com/pump-fun/pump-public-docs/main/README.md)
- Pump `TradeEvent` carries both `sol_amount` and `fee`/`creator_fee`/`holder_rewards`/`buyback_fee` fields, and PumpSwap `BuyEvent` has `quote_amount_in`, `lp_fee`, `protocol_fee`, `user_quote_amount_in`, so fees are separable only via events (IDL fields above).
- The existing GodsEye parse is delta-based and already handles routed SOL hops by looking for the biggest drop and rise among non-wallet accounts — `/Users/srinjoydas/GodsEye/agent/src/chain/parse.ts:116-135` (`routedSolLamports`); `ParsedSwap` records `jitoTip`, `feeLamports` — `parse.ts:62-95`.
- Yellowstone's transaction update includes `index` (position in the block) next to `signature`, `is_vote`, `transaction` and `meta` — [geyser.proto](https://raw.githubusercontent.com/rpcpool/yellowstone-grpc/master/yellowstone-grpc-proto/proto/geyser.proto). This closes the gap noted in `build_your_own_map.md` ("could not confirm that the Yellowstone transaction update exposes a block-position index").
- Since the Alpenglow/Agave 4.3 change, a `processed` subscriber "can ... get two blocks for one slot, told apart by `bank_id`" when a duplicate block is replaced — [Yellowstone CHANGELOG](https://raw.githubusercontent.com/rpcpool/yellowstone-grpc/master/CHANGELOG.md); the realtime note says to dedupe on signature/blockhash, not slot.

### Inferences
**Failure modes of pure delta parsing** (from the facts above plus Solana mechanics I know but did not source):
- *Fees and rent*: signer's lamport delta includes the base fee (`meta.fee`), priority fee, Jito tip (system transfer to a tip account), ATA rent on create/close, and wSOL account create/close; strip them or SOL-side price is wrong. GodsEye tracks `feeLamports`/`jitoTip`; add rent from account-creation inner instructions.
- *wSOL*: wrapped SOL is lamports in a token account; same-mint wSOL deltas appear in token balances, but native SOL curve legs (pump SOL-paired curves) appear only in lamport balances; `closeAccount` moves the wSOL lamports to the owner and shows as a lamport credit with a token-balance disappearance.
- *Token-2022 transfer fee*: wallet receives amount minus fee; delta is right for "what I got", but quoted price from the pool side is off unless you add the fee back (events expose it).
- *Multi-hop / aggregator*: intermediate token accounts net to zero; a delta parser gets the signer's net in/out right but cannot say which pools; splits across pools and fee-on-transfer tokens blur per-hop prices.
- *Fee accounts and referral/platform fees*: Jupiter `platformFeeBps` account and pump protocol/creator fee accounts take a cut from input or output; the wallet delta is net of it (arguably what you want), but "price" is fee-inclusive.
- *Owner field omitted*: `owner` in token balances "may be omitted" (docs), so map token account -> owner via account keys + prior state when missing.
- *ALT resolution*: indices in `accountIndex` refer to the combined key list; static keys, then loaded writable, then loaded readonly (my knowledge of the Solana message format; the getTransaction docs fetched do not state the order, and I did not read the Yellowstone/ConfirmedBlock proto that defines the meta fields).
- *Multiple signers / same wallet twice / failed tx*: skip `meta.err != null`; separate owners per signer; bundle siblings must not be merged.
- *Authority not wallet*: some swaps are executed by a program-derived or delegate authority (copy-trading wallets, bots with relayers); attribute by token-account owner, not by fee payer.

**Failure modes of pure instruction decoding:** discriminator collisions across programs (Q1), layout churn (pump create_v2/buy_v3, DBC transfer-hook variants, DLMM `*2` variants), partial coverage (a decoder generated from an old IDL silently misses new instructions: see Q6, Carbon), events missing when logs are truncated (log-event programs), CPI events missing if inner instructions are not returned, and events only covering the logical swap, not the user's token-account owner/ATA reality.

**Robust hybrid (recommended pipeline):**
1. Resolve the account key list (static + loaded) once; build `ownerOf[tokenAccountIndex]` from pre/post token balances; compute per-(owner, mint) deltas and per-owner lamport deltas, with fee/tip/rent adjustments. Mark the wallet's net legs as the ground truth for amount in / amount out.
2. Walk top-level and inner instructions in order with (program ID, discriminator) -> decoder; record each recognised action (swap, add/remove liquidity, create pool, migrate, fee claim) with the named pool account, plus decoded CPI/log events with their program attribution.
3. Reconcile: for each decoded swap event, check `event.amount_in ≈ wallet delta in (+ transfer fee + fees)` within tolerance; on mismatch, keep the delta and set `confidence = low`. For unknown programs that move tokens, produce a generic "unclassified token movement" record rather than dropping.
4. Use event fields for what deltas cannot give: pool address, direction, fee split, post-trade reserves, curve progress, creator.
5. Dedupe on signature; keep `(slot, bank_id, index)` for ordering; ignore failed transactions at the filter (`failed:false`).

### Gaps
- Exact ordering of `loadedAddresses` relative to static keys and how Yellowstone's `TransactionStatusMeta` populates `loaded_writable_addresses`/`loaded_readonly_addresses`: not read in primary sources this run (the `geyser.proto` imports the ConfirmedBlock `Transaction`/`TransactionStatusMeta` messages, which I did not open).
- No published benchmark of delta-parser accuracy vs event decoding for Solana swaps was found.
- Whether pump's `TradeEvent.sol_amount` includes or excludes fees under v3 not documented in the pieces read.

## 4. Telling liquidity add/remove from swaps and transfers; real-time LP-removal detection over gRPC; Yellowstone filter semantics and cost

### Takeaway
Classify by (programId, instruction discriminator) first (instruction names are unambiguous: withdraw/remove_liquidity/decrease_liquidity vs swap), confirm with the program event (`WithdrawEvent`, `LpChangeEvent`, `RemoveLiquidity`, `EvtLiquidityChange`, `DecreaseLiquidityEvent`, `LiquidityDecreased`, `ray_log` type 2) and with token deltas (both pool vaults decrease, user receives both tokens, LP mint supply falls for LP-token pools; for position-based CLMM/DLMM/DAMM v2 positions the position NFT/account changes instead of an LP mint). For real-time detection on a held token, the cheapest accurate signals are (a) account updates on the LP mint (touched only by deposits/withdrawals) for LP-token AMMs, and (b) a transaction subscription whose `account_include` holds the pool addresses of held tokens, decoded locally; vault account subscriptions are cheap per message but fire on every swap and cannot say who or why. Bandwidth in absolute terms is not published; measure on the existing stream.

### Cited Findings

**Yellowstone filter semantics (primary: proto + Triton docs)**
- `SubscribeRequest` has maps `accounts`, `slots`, `transactions`, `transactions_status`, `blocks`, `blocks_meta`, `entry`, `block_footer`, plus `commitment`, `accounts_data_slice` (list of {offset, length}), `ping`, `from_slot` — [geyser.proto](https://raw.githubusercontent.com/rpcpool/yellowstone-grpc/master/yellowstone-grpc-proto/proto/geyser.proto)
- Account filter `SubscribeRequestFilterAccounts`: `account` (pubkeys), `owner` (program owners), `filters` (memcmp {offset, bytes/base58/base64}, datasize, token_account_state, lamports), `nonempty_txn_signature`, `cuckoo_accounts_filter`; account update `SubscribeUpdateAccountInfo` carries pubkey, lamports, owner, data, write_version and `txn_signature` (so an account write can be joined to its transaction) — same proto
- Transaction filter: `vote`, `failed`, `signature`, `account_include`, `account_exclude`, `account_required`, `cuckoo_account_include`, and an ATA/token-account expansion flag `token_accounts` (ALL: match an owner if it owns a pre OR post token balance; BALANCE_CHANGED: only owners whose token balance changed or whose account was closed) — same proto (present on master; I did not find it in the changelog grep, so release status is unconfirmed)
- Triton: "if all fields are empty, then all transactions are broadcasted. Otherwise, fields work as logical AND, and values in arrays as logical OR"; `account_data_slice` example: instead of all 165 bytes of a token account "we receive only 40 bytes" (offset 32, length 40); default commitment processed; confirmed/finalized are buffered server-side, Triton recommends client-side handling; "You will receive all the transaction notifications or account write notifications for the slot" before that slot's confirmed/finalized notification; some finalized notifications are not issued; the page does not specify ordering between account updates and transactions in a slot, nor `account_required`/`datasize` semantics for the standard stream — [Triton docs: Dragon's Mouth subscriptions](https://docs.triton.one/project-yellowstone/dragons-mouth-grpc-subscriptions)
- Cuckoo filters let a client send thousands of addresses compactly: Triton quotes roughly 3 MB vs 64 MB on the wire for a 2M-account filter (same page); the earlier realtime note covers the ~1% false-positive rule and provider limits.
- Alpenglow-era changes: the server may deliver two Processed blocks for a slot distinguished by `bank_id`; `Confirmed`/`Finalized` once per slot — [Yellowstone CHANGELOG](https://raw.githubusercontent.com/rpcpool/yellowstone-grpc/master/CHANGELOG.md)
- `getProgramAccounts` (for cold starts): up to 4 filters, ALL must match; memcmp decoded data limited to 128 bytes; dataSize, tokenAccountState and dataSlice supported — [Solana docs: getProgramAccounts](https://solana.com/docs/rpc/http/getprogramaccounts)

### Inferences
**Distinguishing from swaps and from plain transfers**
- *Swap*: one pool vault gains the input mint while the other loses the output mint; reserve ratio (price) moves; LP supply and positions unchanged.
- *Liquidity remove (LP-token pools: Raydium AMM v4, CPMM, PumpSwap, DAMM v1)*: both vaults decrease together (price roughly unchanged), LP mint supply decreases (burn instruction among the inner instructions), user receives both tokens. *Liquidity add*: both vaults increase, LP mint supply increases (mint). For concentrated/position-based pools (CLMM, Whirlpool, DLMM, DAMM v2) there is no LP-token supply to watch; look at the position account/NFT change and the `Decrease*`/`RemoveLiquidity`/`EvtLiquidityChange` event, and the pool-level `liquidity` field.
- *Plain transfer*: a bare SPL/System transfer touching a pool vault (donation, "sync" misuse) changes a vault balance without any pool-program instruction; classify by the absence of a recognised pool-program instruction in the transaction. Note a PumpSwap/Raydium pool can have vault balance moved by a direct transfer, so reserve-based price must come from the pool's own accounting where the program separates them (CLMM/DLMM store reserves/liquidity themselves; check per program).
- The ratio test is cheap in code: compute Δbase/Δquote in vault deltas; |Δ| both negative and the ratio ≈ the pool ratio => removal; one side only or opposite signs => swap.
- Rug-relevant: for pump/PumpSwap-canonical pools LP is burned at migration (secondary sources), so classic "pull the LP" is structurally not available there; the live LP-removal risk sits on non-canonical pools (Raydium AMM v4/CPMM pools created by the dev, DAMM v1/v2, DLMM pools, Whirlpool) and creator-fee/sweep flows on pump.

**Real-time LP-removal detection on a held token: options and cost model** (no source gives msgs/sec or GB/day; formulas, not measurements)
1. *Transaction filter on pool addresses* (`account_include` = pool/vault-authority addresses for your held tokens, `vote:false`, `failed:false`): exact semantics (OR over addresses, AND across fields), returns full transactions with meta/inner instructions so you can decode the instruction and event and see who removed what. Cost = (messages per second touching those pools) × (transaction size incl. meta, typically several KB because of logs and balances); swaps on the pool are included, so a hot pool costs far more than a quiet one. Cheap for tens of held tokens; filter list can use the cuckoo filter at scale.
2. *Account subscription on the LP mint* (LP-token pools only): the mint account is only written when LP supply changes (mint/burn), i.e. on add/withdraw, not on swaps. With a data slice on the `supply` field the message is tiny. Detects every remove, including by wallets unknown to you; then fetch/decode the transaction via `txn_signature` (account update field) or a parallel transaction filter. (Mint layout facts: supply is a u64 at offset 36 of an SPL Mint, after the 36-byte `COption<Pubkey>` mint authority; general SPL knowledge, not sourced here.)
3. *Account subscription on pool vault token accounts* with a data slice on `amount` (offset 64, length 8 in the SPL token account layout, again general knowledge; Triton's example uses offset 32/length 40 to read owner+amount). Messages fire on every swap into/out of the pool, so message count ≈ swap count, but each is a few dozen bytes plus the fixed protobuf envelope. Detect removal by "both vault balances drop > x% in one write (or in one tx) without a corresponding price move". Gives no actor, no instruction name; ambiguous with big sells unless you check both sides. `txn_signature` in the update lets you pull the transaction to confirm.
4. *Account subscription on the pool account* (for CLMM/DLMM/DAMM v2/Whirlpool pools): the pool state holds liquidity, price and (DAMM v2/DLMM) reserves; written every swap; a data slice of the liquidity field halves the bytes but not the message count.
5. *Program-wide transaction stream, decode locally*: highest bandwidth (all swaps of all pools of the program), only justified if you also need market context. The realtime note already warns this is the metered-bandwidth cliff.
- Recommended combination for a bot that holds a small set of tokens: (2) for LP-token pools + (1) for the pools of held tokens, with the pool list refreshed by re-sending the whole `SubscribeRequest` (a new request replaces the old one, per the realtime note), and a periodic reconcile via `getMultipleAccounts` on vaults to catch missed updates.
- Commitment: use `processed` for the alert (early), but confirm before acting irreversibly; with 200 ms slots and the Alpenglow bank_id behaviour, key decisions on `(signature)` and tolerate a replaced bank.
- Ordering: within a slot you get all transaction notifications for the slot before the slot's confirmed status; the docs do not guarantee account-update vs transaction order, so join them by `txn_signature`/signature, not by arrival order.

**Measuring cost:** the user's stream already filters program-wide transactions for six venues (`stream.ts:127-134`). Instrument it to log messages/s and bytes/s per program and per message type for one day; that gives the real numbers for options 1 and 5, and a count of account-write-per-swap ratio for option 3.

### Gaps
- No source quantifies messages/sec or GB/day for pump.fun, PumpSwap, Raydium, Meteora or Orca streams (search found only a Chainstack stream-count pricing and a Bitquery 1.05M trades count): bandwidth must be measured.
- Whether Yellowstone sends an initial snapshot of matching accounts on subscribe, and exact datasize/memcmp AND semantics for account filters, is not on the Triton page; the proto defines the fields only.

## 5. Tracking pool state and finding all pools of a token

### Takeaway
Keep reserves current by subscribing to the pool's vault token accounts (or the pool/curve account, which for pump and DAMM v2/DLMM stores reserves or liquidity directly) and by seeding with `getMultipleAccounts`; update from event post-trade reserves for free when the event carries them (PumpSwap `Buy/SellEvent`, CPMM `SwapEvent` vault-before, DAMM v2 `EvtSwap2`/`EvtLiquidityChange`, pump `TradeEvent`). To find all pools of a token, derive the deterministic PDAs where the program allows (pump bonding curve, PumpSwap canonical pool) and use `getProgramAccounts` with memcmp on the mint offsets for the rest; aggregators (GeckoTerminal, DexScreener) are quicker but rate-limited and delayed.

### Inferences
- **Maintaining reserves, ordered by freshness/cost**: (a) events embedded in transactions you already receive (zero extra cost, event-time exact, includes fee/transfer-fee effects); (b) account subscription on the two vault token accounts (`account` filter with their pubkeys, `accounts_data_slice` offset 64 length 8), joined with `txn_signature`; (c) account subscription on the pool/curve account for the programs that store reserves there (pump BondingCurve: `virtual_*`/`real_*` reserves; DBC `VirtualPool`; DAMM v2 `Pool`; Whirlpool/CLMM price+liquidity); (d) polling `getMultipleAccounts` (one call for up to 100 accounts) as the reconciler/seed. Seed once, then apply updates in `(slot, write_version)` order and discard older ones; resync on a `bank_id` replacement or reconnect.
- **PumpSwap price correctness**: use effective quote reserves = quote vault amount + `virtual_quote_reserves` (signed). For pump curves use virtual reserves for price and `real_*` for the progress/liquidity; for DBC use `quote_reserve_amount` / `migration_threshold` from `EvtSwap2`.
- **Token -> pools discovery (precision vs cost)**:
  1. *Deterministic, zero RPC*: pump bonding curve PDA from the mint; PumpSwap canonical pool PDA (index 0, creator = pump pool authority, base_mint = mint, quote_mint = wSOL); for Raydium CPMM/CLMM the PDA includes `amm_config` (several configs per program) and the mint order, so enumerating all configs is needed; Whirlpool PDAs include tick spacing and config. Worth caching a table of known configs.
  2. *Stream-derived*: record every `CreatePoolEvent`/`PoolCreatedEvent`/`LbPairCreate`/`EvtInitializePool`/`Initialize2` seen on the stream into a `pools` table keyed by mint. This catches all new pools going forward at no extra cost (the user's stream already sees them) and is the primary method for a copy bot; it misses pools created before the stream started.
  3. *Backfill by getProgramAccounts*, one call per program per mint: memcmp on the mint offset (and optionally on the quote mint) with `dataSlice` of a few bytes/`dataSize` to keep payloads small: PumpSwap base_mint@43 (+quote@75 for the wSOL pair); CPMM token_0_mint@168 and token_1_mint@200 (two calls, mint may be either side); CLMM @73/@105; DLMM @88/@120; DAMM v2 @168/@200; DBC base_mint@136. Raydium AMM v4: coin_vault_mint and pc_vault_mint sit at 400 and 432 if StateData is 144 bytes (my arithmetic from the struct; widely used values I recall, not source-confirmed); a 752-byte `dataSize` filter narrows it (also unverified). That is roughly 2 calls × ~8 programs ≈ 12–16 `getProgramAccounts` per token, 10 credits each on Helius: about 100–200 credits per token, slow (seconds) on public RPC, and unfiltered scans of Raydium AMM v4 are heavy. Do this once per token and cache; do not do it on the hot path.
  4. *Aggregators*: DexScreener `token-pairs` or GeckoTerminal `tokens/{addr}/pools` return pool addresses and USD liquidity in one HTTP call, with 30–60 requests/min free limits and indexing delay for brand-new pools (delay not measured): good for enrichment, not for completeness (GeckoTerminal returns top-20 per its guide). Use them to pre-filter which pools are worth subscribing to by liquidity.
- **Which pools matter**: a token usually has one dominant pool; subscribe to the top 1–3 by liquidity and fall back to the stream-derived table for the rest. A pool-creation event for a held token is itself an alert (new venue, migration, or fresh liquidity under a different config).

## 6. Open-source decoders and tooling: Carbon, solana-dex-parser, Shyft/Helius, Anchor coder, Codama

### Takeaway
There is no single maintained TypeScript library that decodes all of these programs at today's layouts. The best fits: (1) Codama/Anchor-IDL-generated clients (code-gen from the IDLs above; dependency-light with `@solana/kit` codecs, MIT) for the instruction/event/account layouts, plus your own thin dispatcher on (programId, discriminator); (2) Carbon (Rust, MIT, active, 60+ decoders including every target program) if you accept Rust, but its pre-built decoders lag the newest pump/PumpSwap instructions; (3) solana-dex-parser (TypeScript, MIT, wide coverage, but last release 2025-10 and built on `@solana/web3.js`) as a reference for balance-delta/route handling, not as the source of truth for 2026 layouts.

### Inferences
- **Fit to a TypeScript codebase without heavy dependencies**: the lightest robust path is IDL-driven code generation. Take the IDLs in Q1 (pin them in-repo with a date), generate Codama TypeScript clients (or hand-write small Borsh decoders: swap events are 5–15 fields) and write one dispatcher table `programId -> {discriminatorHex -> decoder}`. Runtime deps then reduce to `@solana/codecs` (or `@noble/hashes` + a tiny Borsh reader) and your gRPC client. Avoid shipping `@coral-xyz/anchor` (13 deps, web3.js) or vendor SDKs (express in the DLMM SDK; GPL-3.0 in the Raydium SDK) as parsing dependencies; use them only offline (fixtures, quoting).
- **Carbon** is the best-engineered full pipeline (Yellowstone datasource, reconnect, instruction + CPI event decoding, accounts), and the decoders are code-generated so refreshing from a newer IDL is a CLI run; but a Rust process in a TS bot's architecture means a sidecar or rewrite, and stock decoders trail the fastest-moving program (pump). If adopted, regenerate pumpfun and pump-swap decoders from the October IDLs before use.
- **solana-dex-parser** is useful as a reference for trade/liquidity output shape and bot-router handling, but its last release (Oct 2025) predates pump v2/v3/multi-hop, the `*2` Meteora variants and PumpSwap negative virtual reserves; I did not read its source (so cannot judge quality). Do not rely on it for 2026 layouts without testing against recent transactions.
- **Shyft's LGPL parser** is Anchor-IDL-driven (needs IDLs anyway) and was last published May 2025; Helius Parsed Streams is the managed alternative (per-event cost) and shares the "unindexed version -> decoded null" failure mode.
- **Test strategy**: for each program, keep 3–5 fixture transactions per instruction variant (captured from your gRPC stream), and a canary that logs any (programId, discriminator) seen in a venue-program transaction that is not in your decoder table, so layout changes are detected the day they ship.
- **Maintenance reality**: the programs' own IDL repos (pump-public-docs, raydium-idl, dlmm-sdk, dynamic-bonding-curve) are the primary source of truth but are not always current (DBC IDL behind its source; Jupiter's public IDL is stale). Pin by program deployment slot/`upgrade authority` events where possible and re-diff IDLs weekly.

## 7. Putting it together: a decoder layer that answers "which pools/programs, what action, who got what, pool state after"

### Takeaway
One pass per transaction: (1) normalise (account keys incl. ALTs, ownership map, inner instructions grouped by top-level index with stack heights, logs), (2) dispatch every instruction and event by (programId, discriminator), (3) compute wallet deltas, (4) reconcile and emit typed `PoolAction` records plus a per-pool state patch. Everything the four questions need is available in the transaction itself except cold-start reserves for pools you have not seen.

### Cited Findings
- All facts supporting this design are cited in Q1–Q6. Specific building blocks verified: discriminator tables and event layouts (Q1), Jupiter route plan/events/inner instructions (Q2), meta fields (Q3), Yellowstone transaction update fields including `index` and the filters (Q4), PDA/offset data (Q5), tool coverage (Q6).

### Inferences
Suggested record shape (my design):
- `TxDecoded { signature, slot, bankId?, index, signer, programs: Set<programId>, venue, actions: PoolAction[], walletDeltas: Map<owner, Map<mint, bigint>>, lamportDeltas, fee, tip, confidence }`.
- `PoolAction { kind: swap | add_liquidity | remove_liquidity | create_pool | migrate | fee_claim | curve_create | transfer | unknown, program, instruction, pool, mints, amountsIn/Out (from event if present, else from deltas), actor, route?: {hopIndex, pool, in, out}[], postState?: {reserveA, reserveB, price?, liquidity?, sqrtPrice?, virtualQuote? } }`.
- Pipeline: group inner instructions by `index`; for each top-level instruction create a tree by `stackHeight`; decode each node with its program's decoder; attach CPI events found among the descendants of the AMM call that emitted them; attach log events by scanning `Program data:` lines between the AMM's `invoke`/`success` markers; compute `walletDeltas`; reconcile (Q3); update a `PoolState` store keyed by pool address from `postState` fields.
- Venue/program list to cover first (by order of relevance to a memecoin copy bot): pump (v1/v2/v3 buy/sell/create/create_v2/migrate/migrate_v2 + TradeEvent/CreateEvent/CompleteEvent/CompletePumpAmmMigrationEvent), PumpSwap (buy/sell v1/v2, create_pool, deposit, withdraw, multi_hop_swap + Buy/Sell/CreatePool/Deposit/Withdraw events), Raydium AMM v4 (tags 1/3/4/9/11/16/17 + ray_log), CPMM, CLMM, LaunchLab, Whirlpool, DLMM, DAMM v2, DAMM v1, DBC, Jupiter, and a generic fallback.
- Add to `VENUES`/labels: Raydium LaunchLab `LanMV9sAd7wArD4vJFi2qDdfnVhFxYSUg6eADduJ3uj`; keep DBC/DAMM v2 label-only per the existing comment about farm wallets.

### Gaps
- No end-to-end implementation was built or tested here; this is a design from the sources above. A live check against a handful of real transactions per program (fetched from your own stream) is the next step and was out of scope (public GET-only research).
