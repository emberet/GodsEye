# Bubble maps can size rug risk, not prove it

**Bottom line.** Yes, a bubble-map style check can rug-screen a token before GodsEye copies a leader, but only as a graded risk input, and only if it runs on chain data inside the existing entry window. A bubble map draws a token's top holders as bubbles sized by balance and links them where on-chain transfers connect them; connected groups are clusters. **No published measurement links cluster or bundle-share buckets to rug rates, on Solana or anywhere else.** The 10%, 20% and 30% cutoffs in circulation are vendor rules of thumb with no stated derivation, and they mean different things depending on how "bundle" is defined (a 36.5% mean in the academic MemeTrans data versus a 10% median in Bitquery's census). The Bubblemaps Data API is real and documented (25 credits per cluster map, 14 chains, "most queries" under 15 s, up to a minute for outliers, no streaming), but its price, its terms and its behaviour on seconds-old pump.fun mints are all unknown. That makes it a poor fit for a 2-10 second entry gate and a reasonable log-only second opinion at +1 and +5 minutes, which is also what the data supports: GodsEye's leaders buy a median 34 s after the pool appears and hold about 10 s, and the replay shows entry drift of 13.4% at 60 s and 21.0% at 120 s, so a delay-and-recheck costs more than a veto can plausibly recover. GodsEye's own holder check reads only 20 token accounts, has no holder-to-holder edges and no service-wallet filter, and returns silent nulls on busy coins, so extending it is justified by code gaps alone. The shadow-log table does not exist in the local database until the agent is restarted, so **no outcome data exists yet and every threshold below is untested**. The design that fits the owner's rules (insider-pattern wallets stay copyable, public site stays read-only and redacted) is to treat cluster information as a per-token size multiplier and exit setting, never a wallet verdict, to measure first, and to put nothing vendor-derived on the public site before a licence check. This report informs a later decision; nothing here is decided.

## A bubble map is a holder graph, and the API's field names mislead

A bubble map shows one token's largest holders as bubbles, with size proportional to the amount held. Two bubbles are linked when an on-chain transfer connects them, and linked groups are coloured as clusters. In the current Bubblemaps app the map holds the top 250 holders, hides contract and exchange bubbles by default, and lets links be filtered by token or dollar value ([Bubblemaps wiki](https://wiki.bubblemaps.io/bubblemaps-v2/how-does-it-work.md)). Premium adds a 1,000-holder map and AI interpretation of clusters ([wiki: Premium](https://wiki.bubblemaps.io/bubblemaps-v2/premium.md)). The API returns 80, 250 or 500 holders ([OpenAPI](https://docs.bubblemaps.io/openapi.json)). Bubblemaps publishes the concepts but no thresholds, time windows or algorithm, so its output cannot be reproduced exactly.

The edge rule is not settled. A 2025 Bubblemaps post says two wallets are linked by at least one historical transfer in the chain's gas token, SOL on Solana ([blog](https://blog.bubblemaps.io/find-deeper-connections-between-wallets/)). The 2026 wiki and API say transfers "can involve any token", grouped by sender, receiver and token, but only for a limited list of "indexed" tokens whose criteria are not given ([API: token model](https://docs.bubblemaps.io/data/api/token-model.md); [API: subgraph](https://docs.bubblemaps.io/data/api/relationships/subgraph.md)). The 2026 docs are the better guide for the API, and the discrepancy suggests the rule changed or the blog is stale. Very busy "supernodes" are kept but two connected supernodes show no link ([API: map](https://docs.bubblemaps.io/data/api/tokens/map.md)).

Three additions are what separate Bubblemaps from a plain "top holders plus first funder" check. **Magic nodes** pull in addresses that hold none of the token but connect holders, such as an address that funds several holders' gas, a deposit address several holders send to, or a wallet that sent everything away ([wiki: Magic Nodes](https://wiki.bubblemaps.io/bubblemaps-v2/magic-nodes.md)). **Time nodes** split exchanges and contracts into one abstract node per time window, so that wallets that touched the same exchange in the same window become linked even with no shared upstream wallet; no window length is defined ([wiki: Time Nodes](https://wiki.bubblemaps.io/bubblemaps-v2/time-nodes.md)). Both are on by default in the API (`use_magic_nodes`, `use_time_nodes`) and, since 2026-09-08 and 2026-10-16, clusters list the magic and time nodes they contain ([changelog](https://docs.bubblemaps.io/data/api/changelog/index.md)). **Fresh wallets** are a separate statistic: supply held by wallets under 10 days old, a coarse proxy that is not "bought in the launch block". Because the exact windows and thresholds are unpublished, a self-built map can imitate the idea but cannot match Bubblemaps cluster for cluster.

Bubblemaps separates two objects that bots often blur. A **bundle** is "a set of wallets that transacted together during the token launch", detected over seconds to minutes; a **cluster** is wallets linked by behaviour over days, weeks or months, such as shared funding or recycled addresses. Its worked examples are a bundle with no cluster (18 wallets buying 0.5-2% each in the first two blocks, 22% together) and a cluster with no bundle (30 wallets funded by one deployer months earlier, 19% together) ([Bubblemaps: Bundle vs Cluster](https://blog.bubblemaps.io/whats-the-difference-between-bundle-cluster-2/)). It also says organic clusters exist, for example friends withdrawing from the same exchange, and that a link shows a transfer happened, not why.

The API field names are where this goes wrong. The table lists the fields a copy-bot would be tempted to use, with what the docs say they are.

| API field | What it is, per the docs | Trap |
|---|---|---|
| `supply_stats.bundles` | "Total supply held by the 10 largest clusters", standalone holders excluded | **Not a launch bundle.** It is a structural cluster concentration; no launch-window bundle field exists in the spec |
| `supply_stats.fresh_wallets` | Supply held by wallets under 10 days old | Coarse proxy for fresh funding, not launch-block buying |
| `supply_stats.top_10_adjusted` | Supply held by the 10 largest entities (holders or clusters), ignoring CEXs, DEXs and similar | Entity-level, so it differs from a raw top-10 wallet share |
| `scores.bubblemaps_score` | 0 (less decentralized) to 100 (more decentralized); `null` on rare occasions | Weights unpublished; it only reflects what Bubblemaps detects; higher is safer, the reverse of a risk score |
| `clusters[].share`, `holder_count`, `holders`, `magic_nodes`, `time_nodes` | Cluster share of supply and membership | Unstated whether `share` excludes CEX, LP or curve balances |

Sources: [API: metrics](https://docs.bubblemaps.io/data/api/tokens/metrics.md) and [OpenAPI](https://docs.bubblemaps.io/openapi.json). Several old names are gone, which matters for any code or notes written earlier: `decentralization_score`, `identified_supply` and `token_stats` were removed on 2026-09-08 (use `metrics.scores.bubblemaps_score`, `metrics.supply_stats`, `stats`), along with the legacy `/chains` and `/maps` paths ([changelog 2026-09-08](https://docs.bubblemaps.io/data/api/changelog/2026-09-08.md)). The earlier GodsEye tooling note's short Bubblemaps section should be read as superseded by this one. Bubblemaps' own guide also states the limits that apply to any bubble map: on-chain only, blind to contract backdoors and off-chain shilling, and a well-distributed token can still have a liquidity lock expiring soon ([Bubblemaps: rug-pull guide](https://blog.bubblemaps.io/how-to-spot-a-rug-pull-using-bubblemaps-before-it-happens/)). No independent accuracy measurement of Bubblemaps clusters on Solana exists.

## GodsEye's holder check sees twenty accounts and misses the long tail

The current screen has four parts: top-10 concentration, launch-bundle share, a one-hop funder grouping of the top-10 wallets, and RugCheck's insider networks where RugCheck has mapped the coin (`agent/src/market/holders.ts`). Defaults are bundle 25%, cluster 15%, top-10 50% and insider 20% (`agent/src/config.ts:155-161`). The whole read runs under an 8,000 ms timeout and fails closed (`agent/src/config.ts:163`, `rugcheck.ts:177-204`). The notes' gap analysis, against the Bubblemaps approach above, finds five structural misses and one false-alarm path.

The holder universe is `getTokenLargestAccounts` alone, which Solana caps at 20 token accounts (`holders.ts:122`; [Solana docs](https://solana.com/docs/rpc/http/gettokenlargestaccounts)). After program-owned accounts are dropped with an on-curve test (`holders.ts:83-89, 131`), at most ten owners form `top10Pct`. **A ring of 40 wallets holding 0.5-1% each never reaches the top 10, so `clusterPct` reads zero.** That is the RugProof pattern, where a creator sent SOL to 162 wallets that bought about half the supply, and it is structural rather than a tuning issue. Second, the check has no holder-to-holder edges: it never looks at SOL or token transfers between holders, only at each wallet's first funder, so supply split by transfer after the buy, or a funder who is not the first funder, is invisible. Third, "launch bundle" is a flow (tokens bought from a pool or curve in the mint's first two slots) while "cluster" is a stock (current top-10), and the two are never joined, so a bundle that already sold still reads as 25%+ bought, and one that moved tokens to fresh wallets reads as full but unlinked. Fourth, the two-slot window is narrower than Bubblemaps' "within seconds" and than the community norms the notes found (a 3-slot co-trade window and a 5-slot bundle window in one open skill), so snipers landing in slots 3-10 are not counted.

Fifth, the check fails silently on exactly the coins a copy signal tends to arrive on. If the mint's second page of 1,000 signatures is also full, `launchBundlePct` returns `null` ("too busy to measure", `holders.ts:137-157`, null at line 156), so any mint with roughly 2,000 or more signatures yields no launch metric. Any holder with 1,000 or more signatures yields no funder (`holders.ts:163`), so bots and old wallets drop out of the cluster without a trace. The false-alarm path runs the other way: `findFunder` (`agent/src/chain/parse.ts:301-318`) picks the account whose lamports fell most in the wallet's first transaction, and the grouping in `holders.ts:170-183` has no exchange, bot-hub or service-wallet exclusion. Two unrelated top holders who each withdrew from the same exchange form a "cluster", and if together they exceed 15% the buy is hard-blocked. Bubblemaps and the open-source tools the notes read exclude exchanges and services from cluster edges; GodsEye does not. Finally, funders are cached only for tracked wallets (`shared/src/schema.ts:56-57`), so holders of a candidate are re-read from scratch each time even though a wallet's first funder never changes once it exists.

One caution on the opposite side: the two-hop and Magic-Node style coverage Bubblemaps offers is also what makes its results harder to audit, because the link rule is unpublished. The in-house check is shallow but every number in it can be reproduced and logged.

## No published data ties cluster share to rug rates

The strongest finding of the evidence review is an absence. **No source, academic, forensic or vendor, publishes a table of the form "tokens above X% cluster or bundle share went to zero Y% of the time, versus Z% below".** What exists falls into three groups, and none substitutes for that table.

The first group is academic and indirect. MemeTrans (41,470 migrated pump.fun tokens around the $TRUMP window, preprint) merges three bundle heuristics (co-purchase, same-funder, Jito bundle ID) and finds that bundled accounts hold 28.13% of holders and **36.50% of supply at migration on average**; dropping its 35 bundle features costs 2.8 AUPRC points against 0.4 for dropping its 59 holding-concentration features (the notes' arithmetic from the ablation table) ([MemeTrans](https://arxiv.org/html/2602.13480)). The paper states its bundle heuristics are unvalidated and estimates no false-positive rate. Its precision of 0.85 at a roughly 74% base rate is a lift of about 1.1x over predicting everything high-risk (the notes' arithmetic), so cluster features rank tokens better than they classify them. Two corrections to earlier notes matter here. "Catching the Rug" by Li et al. uses only trading and liquidity-dynamics features from the first minutes and says it omits bundle-level and wash-trading features, so it provides **no evidence for or against cluster signals** ([Li et al.](https://arxiv.org/html/2608.20271v1)). Chen et al. report no top-holder or bundle share either, only that rug tokens have a median of 9 holders against 41,026 for legitimate ones, and that syndicates use wash trading to "forge the illusion of a low top-holder concentration" ([Chen et al.](https://arxiv.org/html/2603.24625v1)).

The second group is a large vendor census that measures frequency and owner behaviour, not price outcomes. Bitquery's 8,212,568 pump.fun launches (2025-10-30 to 2026-10-07) show someone other than the dev buying in block 0 on 38% of coins, dev wallets in block 0 on 21%, sniper bots on 28%, and a **median 10% of supply bought by the dev on bundled launches**, with more than half of supply on 2% of them. The dev's first sale came within a minute on 65% of launches and within a day on 90%; the study explicitly does not report rug rates or retail losses ([Bitquery](https://bitquery.io/investigations/pump-fun-snipers-bundles)). Luo et al. flag a creator-launch-block buyer in about a quarter of 6,000 projects and associate it with lower returns and shorter dump durations, descriptively, not causally ([Luo et al.](https://arxiv.org/html/2601.08641v2)). The base rate swamps any single flag: 92.22% of pump.fun tokens with at least 30 swaps show a dump under one study's rule ([Marino et al.](https://arxiv.org/html/2602.14860v1)), and 74-84% of migrated tokens are labelled high-risk in MemeTrans. For a copier the useful question is the size and speed of the drawdown, which no source conditions on cluster share.

The third group is the threshold folklore, summarised below. Provenance is the point: none states how its number was derived.

| Source | Rule | Note |
|---|---|---|
| Bubblemaps guides | Single cluster over 20-30% of supply is a red flag (checklist uses 20%); 10 of top 20 wallets linked is a warning; bundle of 10%+ is a major red flag; earlier bands: cluster <15% healthy to >50% extreme, bundle >15% serious, >30% avoid, "not hard rules" | No derivation ([rug-pull guide](https://blog.bubblemaps.io/how-to-spot-a-rug-pull-using-bubblemaps-before-it-happens/), [bundle vs cluster](https://blog.bubblemaps.io/whats-the-difference-between-bundle-cluster-2/)) |
| Webacy | Sniper holdings >30% high; bundler >20% high; >50% in block 0 critical | Page says not every early buyer is malicious ([Webacy](https://docs.webacy.com/glossary/snipers-bundlers)) |
| Conyr | Act at 10% or 20% bundled supply | No precision or recall published ([Conyr](https://conyr.ai/blog/detecting-coordinated-bundles-on-solana)) |
| Solana Tracker | Flag top 10 >70% that fund each other | A screening threshold, not a verdict ([Solana Tracker](https://www.solanatracker.io/blog/bundlers)) |
| SolBundler | Dev-linked >20-25% very high risk | Conflicted: the same site sells wallet distribution for a "clean Bubblemaps profile" ([SolBundler](https://solbundler.app/blog/how-to-avoid-pump-fun-rug-pull-2026)) |
| Bot documentation | No shipped bundle, cluster or insider veto in any copy-trading settings page read (GMGN, Banana Gun, Trojan, Maestro, BonkBot); filters exist only as user-set ranges in discovery screens | The one cluster-like copy exit is GMGN's "Dev Sell" ([GMGN](https://docs.gmgn.ai/index/auto-trading-dev-sell.md)) |

The vendors converge on 10% for bundles and 20% for clusters, which is consistent with copying each other's heuristics and is not independent confirmation. Bitquery's median of 10% places a 10% bundle rule near the middle of already-bundled launches, so "bundle present" alone would reject roughly one launch in five. **The bundle definition changes what a threshold means.** Under MemeTrans' merged definition the average is 36.5% at migration, so a fixed 25% cutoff would reject a large fraction of migrated tokens, not a tail; under Bitquery's launch-transaction definition the median is 10% and the share above 25% is not reported. These are also different populations (a migrated-token mean versus a bundled-launch median), so the figures bracket the problem rather than reconcile. GodsEye has to fix which definition its "bundle 25%" uses, and the safe move is to log raw values under each before choosing any cutoff. Because no bot ships a default, the current 25/15/50/20 cutoffs are as defensible as anything published, which is a statement about the literature, not a validation.

The case studies show a cluster is usually visible at or near launch, yet warning time is poorly documented and often shows the right actor with the wrong timing.

| Case | Cluster signature | Warning and outcome | Caveat |
|---|---|---|---|
| LIBRA (Feb 2025) | 82% of supply in one cluster in the first hour | Exit began early on 15 Feb via one-sided pool changes; about $87M extracted, token down 85% at the time of the thread | No minute-level snapshots; exit was a liquidity pull, so a token-balance monitor would not see it ([Bubblemaps](https://blog.bubblemaps.io/the-libra-playbook-how-one-cluster-drained-87-million-in-a-single-hour/)) |
| HAWK (Dec 2024) | 96% of supply in one cluster on launch day | 285 presale wallets published about a day later; 155 sold, about $3.3M; market cap about $500M to about $25M | No sell timestamps, so seconds of warning cannot be derived ([Bubblemaps](https://blog.bubblemaps.io/hawk-anatomy-of-a-celebrity-rug/)) |
| AVA AI (Nov 2024) | 23 deployer-linked wallets, CEX-funded in a tight window, about 40% of genesis supply | Revealed about 13 months after launch; price peaked two months after launch, then fell over 96% | A minute-1 flag would have preceded a two-month run-up ([Cointelegraph](https://cointelegraph.com/news/bubblemaps-ava-ai-token-sniping-deployer-wallets-solana)) |
| MYSTERY (May 2026) | 90 newly funded wallets, 90% of supply at launch | Cluster sold only about $100,000 and still held about 40% while price fell about 75% | Slow, incomplete dump ([Cointelegraph](https://cointelegraph.com/news/bubblemaps-flags-mystery-over-90-wallet-launch-sniping-cluster)) |
| Rugproof (Jul 2025) | 162 wallets funded by the creator bought about 50% at launch | Price outcome not reported | Team said SOL was redistributed to users ([Cointelegraph](https://cointelegraph.com/news/bubblemaps-rugproof-launchpad-alleged-rug-pull)) |
| FOCAI | At least 15 suspected insider wallets, over 60% of supply, about $20M | Date unconfirmed | Seen only via a search summary |

The warning-time reading is blunt. LIBRA and HAWK gave hours to about a day because the actors needed liquidity to build, which is not the regime GodsEye copies; Bitquery (dev sells within a minute on 65% of launches) and Pine Analytics (over 55% of deployer-funded snipers fully exited within a minute, nearly 85% within five, 87% of snipes profitable) point to far shorter windows for small caps, but cover different token sets ([Pine Analytics](https://pineanalytics.substack.com/p/exit-liquidity-machines)). Every case was selected because it collapsed, and I found no case where a cluster was flagged, the token held, and the flag was retracted, other than Edel Finance's co-founder denying a 160-wallet allegation (only the denial is documented). Three claims in circulation should not be used. The LAPTOP case (about 60% of top holders fresh wallets, token down over 99% within roughly an hour) is **likely a Base token, not Solana**, judging by the Aerodrome pools and Base explorer in the coverage. CAR has no source at all. The "84% of 6,000 coins sniped within five blocks" figure attributed to a University of Sydney paper could not be located. The "98.6% of pump.fun tokens rug" figure is a died-before-graduating metric, not a rug rate.

Evasion is commoditised, which sets the interpretation rule. Bubblemaps' own list includes chain funding, internal shuffling, dormancy then reactivation and "staying under alert thresholds by splitting holdings" ([Bubblemaps](https://blog.bubblemaps.io/how-to-spot-a-rug-pull-using-bubblemaps-before-it-happens/)). Conyr's example is forty wallets at 0.7% each, 28% of float, with staggered entries, varied funding paths and different DEX routes ([Conyr](https://conyr.ai/blog/detecting-coordinated-bundles-on-solana)). Luo et al. say gradual, non-launch-block bundles are substantially harder to detect. GitHub holds repos advertising tools to defeat Bubblemaps analysis and a bundler vendor sells a "clean Bubblemaps profile" (those listings were seen via search summaries and not verified). Bubblemaps' top-250 truncation hides supply below the cut by construction, the AVA cluster survived CEX funding because timing, amounts and zero history still linked it, and a burned LP blocks only pool withdrawal, not creator selling. **A dense cluster is moderately strong evidence of coordination; a clean map is weak evidence of its absence.** A flag should therefore move size down, while a clean result should not move size up. The one thing evasion cannot hide is that the cluster still has to sell, which makes co-selling the most promising post-buy trigger (a design idea, untested).

## A 34-second entry window leaves room for one cheap check

The internal timing data frames what is feasible. Across 427 mints where the 10 copy-weighted leaders made a first buy of at least 0.2 SOL since 2026-10-12, the median gap between the earliest pool GeckoTerminal knows and the leader's buy is **34 s** (p25 21 s, p75 64 s; 15% within 15 s, 74% within 60 s, 98% within 5 min), and the leaders' median hold is about 10 s (`data/copycow.db`, `wallet_swaps`, `token_info`; `agent/src/market/geckoterminal.ts`). The 107 apparent pool-creation entries of about 168 SOL at age 0 were excluded. There is a caveat that could change the framing: "pool age" may be time since the PumpSwap pool was created at migration, not since the bonding curve began. A 34 s median is hard to reconcile with a median of about 4.4 minutes from creation to graduation on pump.fun ([Marino et al.](https://arxiv.org/html/2602.14860v1)), which suggests leaders buy about half a minute after migration, when the curve phase, its bundle, its sniper wave and its funding links are minutes old. If instead the age is since curve creation, the reverse holds. A 20-mint spot check (compare each mint's first on-chain signature with `pool_created_at`) settles it. The question matters because it decides whether a fuller map is available at decision time.

What exists when is clear enough to design around. Funding links pre-date launch, so a funder-cluster check does not have to wait. Bundle membership is fixed after the first few slots. Holdings are not: Pine's deployer-funded snipers are about 11% gone by 15 s and over 55% by a minute. A single "cluster share held now" figure therefore mixes two things, because by a 30 s decision part of the launch cohort has already sold, and a cluster that has sold is a warning rather than a safe zero. The notes recommend three separate numbers per cluster: launch-bought share, current-held share and sold fraction.

Delay and recheck is the wrong tool against this clock. The copy-fill replay (10 copied leaders, 2026-10-12 to 10-26, 0.1 SOL copies, 100 bps fee each way, tape coverage 92% so drift is a lower bound) measures entry drift against the leader's fill as follows ([replay output, `npm run replay`](/Users/srinjoydas/GodsEye/agent/src/replay/model.ts)).

| Delay after leader buy | 1 s | 5 s | 15 s | 30 s | 60 s | 120 s |
|---|---|---|---|---|---|---|
| Entry price drift | 3.5% | 3.8% | 5.3% | 8.5% | 13.4% | 21.0% |
| Pooled mean copy return | -0.9% | +0.8% | +0.3% | +0.2% | -0.5% | -1.9% |

The leader's own mean return on the same positions is about 21%, and these are model outputs, not real copies, on wallets selected for profit in the same period. A recheck at +1 to +5 minutes is longer than the leader's median hold and costs more than most vetoes can recover; an outside anchor, a 2-minute-delayed entry after large wallet clusters losing about 41% per token over 93 tokens, is an unnamed researcher's claim with undisclosed exits ([TokenPost](https://www.tokenpost.com/news/investing/35409)). The placement that follows from the data is one cheap chain-based check inside the existing window, run in parallel with the quote, with its result applied as a size and exit setting. Delay-and-recheck is justified only for the narrow case where the first check was inconclusive (holders failed, timed out or was too busy to reach the launch), and then no later than the existing 60 s lateness limit. Vendor maps (Bubblemaps API, RugCheck) run log-only at +1 and +5 minutes, which tells GodsEye how late they are and how often they agree with the chain-derived numbers, without letting later information leak into a decision made at +30 s.

**Flat cutoffs are the wrong unit.** The same share of supply costs very different drawdowns depending on the base-token reserve behind it, which shrinks as the curve fills. For a constant-product pool with base reserve B, dumping cluster tokens T in full lowers the final spot price by D = 1 - 1/(1+T/B)^2. The table below is the research notes' own arithmetic, with fees ignored, computed from the pump.fun curve constants (30 SOL virtual, 1,073M virtual tokens, graduation near 85 SOL) and a derived 206.9M-token base for a freshly migrated PumpSwap pool; the 206.9M figure has not been checked against a real pool ([Pump program README](https://raw.githubusercontent.com/pump-fun/pump-public-docs/main/docs/PUMP_PROGRAM_README.md), [PumpSwap README](https://raw.githubusercontent.com/pump-fun/pump-public-docs/main/docs/PUMP_SWAP_README.md)). Cells show the cluster share of total supply, in percent, whose full sale produces the stated price drop.

| Real SOL raised on curve | -20% | -35% | -50% | -70% |
|---|---|---|---|---|
| 5 | 10.9 | 22.1 | 38.1 | 75.9 |
| 20 | 7.6 | 15.5 | 26.7 | 53.2 |
| 40 | 5.4 | 11.1 | 19.0 | 38.0 |
| 85 (graduation) | 3.3 | 6.7 | 11.6 | 23.1 |
| PumpSwap just after migration | 2.4 | 5.0 | 8.6 | 17.1 |

On a freshly migrated pool a cluster holding 5%, 15% or 30% of supply dumping fully would give about -35%, -66% or -83%, so the current 15% cluster cutoff passes clusters that cause a two-thirds drop there, and the same 15% is only about -26% at 5 SOL raised. If leaders really do buy shortly after migration, about 5% of supply is already a -35% shock, and the MemeTrans average of 36.5% bundled at migration shows why a cutoff on launch-bought share would reject nearly every fresh token. The cutoff belongs on current held share after snipers have sold. The decision shape the notes propose, to test in shadow and not to enable, is a size multiplier that is 1 below a stress level near 20%, falls linearly to 0.25-0.5 near 55-60%, and becomes a veto only when a hard structural condition also holds (a creator-funded cluster that has not reduced, a stress above about 70%, or the leader being the creator). Those levels are guesses to fit on shadow data; the proportional, pool-relative shape is the suggestion. The reasoning is that with a 74-84% high-risk base rate a veto removes most of the sample needed to learn whether the rule works, while a multiplier keeps every candidate observable and caps loss. When the holder read fails or times out, the notes favour a reduced size over skipping, with the status logged.

**Leader-aware handling follows the owner's decision that insider-pattern wallets stay copyable.** Under it, "leader in the cluster" is per-token information that changes size and exit, never `copy_weight` or a wallet verdict. The notes separate four cases. If the leader is the creator (zero RPC: the pump `TradeEvent.creator` field), the buy is not independent information and the leader controls the exit, so size is cut hard or the token is skipped. If the leader sits in the creator-linked or launch-bundle cluster, the leader's sell is probably the earliest observable cluster sell, so the existing mirror-the-leader exit is the best proxy available but lands after the leader's own price impact; the notes suggest smaller size, tighter max hold and no scale-in. If the leader is an independent early buyer, the cluster is someone else's and the leader's sell says nothing about when the cluster sells. If the leader is outside any cluster, the cluster term stands alone. Computing the stress number twice, with and without the leader's own tokens, approximates respectively the risk the leader-sell mirror cannot cover and how far the leader's exit moves price before the mirrored sell lands. That decomposition is untested, and "leader in cluster implies worse copier outcome" is a hypothesis supported only in mechanism by Pine's exit speeds and the HAWK and FOCAI cases.

**Post-buy cluster-sell monitoring is a later question.** The dominant Solana rug type is holders selling, 79.0% of 76,469 flagged tokens ([Chen et al.](https://arxiv.org/html/2603.24625v1)), and bots already ship the creator-sell version, but no source quantifies lead time or false positives and no Bubblemaps alert product was found. The notes' cheapest design watches each open position's pool or curve address, decodes every sell and compares sellers with the cluster list, adds the creator-sell trigger (the GMGN Dev Sell pattern), and adds a pool-vault balance check for liquidity-pull exits like LIBRA. Hypothesis triggers are a creator sell, a cluster sold fraction above roughly 25% (sell half, tighten the stop) and above roughly 50% or a stress above roughly 50% (sell all); all thresholds are placeholders. The notes' cost arithmetic, resting on an assumed 20 messages per wallet per hour of about 3 KB, comes to about 1.4 GB a day or $0.12 a day for 20 positions at Triton's $0.08 per GB, small next to the existing wallet stream ([Triton pricing](https://triton.one/pricing)). The binding limit is more likely a provider's cap on addresses per subscription, which is why the pool-address approach beats per-wallet lists. The relevance caveat is the important one: leaders hold about 10 s and the replay ends with only 0-3 of roughly 5,800 positions per delay still open, so a cluster monitor changes outcomes only for the tail of positions that outlive the leader. The shadow log can size that tail before anything is built.

## The vendor map is rich but unpriced, and the self-build is cheap but unvalidated

**What the Bubblemaps Data API offers.** The base is `https://api.bubblemaps.io` with an `X-ApiKey` header, spec version 0.3.2, described by the vendor as "still an early version" ([docs](https://docs.bubblemaps.io/data/api/introduction.md)). The map call costs **25 credits** (plus 50 for 250 holders, 100 for 500, 25 for `return_nodes`, 25 for `refresh`, 50 for `timestamp`), metrics 25, top holders 1, subgraph 10 plus 1 per address, and address metadata is available only on custom plans ([map](https://docs.bubblemaps.io/data/api/tokens/map.md), [authentication](https://docs.bubblemaps.io/data/api/authentication.md)). 14 chains are supported, including Solana. The only published rate limit is 10,000 calls a minute per IP; going over credits returns 429. Monthly credit allowances and prices **are not published anywhere readable**; the Pro platform is a JavaScript app that returned nothing to the research fetcher. Freshness wording is thin: "cache TTL depends on token age", `refresh=true` bypasses the cache, queries run "a few ms" on cache hits up to a minute for outliers with "most" under 15 s (the vendor's statement, not measured), and the V2 app guarantees a refresh within six hours, with newly launched tokens possibly lagging (that wording came through a summarising fetch and should be rechecked on the page). There is no streaming or webhook in the 11 REST operations. Bubblemaps' docs name trading bots as a Data API use case ([B2B products](https://docs.bubblemaps.io/introduction.md)). The Terms & Conditions are hosted on Notion and could not be read, so commercial use is invited in the docs but **unverified in the binding terms, and redistribution on a public site is unaddressed**. The sanctioned public display is the iFrame product with a `partnerId`, which has no subscription for basic uses such as a token team showing its own map and volume-based plans for platforms ([iframe pricing](https://docs.bubblemaps.io/iframe/pricing.md)); whether GodsEye's public site counts as "basic" is not stated.

Cost arithmetic, from the notes' figures: at the internal rate of roughly 430-600 candidate mints a week, one 25-credit metrics or map call each is about 11,000-15,000 credits a week, and a forced-fresh 50-credit call about 21,000-30,000. A validation pass over 200 tokens at the full 125-credit configuration (map, 250 holders, nodes, refresh) is about 25,000 credits per pass. The unknown is what a credit costs. The notes' realistic role for the API is an asynchronous second stage: re-score a held position or gate an add-on at +1 to +5 minutes, given a stated 15 s typical latency and no documentation of what a seconds-old pump.fun mint returns (data, 404 or stale data).

**Alternatives.** Birdeye's `holder-profile` and `holder-positions` endpoints (released 2026-04-17, Solana) return per-tag holder counts, supply share, buy and sell volume and unrealized PnL for `bundler`, `sniper`, `insider` and `dev` tags; the tags are undefined on the page, bundler data is stated accurate only for tokens created from 2026-03-01, and the credit cost is unstated ([Birdeye changelog](https://data.birdeye.so/docs/changelog/20260417-release-token-holder-profile-positions-apis)). Solana Tracker has a risk object with snipers, insiders and bundlers and published plans (Free 10,000 requests a month at 3 per second; EUR 50, 200,000; EUR 200, 1M; EUR 397, 10M with a WebSocket datastream), and its terms allow bots and displaying derived data while prohibiting redistribution of raw API data ([pricing](https://docs.solanatracker.io/pricing.md), [terms](https://www.solanatracker.io/terms)). RugCheck's insider graph is already in the screen; its JSON schema and key requirement were not confirmed. GMGN's data API is whitelist-only. Helius and Solscan give first-funder primitives, not clusters. No source compares the accuracy or latency of any of these against Bubblemaps, so ranking them needs the shadow-log harness. The Solana Tracker terms are also the nearest template for what a data licence might say, but they are not evidence about Bubblemaps' terms.

**The self-build.** There is no maintained, licensed open-source bubble-map engine for Solana. The closest reference, seizd (created 2026-10-23, no licence, no stars, no accuracy data), is useful for its edge taxonomy and its service-funder test, and because it carries no licence the safe course is to re-implement the described ideas and not copy code ([seizd](https://github.com/benguadomar/seizd)). The notes' design has five parts. First, a per-mint launch ledger fed by the Yellowstone stream GodsEye already runs (`agent/src/stream/stream.ts:127-134`), keeping for each young mint every buy and sell with wallet, slot, signature, size and tip; it removes the 2,000-signature ceiling and supports a launch window of 5-10 slots (an assumed value taken from the community skill) with `bought`, `sold` and `held_now` per wallet and cluster-level current, peak and exited share. The stream carries the transaction index within a block only if `convertGrpcTx` passes it through (`agent/src/stream/convert.ts:49-63` keeps only the slot), and that index is unverified. Second, exact current holders from a snapshot, ledger or account subscription, covering both token programs because pump `create_v2` uses Token-2022. Third, a **permanent funder cache** (`address_funding`) since a first funder never changes, filled on misses by Helius `getTransactionsForAddress` in ascending order with `limit: 1`, with a batch identity call to label exchange funders. Fourth, edges in tiers: Tier A alone can cluster (direct SOL or token transfer between holders, a shared buy transaction or fee payer, a shared non-service funder with small fan-out, creator funding); Tier B needs two independent signals (same slot or bundle fingerprint, near-identical buy sizes, narrow-window CEX funding of fresh wallets, so the AVA pattern is downgraded, not discarded); Tier C is display only. Clusters are union-find over Tier A plus qualified Tier B, a hard block needs a Tier A cluster, and a Tier B-only cluster only warns. Fifth, a **service-wallet filter** on funders: a deny-list (24 pump fee recipients, 8 Jito tips, programs, PDAs, and for holder-rewards coins the pump distributor), a fan-out count (the earlier note proposed 25 distinct wallets, derived by reasoning), and seizd's throughput test (1,000 signatures in under 6 hours) ([seizd funding.ts](https://raw.githubusercontent.com/benguadomar/seizd/main/server/src/analysis/funding.ts)).

Costs and latency are estimates, not measurements. The notes put a typical token at 100-400 Helius credits and a worst case of 500-1,000, so about 10,000-100,000 tokens a month on the 10M-credit Developer plan ($49), and a latency of 2-5 s inside the 8 s timeout; the work can start at mint creation so most wallets are cached by the time a leader buys ([Helius pricing](https://www.helius.dev/pricing), [credits](https://www.helius.dev/docs/billing/credits)). One discrepancy must be settled with a test call: the `getTransactionsForAddress` method page gives 10 credits (flat for signatures, or 10 per 100 full transactions), while a search summary says 100 credits and a Developer-plan requirement ([method page](https://www.helius.dev/docs/rpc/gettransactionsforaddress.md)). The method is also Helius-only, so on other RPC providers it falls back to more calls per wallet. The pump-specific handling includes reading the `BondingCurve` account for creator, Mayhem flag and exact curve balance, computing shares on both total and circulating supply, and flagging Mayhem coins (an extra billion tokens held by an agent whose vault location is undocumented).

The staged path with the lowest regret, in the notes' judgement, is to fix the false-positive and null problems in the existing check, add the ledger and Tier A edges for the top 50-100 holders, run Bubblemaps in shadow beside it for a few weeks, and then decide component by component. The in-house route wins on real-time visibility, no dependence on cache age, current versus peak shares and near-zero marginal cost once funders are cached; it loses on cross-token and cross-chain links, labels and tuning without ground truth.

## Measure before any rule blocks anything

The shadow log is designed for this and has not run: it writes `shadow_candidates` for each first copyable leader buy, with raw inputs and screen timings, and `shadow_samples` at 1, 5, 15, 30 min and 1, 6, 24 h (`agent/src/shadow/log.ts`, `sampler.ts`, `labels.ts`). **The table does not exist in the local database until the agent is restarted**, so there are no outcome rows to analyse. The replay explicitly does not model rug and holder checks and cannot yet take a per-token multiplier.

The notes' additions to the log are chain-derived columns at decision time, +60 s and +300 s in a separate cluster-sample table: cluster share by time since launch, launch-bought versus current-held versus sold fraction, wallet count, the creator-funded flag, the same shares excluding the leader's tokens, the stress number with the reserves behind it, and raw values under both bundle definitions (Bitquery-style launch transaction and MemeTrans-style merged). Leader context columns cover `leader_is_creator`, launch-bundle membership, funding by the creator cluster and slot offset from creation. Post-entry columns record first cluster sell, cluster sold fraction at 1, 5, 15 and 60 minutes, creator sell time and size, leader sell time, and time to the first 25% and 50% drawdown, so lead time can be measured as a distribution. Time since launch is stored on two clocks (mint creation and first pool) to resolve the pool-age question. Vendor columns (Bubblemaps score and cluster share, RugCheck insiders) are log-only with request time. Every cluster sample carries a status so a "too busy to reach launch" null is its own state, not a missing value.

The evaluation protocol freezes definitions and cutoffs before looking at outcomes, computes each rule's counterfactual against shadow outcomes and replay fills, and compares buckets (deciles or four to five bands) rather than one cutoff, with a chronological split. The notes' sample-size arithmetic is about 135 tokens per bucket to separate a 35% from a 20% rug-like rate, about 325 for 35% against 25%, and a zero-event bound near 3/n. At roughly 430-600 mints a week, a worst-severity bucket holding 15-20% of candidates (an unknown) reaches 135 in about 1.5-2 weeks and 325 in 4-5 weeks. Tokens bought by two or more copied wallets are not independent, so distinct mints count. A small randomized exploration sample of 3-5% on vetoed tokens keeps the blocked group's outcomes from being purely modelled. The pitfalls the notes list apply directly: only leader-bought tokens are observed (cutoffs learned there do not transfer to other leaders), a cluster that has sold looks cluster-free if measured afterward, silent rugs look like missing data, a leader's own exit confounds the price path, rule features and labels must not be circular, many knobs on a few hundred tokens a week overfit, and a vendor map fetched at +5 minutes contains information a +30 s decision did not have.

To compare a home-built map with Bubblemaps, the notes propose 150-300 tokens stratified by age and venue (fresh curve, just-graduated PumpSwap, older, later-rugged and held, plus known Bubblemaps-flagged cases), using the same 250-holder configuration with nodes on and off. Adjusted Rand Index and adjusted mutual information measure partition agreement on common holders, with a supply-weighted pairwise version; magnitude agreement uses Spearman correlation and median absolute error of cluster share; decision agreement at the bot's cutoffs uses a confusion matrix and Cohen's kappa, with a triage of each disagreement. Agreement with Bubblemaps is a reference, not ground truth, so the outcome check against rug or fall of at least 80% within N hours remains the test that matters. Bubblemaps' `timestamp` parameter (+50 credits) offers a retrospective map for tokens not logged live, but whether it returns early-state clusters for a token younger than a minute is untested.

## Conclusion

The research changes the question. "Should we call Bubblemaps?" assumes the vendor map is the better detector, and nothing in the evidence supports that or its opposite: there is no accuracy measurement for Bubblemaps, no cluster-to-rug table anywhere, and no bot that ships a cluster veto to imitate. What the evidence does support is narrower and more useful. The in-house check has demonstrable structural blind spots (twenty accounts, no holder edges, silent nulls, no service filter) that a vendor call would not fix inside the entry window, and a measured clock (34 s to the leader's buy, 10 s hold, 13-21% drift at 60-120 s) that rules out waiting for a slow map. A cluster signal also answers a different question from the one a flat cutoff asks. Its value is probably in how much a token can fall and how soon, which the pool-relative stress number captures and a share-of-supply percentage does not, and in what the leader's own relation to the cluster says about exit, which is per-token information the owner's insider-wallet policy leaves free to use.

The asymmetry between a dirty and a clean map should shape every rule. Evasion is cheap, so a dense cluster is real evidence and a clean map is not, which argues for size reductions on positive findings and no upsizing on negative ones. The largest risk in the whole programme is not missing a rug but acting on thresholds nobody has validated: with 74-92% of fresh tokens dumping anyway, a flat veto would remove most of the sample needed to learn anything. The cheapest high-value step is the least exciting one: restart the agent so the shadow log fills, answer the pool-age question with twenty mints, and add the cluster columns, so the first real bucket comparison arrives in a few weeks rather than after a build.
